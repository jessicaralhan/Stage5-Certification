### Destructive Changes

❌ **CRITICAL**: Production RDS cluster forced replacement on subnet group change.
   - **Resource**: `aws_rds_cluster.prod`
   - **Action**: Destroy and recreate (indicated by `-/+` in plan)
   - **Forcing Attribute**: `db_subnet_group_name`
   - **Environment**: Production
   - **Impact**: Full cluster destruction triggers data loss risk, extended downtime, and manual recovery procedures. Any in-flight transactions are terminated immediately.
   - **Why This Matters**: Unplanned production database outages violate RTO/RPO requirements and expose the organization to data consistency issues and customer-facing service degradation.

### Security Exposure

⚠️ **MEDIUM**: RDS cluster uses AWS-managed encryption instead of customer-managed keys.
   - **Resource**: `aws_rds_cluster.prod`
   - **Issue**: `storage_encrypted` is set to `true`, but `kms_key_id` is not specified, defaulting to AWS-managed key material.
   - **Impact**: Organization cannot rotate or revoke encryption keys independently; key custody remains with AWS. Compliance frameworks (HIPAA, PCI-DSS, FedRAMP) often require customer-managed key control.
   - **Recommendation**: Specify a customer-managed KMS key via the `kms_key_id` parameter. A new `aws_kms_key.rds` resource is already planned; ensure key rotation is enabled and access is restricted to database service roles only.

⚠️ **MEDIUM**: RDS cluster allows password-only authentication instead of enforcing IAM database authentication.
   - **Resource**: `aws_rds_cluster.prod`
   - **Issue**: `iam_database_authentication_enabled` is set to `false`, permitting traditional username/password credentials only.
   - **Impact**: Database credentials cannot be centrally rotated via IAM; passwords are static and must be managed separately. This increases exposure to credential compromise and complicates audit trails.
   - **Recommendation**: Set `iam_database_authentication_enabled` to `true` and migrate database users to IAM-authenticated roles. This enables credential rotation via temporary tokens and integrates with existing IAM audit logging.

### Cost Impact

💰 **Ongoing Cost**: AWS KMS key management and usage.
   - **Resource**: `aws_kms_key.rds` (newly created)
   - **Details**: AWS KMS keys incur monthly key management fees (~$1/month per key) plus per-request encryption/decryption costs.

💰 **One-Time Cost**: RDS cluster replacement and data migration.
   - **Impact**: Forced recreation of `aws_rds_cluster.prod` requires data export, downtime, re-import, and application failover. Depending on cluster size and replication lag, this may incur significant operational costs and SLA penalties.

### Priority 2: HIGH — Enable Customer-Managed Encryption

1. **Ensure `kms_key_id` is populated with the newly created KMS key.**
   - Verify that `aws_kms_key.rds` is created before the RDS cluster references it (use explicit `depends_on` in Terraform if needed).

3. **Restrict KMS key access.**
   - Update the KMS key policy to allow only:
     - RDS service principal (`rds.amazonaws.com`)
     - Database administrator IAM roles
     - Exclude broad administrator access (`Principal: "*"`)

4. **Test encryption with customer-managed keys in a non-production environment first.**
   - Verify that backup/restore operations function correctly with customer-managed keys.

### Priority 3: HIGH — Enable IAM Database Authentication

1. **Set `iam_database_authentication_enabled = true` in the RDS cluster resource.**

2. **Create IAM database users corresponding to existing application roles.**
   - Use AWS documentation on "IAM DB Authentication" to generate token-based credentials.
   - Each application instance should assume an IAM role with a policy granting `rds-db:connect` permission.

3. **Update application connection strings to use IAM tokens.**
   - Replace hardcoded passwords with dynamic token generation at connection time.
   - This typically requires a small application code change (most drivers support token-based auth natively).

4. **Retire static password-based accounts after IAM migration is complete.**
   - Reduce the attack surface by removing unnecessary master user credentials.

5. **Enable Enhanced Monitoring and audit logging for database connections.**
   - Configure CloudWatch Logs to log all connection attempts.

2. **Plan maintenance windows to minimize downtime costs.**
   - Schedule blue-green migrations during periods of lowest traffic to reduce revenue impact.

3. **Reserve capacity if cluster size will remain stable.**
   - Consider RDS reserved instances for long-term cost savings (if applicable to cluster configuration).
