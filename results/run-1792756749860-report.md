# Infrastructure Security Review Report

## Executive Summary

This report covers the Terraform Safety Review of the CloudTrail audit-logging infrastructure, which spans the KMS key `aws_kms_key.logs`, the S3 bucket policy `aws_s3_bucket_policy.trail`, the bucket versioning and logging configuration (`aws_s3_bucket_versioning.logs`, `aws_s3_bucket_logging.logs`), and the associated cost profile. The combined risk level is **HIGH**, and the verdict is **REVISE**. The review found no destructive changes but identified four security exposures, one rated HIGH and three rated MEDIUM. The HIGH finding is that CloudTrail cannot write to the SSE-KMS encrypted log bucket because the KMS key has no key policy granting `cloudtrail.amazonaws.com` access, which creates an audit gap. The change cannot be approved until a complete Terraform plan incorporating remediations is resubmitted and validated. Immediate action is required on the KMS key policy and the CloudTrail `kms_key_id` binding, followed by the bucket hardening items.

## Infrastructure (Terraform) Findings

Risk Level: **HIGH**

### Destructive Changes

None identified. The plan contains no destroy or replace actions.

### Security Exposure

❌ **HIGH**: CloudTrail log delivery to the encrypted bucket may fail
- **Resource**: `aws_kms_key.logs`
- **Exposure type**: Missing key policy and missing CloudTrail encryption binding
- **Issue**: The key has no key policy, and `aws_cloudtrail` has no `kms_key_id`. The `cloudtrail.amazonaws.com` principal lacks `kms:GenerateDataKey*`, so log delivery to the SSE-KMS bucket may fail.
- **Impact**: Audit events may not be recorded. This is a silent gap in the audit trail, and it is the most serious item in this review because logs the organization relies on for detection and compliance may never be written.

⚠️ **MEDIUM**: Non-TLS requests are not explicitly denied
- **Resource**: `aws_s3_bucket_policy.trail`
- **Exposure type**: Incomplete transport-encryption enforcement
- **Issue**: The policy contains no statement denying requests where `aws:SecureTransport` is `false`. The condition is enforced only on the CloudTrail `PutObject` grant.
- **Impact**: Any principal with access to the bucket can read or write audit logs over unencrypted HTTP. Audit log confidentiality and integrity depend on TLS, and that requirement should apply to all callers.

⚠️ **MEDIUM**: Audit logs can be deleted or tampered with
- **Resource**: `aws_s3_bucket_versioning.logs`
- **Exposure type**: No MFA Delete and no Object Lock
- **Issue**: MFA Delete is disabled and S3 Object Lock is not configured. Any principal with `s3:DeleteObject` can permanently delete or overwrite audit logs.
- **Impact**: An attacker or an insider with delete permissions can destroy evidence after a compromise, undermining incident response and forensic investigations.

⚠️ **MEDIUM**: Access logs write into the audit bucket they monitor
- **Resource**: `aws_s3_bucket_logging.logs`
- **Exposure type**: Self-targeted server access logging
- **Issue**: Access logs target the same bucket they monitor. This mixes access logs with CloudTrail audit logs and can generate recursive log writes.
- **Impact**: Audit data becomes harder to review and filter, and the logging loop increases request volume and storage consumption.

### Cost Impact

- **`aws_kms_key.logs`**: The new KMS key adds a fixed monthly charge plus per-request KMS charges for S3 and CloudTrail writes. The impact is partly reduced by `bucket_key_enabled = true`. Accept this cost as a requirement of encrypting audit logs, and track it with the KMS request metrics.
- **`aws_s3_bucket_logging.logs`**: Self-targeted access logging continuously writes new objects into the audit bucket, which increases request and storage costs over time. Resolving the self-targeting issue (see Recommendations) also resolves this cost driver.
- **`aws_s3_bucket_versioning.logs`**: Versioning is enabled with no lifecycle rules, so noncurrent versions of CloudTrail logs accumulate storage charges indefinitely. Lifecycle rules must be defined in alignment with the retention requirements (see Recommendations).

### Verdict: REVISE

The reviewer returned REVISE. The reviewer's stated reasoning is that the remediation output could not be validated against the findings and that no actual HCL plan was provided. The remediation output was recorded with a populated fix for `aws_kms_key.logs`, but the reviewer's conclusion still holds for the following reasons:

- Only one of the four findings (`aws_kms_key.logs`) has a proposed remediation. The TLS deny, the MFA Delete and Object Lock gap, and the self-targeted logging issue have none.
- The proposed KMS fix is a policy fragment, not a complete HCL plan. It must be integrated into `aws_kms_key.logs` and paired with `kms_key_id = aws_kms_key.logs.arn` on `aws_cloudtrail`, and the resulting plan must be reviewed for any create, update, or replace actions.
- The reviewer's stated basis cited an unfilled `{{remediations}}` placeholder. That does not match the recorded generator output, so the audit record should be corrected before resubmission to avoid confusion during review.

Do not merge or apply this change until a full plan has been resubmitted and reviewed.
