## Container Security (Kubernetes) Findings

Risk Level: **MEDIUM** (analyzer rating; pipeline combined rating reported as LOW)

The `api-server` workload has solid baseline hardening. The remaining gaps are concentrated in network isolation, syscall filtering, and credential exposure.

### RBAC Issues

**LOW**: `configmaps` rule in Role `api-server-role` (namespace `secure-app`)
- **Issue:** The rule grants the `list` verb with `resourceNames` restricted to `api-config`. Kubernetes does not enforce `resourceNames` on `list` or `watch` requests, so the restriction does not limit listing. Any ConfigMap in `secure-app` can be listed and read.
- **Why it matters:** The intended scope of access to `api-config` is not enforced. Listing returns all ConfigMaps in the namespace, which may expose unrelated configuration.
- **Fix needed:** Remove `list` from the `configmaps` rule and keep `get` restricted to `resourceNames: [api-config]`. If the workload needs enumeration, move the required data into a single named ConfigMap and grant only `get` on it.

**LOW**: `secrets` rule in Role `api-server-role` (namespace `secure-app`)
- **Issue:** The rule grants `get` on the secret `db-password`. This is appropriate in principle, but the grant is only correct if `db-password` is the only secret the workload needs.
- **Why it matters:** Any future reference to another secret will require a Role change. This is a maintenance and review checkpoint, not a current exposure.
- **Fix needed:** Confirm with the application owner that `db-password` is the only secret required. Document this in the Role's annotations so future changes are reviewed.

### Network Policies

**MEDIUM**: Namespace `secure-app` has no default-deny NetworkPolicy
- **Policy gap:** Pods not selected by `api-server-policy` accept and send unrestricted traffic.
- **Impact:** Any pod in `secure-app` that is not covered by `api-server-policy` can communicate with any destination, which weakens the isolation that `api-server-policy` is meant to provide.
- **Fix needed:** Add a default-deny policy in `secure-app` that selects all pods and declares both `Ingress` and `Egress` policy types with no allow rules. Then re-allow only the traffic that `api-server-policy` permits.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: secure-app
spec:
  podSelector: {}
  policyTypes:
    - Ingress
    - Egress
```

**LOW**: DNS egress rule in `api-server-policy` uses an unrestricted namespace selector
- **Policy gap:** The rule uses `namespaceSelector: {}` with `podSelector: k8s-app: kube-dns`, which permits DNS traffic to kube-dns pods in any namespace rather than only `kube-system`.
- **Impact:** A pod in another namespace labeled `k8s-app: kube-dns` could receive DNS queries from `api-server`, which is a possible exfiltration path.
- **Fix needed:** Scope the selector to the `kube-system` namespace by name:

```yaml
namespaceSelector:
  matchLabels:
    kubernetes.io/metadata.name: kube-system
podSelector:
  matchLabels:
    k8s-app: kube-dns
```

**LOW**: DNS egress rule in `api-server-policy` allows only UDP port 53
- **Policy gap:** TCP port 53 is not permitted, so DNS fallback for large responses (for example, responses over 512 bytes or DNSSEC responses) is blocked.
- **Impact:** Intermittent name resolution failures for `api-server` that are difficult to diagnose.
- **Fix needed:** Add a TCP port 53 rule alongside the existing UDP rule, using the same restricted `namespaceSelector` and `podSelector` described above.

### Security Contexts

**MEDIUM**: Deployment `api-server` (namespace `secure-app`), container `api`
- **Missing setting:** `seccompProfile` is not set to `RuntimeDefault` in the pod spec.
- **Impact:** The `api` container runs without an explicit seccomp syscall filter, so it can invoke syscalls that the runtime default profile would block.
- **Fix needed:** Add the following to the pod-level `securityContext` of Deployment `api-server`:

```yaml
securityContext:
  seccompProfile:
    type: RuntimeDefault
```

**LOW**: Deployment `api-server` (namespace `secure-app`), container `api`
- **Gap:** The image is referenced by the mutable tag `api-server:v1.2.3` rather than an immutable digest.
- **Impact:** The image contents can change without any manifest change, so the deployed artifact is not guaranteed to be the one that was reviewed.
- **Fix needed:** Pin the image by digest, for example `api-server@sha256:<digest>`, and record the tag in an annotation for readability.

### Pod Security

**MEDIUM**: ServiceAccount `api-server` (namespace `secure-app`)
- **Issue:** `automountServiceAccountToken` is not set to `false`, so the API token is mounted into the `api` container even though the workload needs only the narrow permissions in `api-server-role`.
- **Impact:** A compromised container can use the token to call the Kubernetes API with the permissions bound to this ServiceAccount.
- **Fix needed:** Set `automountServiceAccountToken: false` on ServiceAccount `api-server`. Only set it to `true` at the pod level if the application actually calls the API.

**MEDIUM**: Deployment `api-server` (namespace `secure-app`), pod spec
- **Issue:** `automountServiceAccountToken` is not set to `false` at the pod level, so the token is auto-mounted into the `api` container.
- **Impact:** Same as above. A pod-level setting is needed because pod-level values take precedence over the ServiceAccount setting and should be explicit.
- **Fix needed:** Add `automountServiceAccountToken: false` to the pod spec of Deployment `api-server`.
