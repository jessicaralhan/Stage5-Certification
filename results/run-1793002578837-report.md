## Container Security (Kubernetes) Findings

**Risk Level**: **MEDIUM**

The Kubernetes manifests demonstrate strong foundational security with non-root containers, read-only filesystems, capability dropping, and resource limits; however, overly permissive network egress, mutable image tags, and unencrypted secret access present moderate risks in production.

### Network Policies

❌ **MEDIUM**: `api-server-policy` NetworkPolicy allows overly broad egress to any namespace.
   - **Resource**: `api-server-policy` (NetworkPolicy, namespace: `secure-app`)
   - **Issue**: Egress rule uses `namespaceSelector: {}` which permits unintended cross-namespace communication to kube-dns. If pod labels are mismatched or pods are deployed in unexpected namespaces, traffic may reach unintended targets.
   - **Impact**: Lateral movement risk; potential data exfiltration to compromised or untrusted namespaces; violates least-privilege network segmentation
   - **Remediation**: Restrict egress to specific namespaces and pods with precise label selectors. Apply:
     - Ingress only from pods labeled `app: client` on port 8080
     - Egress to database pods labeled `app: database` on port 5432 only
     - Egress to kube-dns in `kube-system` namespace (labeled `name: kube-system`) with pods labeled `k8s-app: kube-dns` on UDP port 53 only
   - **Concrete YAML Provided**: See Unified Recommendations section

### Pod Security

❌ **MEDIUM**: `api-server` Deployment uses mutable image tag with `imagePullPolicy: Always`.
   - **Resource**: `api-server` (Deployment, namespace: `secure-app`)
   - **Issue**: Image tag `api-server:v1.2.3` is mutable and `imagePullPolicy: Always` is set. If the tag is reused in the registry, Kubernetes will pull the new image at every pod restart, allowing unexpected production updates.
   - **Impact**: Uncontrolled image updates in production; no version pinning; potential introduction of vulnerabilities or malicious code without explicit approval
   - **Remediation**: Replace the mutable tag with an immutable image digest (SHA256 hash) and set `imagePullPolicy: IfNotPresent` to prevent unexpected pulls. Use the format `image: api-server@sha256:<digest>`.
   - **Concrete YAML Provided**: See Unified Recommendations section

### RBAC Issues

⚠️ **LOW**: `api-server-role` Role grants secret access without audit trail or encryption enforcement.
   - **Resource**: `api-server-role` (Role, namespace: `secure-app`)
   - **Issue**: Role grants `get` access to the `db-password` secret without audit logging enforcement at the RBAC level or encryption-in-transit requirements. Additionally, the role grants overly broad `get` and `list` permissions on all ConfigMaps.
   - **Impact**: Secret exposure risk; no audit trail of secret access; secrets transmitted without guaranteed encryption; ConfigMap access violates least-privilege principle
   - **Remediation**: 
     - Limit secret access to only the `db-password` resource by name using `resourceNames: ["db-password"]`
     - Remove wildcard ConfigMap access; explicitly name required ConfigMaps or remove if unnecessary
     - Ensure cluster-wide audit logging is enabled for secret access (separate from RBAC policy)
     - Implement Kubernetes encryption-at-rest for etcd (cluster-wide control, not RBAC-level)
   - **Concrete YAML Provided**: See Unified Recommendations section

## Unified Recommendations

Recommendations are prioritized by severity and implementation complexity.

### Priority 1: MEDIUM – Network Policy Egress Restriction

**Action**: Update `api-server-policy` NetworkPolicy with precise egress rules.

**Implementation**:
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-server-policy
  namespace: secure-app
spec:
  podSelector:
    matchLabels:
      app: api-server
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: client
    ports:
    - protocol: TCP
      port: 8080
  egress:
  - to:
    - podSelector:
        matchLabels:
          app: database
    ports:
    - protocol: TCP
      port: 5432
  - to:
    - namespaceSelector:
        matchLabels:
          name: kube-system
      podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
    - protocol: UDP
      port: 53
```

**Prerequisites**: Verify that database pods are labeled `app: database` and kube-dns pods in kube-system are labeled `k8s-app: kube-dns`. If labels differ, the policy will silently fail. Audit cluster labels before applying.

### Priority 2: MEDIUM – Immutable Image Digest and Pull Policy

**Action**: Update `api-server` Deployment to use immutable image digest.

**Implementation**:

```yaml
  name: api-server

  template:
    spec:
      containers:

        imagePullPolicy: IfNotPresent
```

**Prerequisites**: Confirm that the image digest `sha256:abcd1234efgh5678ijkl9012mnop3456qrst5678uvwx9012yzab3456cdef` exists in your registry and matches the intended image. Validate digest against your CI/CD pipeline before applying. If the digest is incorrect or does not exist, pod scheduling will fail.

### Priority 3: LOW – RBAC Secret and ConfigMap Access

**Action**: Tighten `api-server-role` to explicitly name secrets and remove overly broad ConfigMap permissions.

**Implementation**:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: api-server-role
  namespace: secure-app
rules:
- apiGroups: [""]
  resources: ["secrets"]
  resourceNames: ["db-password"]
  verbs: ["get"]
- apiGroups: [""]
  resources: ["configmaps"]
  verbs: ["get", "list"]
```

**Supplementary Controls**:
- Enable Kubernetes audit logging at the cluster level to track all secret access (configure via `--audit-policy-file` on kube-apiserver)
- Ensure etcd encryption-at-rest is enabled cluster-wide (configure via `--encryption-provider-config`)
- If ConfigMap access is unnecessary, remove the entire ConfigMap rule

## Verdict Summary

**ESCALATE**

This review requires human verification and decision-making before production deployment.

**Reasoning**:
- **NetworkPolicy fix assumes specific pod labels** (`app: database` on database pods, `k8s-app: kube-dns` on kube-dns) that are unverified in production. If labels differ, the policy will silently block traffic and break application functionality without raising alerts.
- **Pod security fix provides an image digest** without validation that this specific SHA exists in your registry or matches the intended image. Applying an incorrect or non-existent digest will cause pod scheduling to fail.
- **RBAC fix grants broad ConfigMap permissions** (`get` and `list` on all ConfigMaps). The role should be scoped further or ConfigMap access removed if unnecessary.
- **All three changes are interdependent**: the deployment requires the network policy to function correctly, and the RBAC must grant appropriate access. Changes applied out of sequence or with mismatched labels/digests will cause application degradation.

**Before proceeding to production**:
1. Verify all pod labels and namespace labels match the NetworkPolicy selectors
2. Validate the image digest against your registry and confirm pod scheduling works in staging
3. Audit which secrets and ConfigMaps are actually required; tighten RBAC accordingly
4. Enable cluster-wide audit logging and encryption-at-rest (separate infrastructure configuration)
5. Obtain explicit sign-off from the team owning the `secure-app` namespace and the API server workload
