### Security Exposure

#### 1. ❌ **HIGH**: Missing S3 Object Protection (Versioning, MFA Delete, Object Lock)

- **Resource**: `aws_s3_bucket.app`
- **Issue**: S3 bucket has no versioning, MFA delete, or object lock configured, increasing risk of accidental or malicious data loss in production.
- **Impact**: Production data is unprotected against unintended overwrites or deletion. Without versioning, previous object states cannot be recovered. MFA delete provides an additional authorization gate for destructive operations.
- **Remediation**: Implement S3 versioning and object lock with governance-mode retention:
  ```hcl
  resource "aws_s3_bucket_versioning" "app" {
    bucket = aws_s3_bucket.app.id
    versioning_configuration {
      status = "Enabled"
    }
  }
  
  resource "aws_s3_bucket_object_lock_configuration" "app" {
    bucket = aws_s3_bucket.app.id
    rule {
      default_retention {
        mode = "GOVERNANCE"
        days = 30
      }
    }
  }
  ```
- **Note**: Object lock is immutable after bucket creation and requires bucket recreation if not enabled at launch.

#### 2. ❌ **HIGH**: Missing S3 Access Logging

- **Resource**: `aws_s3_bucket.app`
- **Issue**: S3 bucket has no logging enabled, preventing audit trail of access and modifications in production environment.
- **Impact**: No audit trail for data access, modifications, or security incidents. Compliance frameworks (SOC 2, PCI-DSS, HIPAA) require access logging for production data stores.
- **Remediation**: Enable S3 access logging to a dedicated log bucket:
  ```hcl
  resource "aws_s3_bucket_logging" "app" {
    bucket            = aws_s3_bucket.app.id
    target_bucket     = aws_s3_bucket.log_bucket.id
    target_prefix     = "s3-access-logs/"
  }
  ```
- **Note**: A separate log bucket must be created with appropriate retention policies and lifecycle rules to manage storage costs.

#### 3. ⚠️ **MEDIUM**: Weak S3 Encryption (AES256 vs. KMS)

- **Resource**: `aws_s3_bucket_server_side_encryption_configuration.app`
- **Issue**: S3 bucket uses AES256 (SSE-S3) instead of KMS encryption, limiting key rotation and audit control in production.
- **Impact**: Encryption keys are managed entirely by AWS with no customer visibility or rotation control. No CloudTrail logging of encryption key usage. Cannot enforce encryption key policies or restrict decryption by principal.
- **Remediation**: Switch to KMS-managed encryption:
  ```hcl
  resource "aws_s3_bucket_server_side_encryption_configuration" "app" {
    bucket = aws_s3_bucket.app.id
    rule {
      apply_server_side_encryption_by_default {
        sse_algorithm     = "aws:kms"
        kms_master_key_id = aws_kms_key.s3.arn
      }
      bucket_key_enabled = true
    }
  }
  ```
- **Note**: Requires creation of a KMS key with appropriate key policy. Existing SSE-S3 encrypted objects must be re-encrypted.

#### 4. ⚠️ **MEDIUM**: Overly Broad S3 Write Permissions

- **Resource**: `aws_iam_role_policy.app`
- **Issue**: IAM policy grants `s3:PutObject` permission without conditions, allowing role to overwrite or delete existing objects in the bucket.
- **Impact**: Any principal assuming this role can modify or replace any object in the bucket without server-side encryption enforcement. Increases risk of data tampering or unencrypted uploads bypassing security controls.
- **Remediation**: Restrict `PutObject` with mandatory encryption and resource prefix conditions:
  ```json
  {
    "Effect": "Allow",
    "Action": "s3:PutObject",
    "Resource": "arn:aws:s3:::bucket-name/uploads/*",
    "Condition": {
      "StringEquals": {
        "s3:x-amz-server-side-encryption": "aws:kms"
      }
    }
  }
  ```
- **Note**: Scope write access to specific prefixes (e.g., `uploads/`) rather than the entire bucket. Require KMS encryption for all uploads.
