## Infrastructure (Terraform) Findings

**Risk Level**: **CRITICAL**

### Destructive Changes

❌ **CRITICAL**: Production RDS cluster will be destroyed and recreated.
   - **Resource**: `aws_rds_cluster.prod`
   - **Action**: Destroy and recreate
   - **Forcing Attribute**: `db_subnet_group_name`
   - **Environment**: Production
   - **Impact**: Complete production downtime during cluster replacement; potential data loss if backup mechanisms are not properly configured; service interruption for all dependent applications
   - **Why This Matters**: RDS cluster destruction in production is irreversible without backups and violates standard infrastructure stability practices

### Security Exposure

⚠️ **HIGH**: RDS cluster encryption uses AWS-managed keys instead of customer-managed KMS encryption.
   - **Resource**: `aws_rds_cluster.prod`
   - **Issue**: Configuration has `storage_encrypted = true` but lacks explicit `kms_key_id` specification, defaulting to AWS-managed key
   - **Impact**: No customer control over encryption key access, limiting audit capabilities and key rotation policies; compliance frameworks requiring customer-managed encryption cannot be satisfied
   - **Why This Matters**: Regulatory requirements (PCI-DSS, HIPAA, SOC 2) often mandate customer-managed encryption keys for sensitive data at rest

⚠️ **MEDIUM**: IAM database authentication is disabled.
   - **Resource**: `aws_rds_cluster.prod`
   - **Issue**: `enable_iam_database_authentication` is not configured or set to false, forcing password-based authentication only
   - **Impact**: Database credentials must be stored and rotated manually; credential exposure increases with multiple applications requiring direct password access; no native AWS identity federation for database access
   - **Why This Matters**: Password-based authentication creates larger credential surface area and blocks modern identity management practices

### Cost Impact

- **New KMS key creation**: Approximately $1/month for customer-managed key storage
- **Cluster replacement**: Data transfer charges during migration and temporary dual-cluster costs during blue-green transition (if lifecycle rules are implemented)

## Unified Recommendations

Recommendations are prioritized by severity and execution order.

### Priority 1: CRITICAL – Prevent Destructive Replacement

**Recommendation 1.1**: Implement lifecycle protection to preserve the existing RDS cluster.

**Action**: Add lifecycle rule to the `aws_rds_cluster.prod` resource:
```hcl
resource "aws_rds_cluster" "prod" {
  # ... existing configuration ...
  
  lifecycle {
    create_before_destroy = true
  }
}
```

**Alternative Approach**: Import the existing subnet group into Terraform state instead of recreating it:
```bash
terraform import aws_db_subnet_group.prod <existing-subnet-group-name>
```

**Rationale**: Prevents cluster destruction while maintaining infrastructure-as-code parity. `create_before_destroy` ensures a new cluster is ready before the old one terminates, minimizing downtime.

**Execution Owner**: Infrastructure team (Terraform)  
**Timeline**: Must be implemented before plan application  
**Validation**: Run `terraform plan` to confirm resource is marked for update, not replacement

### Priority 2: HIGH – Enable Customer-Managed Encryption

**Recommendation 2.1**: Provision a customer-managed KMS key and configure RDS to use it.

**Action**: Add KMS key resource and update RDS cluster configuration:
```hcl
resource "aws_kms_key" "rds" {
  description             = "Customer-managed key for RDS cluster encryption"
  deletion_window_in_days = 30
  enable_key_rotation     = true

  tags = {
    Name        = "rds-prod-key"
    Environment = "production"
  }
}

resource "aws_kms_alias" "rds" {
  name          = "alias/rds-prod"
  target_key_id = aws_kms_key.rds.key_id
}

resource "aws_rds_cluster" "prod" {
  # ... existing configuration ...
  
  storage_encrypted = true
  kms_key_id        = aws_kms_key.rds.arn
}
```

**Rationale**: Enables key rotation, audit logging, and granular access control. Customer-managed keys satisfy compliance requirements and provide visibility into encryption operations.

**Execution Owner**: Security team + Infrastructure team  
**Timeline**: Coordinate with Priority 1; can be deployed concurrently  
**Validation**: Verify `aws rds describe-db-clusters` shows the custom KMS key ARN; confirm CloudTrail logs KMS operations

---

### Priority 3: MEDIUM – Enable IAM Database Authentication

**Recommendation 3.1**: Enable IAM-based authentication for the RDS cluster.

**Action**: Update RDS cluster configuration:
```hcl
resource "aws_rds_cluster" "prod" {
  # ... existing configuration ...
  
  enable_iam_database_authentication = true
}
```

**Additional Step**: Create IAM policy for applications requiring database access:
```hcl
resource "aws_iam_policy" "rds_iam_auth" {
  name        = "rds-iam-authentication"
  description = "Allow IAM database authentication to RDS cluster"

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect = "Allow"
        Action = [
          "rds-db:connect"
        ]
        Resource = [
          "arn:aws:rds:${data.aws_region.current.name}:${data.aws_caller_identity.current.account_id}:dbuser:*/iamuser"
        ]
      }
    ]
  })
}
```

**Rationale**: Eliminates static password storage in application configuration; integrates with AWS identity ecosystem; enables audit trails via CloudTrail for database access.

**Execution Owner**: Application team + Database team  
**Timeline**: Deploy after Priority 1 and 2 are validated  
**Validation**: Test connection using `aws rds generate-db-auth-token`; verify applications can authenticate via IAM role
