## Findings by Domain

## Container Security (Kubernetes) Findings

Risk Level: **HIGH**

The `api-server` workload has solid container hardening: it runs as non-root, uses a read-only root filesystem, drops capabilities, and sets bounded resources. The gaps are in namespace-level network isolation, RBAC scoping, token handling, syscall filtering, and image pinning.

### RBAC Issues

| Resource | Role Binding | Severity | Fix Needed |
|---|---|---|---|
| `api-server-role` (Role, `secure-app`) | `api-server` ServiceAccount | **MEDIUM** | Remove the `list` verb on the `configmaps` rule |

- **Issue:** The `configmaps` rule grants `list` with `resourceNames`. Kubernetes does not reliably restrict `list` requests by `resourceNames`, so the rule can expose every ConfigMap in the namespace, not only `api-config`.
- **Why it matters:** A compromised api-server process could enumerate and read unrelated ConfigMaps, which often contain connection strings, feature flags, or internal endpoints.
- **Fix:** Restrict the rule to `get` on the named resource only:
  ```yaml
  rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    resourceNames: ["api-config"]
    verbs: ["get"]
  ```
  Confirm the application does not call `list` or `watch` on ConfigMaps before deploying. If it does, move that access to a dedicated Role with a documented justification.

### Network Policies

| Namespace | Policy | Gap | Severity | Impact |
|---|---|---|---|---|
| `secure-app` | *(none)* | No default-deny NetworkPolicy | **HIGH** | Pods without `app: api-server` accept and send traffic unrestricted |
| `secure-app` | `api-server-policy` | DNS egress allows only UDP 53 | **LOW** | TCP DNS fallback for large responses is blocked, causing intermittent resolution failures |

- **Default-deny gap:** Pods outside the `app: api-server` selector have no isolation, so lateral movement within the namespace and to the cluster is unrestricted. The `api-server-policy` only governs the pods it selects.
- **DNS gap:** The current egress rule permits only UDP 53. Responses larger than 512 bytes (common with DNSSEC or large record sets) are retried over TCP, which this policy blocks.
- **Fix:** See Unified Recommendations, items 1 and 2. The generated manifests (`default-deny-all` and `allow-dns-egress`) address both gaps, but they must be validated before rollout (see the Verdict section).

### Pod Security

| Issue Type | Affected Resource | Severity | Gap |
|---|---|---|---|
| Token auto-mount | ServiceAccount `api-server` | **MEDIUM** | `automountServiceAccountToken` is not set to `false` |
| Syscall filtering | Deployment `api-server` | **MEDIUM** | `seccompProfile` (RuntimeDefault) is omitted, so no syscall filter applies |
| Image integrity | Deployment `api-server` | **LOW** | Image `api-server:v1.2.3` is referenced by mutable tag, not digest |

- **Token auto-mount:** The API token is mounted into `api-server` pods even though they need only the narrow permissions in `api-server-role`. A compromised pod could use the token to call the Kubernetes API.
- **Seccomp:** Without a RuntimeDefault profile, the container can invoke any syscall the kernel allows, which widens the kernel attack surface.
- **Mutable tag:** A tag such as `v1.2.3` can be repointed to a different image, so the deployed code may not match what was reviewed.
