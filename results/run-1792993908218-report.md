# Infrastructure Security Review: Container Security (Kubernetes)

## Executive Summary

This review covers the Kubernetes manifests for the `secure-app` namespace, including the `api-server` Deployment, its ServiceAccount, `api-server-policy` NetworkPolicy, and `api-server-role` RBAC Role. The combined risk level is **HIGH**. The `api-server` workload is well hardened: it runs as non-root, uses a read-only root filesystem, drops capabilities, has scoped RBAC, and sets resource limits. The main exposure is at the namespace level. No default-deny NetworkPolicy exists, so pods not selected by `api-server-policy`, including frontend and database pods, allow all ingress and egress. The reviewer returned **ESCALATE** because the generated `default-deny-all` policy would break legitimate traffic if applied alone, including DNS. Segmentation must be rolled out with companion allow rules. Pod-level controls (seccomp, token automount) and two low-severity RBAC grants should be fixed in the same change window.

## Findings by Domain

### Container Security (Kubernetes)

Risk Level: **HIGH**

The `api-server` workload has solid hardening (non-root user, read-only root filesystem, dropped capabilities, scoped RBAC, and resource limits). The namespace lacks a default-deny network policy, and several pod-level controls (seccomp, token automount) are missing.

### RBAC Issues

| Resource | Role | Severity | Finding | Fix Needed |
|---|---|---|---|---|
| `api-server-role` (Role) | `api-server-role` | **LOW** | The `list` verb on `configmaps` is combined with `resourceNames`. `list` requests are not scoped by resource name, so the restriction is ineffective and misleading. | Remove the `list` verb, or replace it with `get`-only access on the named ConfigMaps. |
| `api-server-role` (Role) | `api-server-role` | **LOW** | `get` is granted on the `db-password` Secret. **Why it matters:** Unnecessary read access to secrets through the API expands the blast radius if the pod or its token is compromised. Ineffective restrictions create a false sense of control during audits.

**Why it matters:** Without a seccomp filter, the container can invoke any syscall the kernel permits, which increases kernel attack surface.

### Pod Security

|---|---|---|---|
| Token automount not disabled | `api-server` (Deployment) | **MEDIUM** | `automountServiceAccountToken` is not set to `false`, so the `api-server` token is mounted even though it may not be needed. |

**Why it matters:** A mounted token gives any code running in the pod (including a compromised dependency) a Kubernetes API identity. If the application does not call the API, the token is unnecessary exposure.

### Verdict: ESCALATE

The reviewer escalated the change because the generated `default-deny-all` NetworkPolicy applies to every pod in `secure-app` with no companion allow rules. Frontend and database pods would lose all ingress and egress, including DNS, which would break legitimate traffic. The reviewer also noted that the other six findings (seccomp, token automount on the Deployment and ServiceAccount, the DNS `namespaceSelector: {}` rule, and the `configmaps` list and `db-password` get grants) remain unaddressed. A human owner must approve a staged segmentation rollout before the default-deny policy is applied.

## Unified Recommendations

Recommendations are ordered by priority.

### HIGH

**1. Implement namespace segmentation as a staged rollout (do not apply `default-deny-all` alone)**

Do not apply the generated `default-deny-all` policy by itself. Apply it together with explicit allow rules so DNS and service traffic continue to work.

Step 1: Confirm the workload labels and ports in the manifests (`app: frontend`, `app: database`, and the `api-server` container port). The findings do not specify these values, so verify them against the source manifests before applying.

Step 2: Apply the allow rules and the default-deny policy in the same change:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-api-server
  namespace: secure-app
spec:
  podSelector:
    matchLabels:
      app: api-server
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: <api-server container port from manifest>
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-api-server-to-database
  namespace: secure-app
spec:
  podSelector:
    matchLabels:
      app: api-server
  policyTypes:
  - Egress
  egress:
  - to:
    - podSelector:
        matchLabels:
          app: database
    ports:
    - protocol: TCP
      port: <database port from manifest>
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: secure-app
spec:
  podSelector: {}
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
      podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: secure-app
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
```

Step 3: Validate in a non-production namespace or staging cluster. Confirm frontend-to-API, API-to-database, and DNS resolution all succeed before promoting to production.

Step 4: Confirm that `api-server-policy` covers the `api-server` pods only. If it also restricts egress for those pods, ensure the allow rules above are consistent with it.
