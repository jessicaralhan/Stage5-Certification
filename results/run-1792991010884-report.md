## Executive Summary

This review covered the Kubernetes manifests for the `insecure-app` workload in the `insecure-app` namespace, including the cluster-scoped RBAC objects that grant it privileges. The combined risk level is **CRITICAL**, and the Kubernetes review verdict is **ESCALATE**. The workload grants `app-sa` cluster-wide admin-equivalent access through the `admin-like-role` ClusterRole and the `app-admin-binding` ClusterRoleBinding. Combined with the absence of any NetworkPolicy, weak container and pod security settings, and an automatically mounted service account token, a compromise of this container would give an attacker broad control over the cluster. Immediate actions are to remove the cluster-wide wildcard RBAC after verifying the workload's real permission needs, to add a NetworkPolicy with verified dependencies, and to harden the Deployment. ## Findings by Domain

### Container Security (Kubernetes)

Risk Level: **CRITICAL**

The `insecure-app` workload has critical cluster-wide RBAC over-privilege via wildcard admin-like permissions bound to `app-sa`, combined with no network policies and weak container and pod security settings. The workload is unsuitable for production in its current form.

#### RBAC Issues

❌ **CRITICAL**: Wildcard ClusterRole equivalent to cluster-admin
- **Resource**: ClusterRole `admin-like-role` (cluster-wide)
- **Binding**: ClusterRoleBinding `app-admin-binding`
- **Issue**: Grants wildcard `apiGroups`, `resources`, and `verbs`, which is equivalent to `cluster-admin`.
- **Impact**: Any process running as `app-sa` can read secrets, modify workloads, change RBAC, and act on every namespace.
- **Fix needed**: Delete `app-admin-binding` and `admin-like-role`. Replace them with a namespaced Role and RoleBinding only after confirming the required permissions (see Recommendations).

❌ **CRITICAL**: Service account bound to cluster-wide admin-like privileges
- **Resource**: ServiceAccount `app-sa` (namespace `insecure-app`)
- **Binding**: ClusterRoleBinding `app-admin-binding`
- **Issue**: The ServiceAccount inherits cluster-wide admin-like privileges through the ClusterRoleBinding.
- **Impact**: The workload's identity is effectively a cluster administrator identity.
- **Fix needed**: Remove the ClusterRoleBinding. Grant only the namespaced permissions the application requires.

#### Network Policies

⚠️ **HIGH**: No NetworkPolicy in the `insecure-app` namespace
- **Namespace**: `insecure-app`
- **Policy gap**: No ingress or egress policy selects the `insecure-app` pods, so all traffic is allowed by default.
- **Impact**: Any pod in the cluster can reach `insecure-app`, and the workload can reach any destination, including the Kubernetes API, other namespaces, and external endpoints. This enables lateral movement, data exfiltration, and abuse of the over-privileged token.
- **Fix needed**: Add a NetworkPolicy that restricts ingress and egress to verified sources and destinations. The proposed policy is not safe as written (see Recommendations).

#### Security Contexts

⚠️ **HIGH**: No securityContext and no `runAsNonRoot`
- **Resource**: Deployment `insecure-app`, container `app`
- **Missing settings**: `securityContext`, `runAsNonRoot`
- **Impact**: The container may run as root, which increases the impact of any container escape or application exploit.

🟡 **MEDIUM**: Writable root filesystem
- **Resource**: Deployment `insecure-app`, container `app`
- **Missing settings**: `readOnlyRootFilesystem: true`
- **Impact**: An attacker can modify binaries and configuration inside the container.

🟡 **MEDIUM**: Privilege escalation not disabled
- **Resource**: Deployment `insecure-app`, container `app`
- **Missing settings**: `allowPrivilegeEscalation: false`
- **Impact**: Processes can gain additional privileges, such as through setuid binaries.

🟡 **MEDIUM**: Mutable image tag with Always pull policy
- **Resource**: Deployment `insecure-app`, container `app`
- **Configuration**: image `app:latest`, `imagePullPolicy: Always`
- **Impact**: Deployed code is not pinned or reproducible, and any change to the tag alters production without a review.

#### Resource Limits

🟡 **MEDIUM**: No CPU or memory limits
- **Resource**: Deployment `insecure-app`, container `app`
- **Missing settings**: `resources.limits.cpu`, `resources.limits.memory` (requests are set)
- **Impact**: A runaway process or resource-exhaustion attack can consume node capacity and affect co-located workloads.

#### Pod Security

⚠️ **HIGH**: Service account token automatically mounted
- **Resource**: Deployment `insecure-app`, pod template
- **Missing settings**: `automountServiceAccountToken: false`
- **Impact**: The `app-sa` token, which has admin-equivalent privileges, is available to any process in the container. This turns any application compromise into a cluster compromise.

🟡 **MEDIUM**: No pod-level securityContext
- **Resource**: Deployment `insecure-app`, pod template
- **Missing settings**: pod-level `securityContext` with `seccompProfile` and `runAsNonRoot`
- **Impact**: Seccomp filtering and non-root enforcement are not applied at the pod level.

🟡 **MEDIUM**: Linux capabilities not dropped
- **Resource**: Deployment `insecure-app`, container `app`
- **Missing settings**: `capabilities.drop: [ALL]`
- **Impact**: The container inherits the default capability set, which is broader than most application workloads need.

### Verdict: ESCALATE

The reviewer determined that the proposed fixes are incomplete and risky for a production environment:

- The ClusterRole `admin-like-role` and ClusterRoleBinding `app-admin-binding` are not actually deleted by the proposed changes. The binding deletion appears only as a comment.
- The replacement Role grants `get`, `list`, and `watch` on `configmaps` only. Its adequacy for `app-sa`'s real needs is unverified.
- The proposed NetworkPolicy's egress allows only DNS. This blocks database, API, and external calls. It also assumes the pod label `app: insecure-app` and port `8080`, which have not been verified.
- Most Deployment findings (securityContext, `automountServiceAccountToken`, resource limits, image pinning, capabilities) have no concrete fix.

A human owner must decide the production approach before any change is applied.
