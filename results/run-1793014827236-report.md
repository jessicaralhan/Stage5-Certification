## Container Security (Kubernetes) Findings

**Risk Level:** 🔴 **CRITICAL**

Production deployment exhibits critical RBAC misconfiguration (wildcard admin role binding), combined with missing security contexts, resource limits, and network policies, creating severe privilege escalation and resource abuse risks.

### RBAC Issues

**Severity: 🔴 CRITICAL**

- **Resource:** `ClusterRole` named `admin-like-role` (cluster-wide scope)
  - **Issue:** Grants wildcard permissions on all API groups, resources, and verbs (`*`), allowing any bound ServiceAccount unrestricted cluster-wide access.
  - **Impact:** ServiceAccounts bound to this role can read secrets, modify deployments, access all namespaces, and escalate privileges across the entire cluster.
  - **Immediate Risk:** Lateral movement, data exfiltration, and complete cluster compromise if the `insecure-app` ServiceAccount is compromised.

- **Resource:** `ClusterRoleBinding` named `app-admin-binding` (cluster-wide scope)
  - **Issue:** Binds `app-sa` ServiceAccount (in `insecure-app` namespace) to `admin-like-role`, granting cluster-wide admin privileges to an application ServiceAccount.
  - **Impact:** The application container runs with cluster-admin equivalent permissions. Any vulnerability in the application code, container image, or runtime can be exploited to gain full cluster control.
  - **Root Cause:** Violates principle of least privilege; applications should only access resources they require.

### Security Contexts

**Severity: 🔴 HIGH**

- **Resource:** `Deployment` named `insecure-app` (namespace: `insecure-app`), Container: `app`
  - **Issue:** Container lacks `securityContext` definition; will run as root with default capabilities and writable filesystem.
  - **Impact:** Attacker with container access gains root privileges by default. Can install malware, modify application binaries, and access host kernel interfaces.
  - **Additional Risk:** No `runAsNonRoot` enforcement; container explicitly allows root execution.
  - **Recommendation:** Add container-level `securityContext` with `runAsNonRoot: true`, `runAsUser: <non-zero-uid>`, and `allowPrivilegeEscalation: false`.

- **Resource:** `Deployment` named `insecure-app` (namespace: `insecure-app`), Container: `app`
  - **Issue:** Container missing `readOnlyRootFilesystem: true`; permits write access to root filesystem.
  - **Impact:** Attacker can modify application files, inject backdoors, or overwrite critical binaries. Filesystem tampering is difficult to detect.
  - **Recommendation:** Set `readOnlyRootFilesystem: true`. Use `emptyDir` volumes for temporary storage if required.

- **Resource:** `Deployment` named `insecure-app` (namespace: `insecure-app`), Pod spec
  - **Issue:** Pod-level `securityContext` is absent, leaving all containers without pod-level security defaults.
  - **Impact:** Cannot enforce pod-wide policies (e.g., `fsGroup` for volume permissions, `seLinuxOptions`, `seccompProfile`).
  - **Recommendation:** Add pod-level `securityContext` with `runAsNonRoot: true`, `runAsUser: <uid>`, `fsGroup: <gid>`, and `seccompProfile.type: RuntimeDefault`.

### Resource Limits

**Severity: 🔴 HIGH**

- **Resource:** `Deployment` named `insecure-app` (namespace: `insecure-app`), Container: `app`
  - **Issue:** Container has no memory or CPU limits defined; allows unbounded resource consumption.
  - **Impact:** A single container can exhaust cluster resources, causing denial of service (DoS) to other workloads. No automatic throttling or eviction occurs.
  - **Cluster Impact:** Memory leaks or fork bombs in `insecure-app` can crash the entire node or cluster.
  - **Recommendation:** Define `resources.limits` (e.g., `memory: 512Mi`, `cpu: 500m`) and `resources.requests` (e.g., `memory: 256Mi`, `cpu: 250m`) based on application profiling.

### Network Policies

**Severity: 🔴 HIGH**

- **Resource:** Namespace `insecure-app`
  - **Issue:** No `NetworkPolicy` exists in the namespace; all ingress and egress traffic is unrestricted by default.
  - **Impact:** The `insecure-app` container can send traffic to any pod, service, or external endpoint. Compromised containers can exfiltrate data, communicate with C2 servers, or attack other services.
  - **Lateral Movement Risk:** Without network segmentation, a compromised application can pivot to databases, caches, and internal APIs in other namespaces.
  - **Recommendation:** Deploy a default-deny ingress `NetworkPolicy` and explicitly allow only required traffic:
    - Ingress: Allow traffic only from known frontend/ingress controller pods (selector: `app: frontend`), on port 8080.
    - Egress: Allow traffic to DNS (UDP port 53), external APIs if required, and internal services only as needed. Deny all other egress by default.

### Pod Security Policy & Image Configuration

**Severity: 🟡 MEDIUM**

- **Resource:** `Deployment` named `insecure-app` (namespace: `insecure-app`), Container: `app`
  - **Issue:** Container image `app:latest` uses mutable `latest` tag with `imagePullPolicy: Always` (default).
  - **Impact:** Image contents can change unexpectedly between pod restarts or node reschedules. Malicious or vulnerable code changes are not auditable and may be deployed silently.
  - **Recommendation:** Use immutable image tags (e.g., `app:v1.2.3` or `app:sha256:abc123...`). Set `imagePullPolicy: IfNotPresent` or `Never` to prevent unexpected updates. Implement image scanning and approval workflows.

## Unified Recommendations

### Priority: 🔴 CRITICAL — RBAC Misconfiguration

**Action 1: Revoke Wildcard RBAC Binding**
- **Step 1:** Delete the `ClusterRoleBinding` named `app-admin-binding` immediately.
  ```bash
  kubectl delete clusterrolebinding app-admin-binding
  ```
- **Step 2:** Delete or re-purpose the `ClusterRole` named `admin-like-role` if no other legitimate use exists.
  ```bash
  kubectl delete clusterrole admin-like-role
  ```
- **Step 3:** Create a namespace-scoped `Role` with minimal permissions required by the application (e.g., read ConfigMaps, get Pods). Example:
  ```yaml
  apiVersion: rbac.authorization.k8s.io/v1
  kind: Role
  metadata:
    name: app-minimal-role
    namespace: insecure-app
  rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["get", "list"]
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get"]
  ```
- **Step 4:** Bind the new `Role` to `app-sa` using a namespace-scoped `RoleBinding`:
  ```yaml
  apiVersion: rbac.authorization.k8s.io/v1
  kind: RoleBinding
  metadata:
    name: app-minimal-binding
    namespace: insecure-app
  roleRef:
    apiGroup: rbac.authorization.k8s.io
    kind: Role
    name: app-minimal-role
  subjects:
  - kind: ServiceAccount
    name: app-sa
    namespace: insecure-app
  ```
- **Validation:** Verify removal by running `kubectl auth can-i --list --as=system:serviceaccount:insecure-app:app-sa` and confirm only required permissions remain.

### Priority: 🔴 CRITICAL — Security Context Hardening

**Action 2: Add Container Security Context**
- Modify the `Deployment` named `insecure-app` to include pod-level and container-level `securityContext`:
  ```yaml
  apiVersion: apps/v1
  kind: Deployment
  metadata:
    name: insecure-app
    namespace: insecure-app
  spec:
    template:
      spec:
        securityContext:
          runAsNonRoot: true
          runAsUser: 1000
          runAsGroup: 3000
          fsGroup: 2000
          seccompProfile:
            type: RuntimeDefault
        containers:
        - name: app
          image: app:v1.2.3  # Use pinned tag instead of 'latest'
          imagePullPolicy: IfNotPresent
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            runAsNonRoot: true
            runAsUser: 1000
            capabilities:
              drop:
              - ALL
          resources:
            limits:
              memory: 512Mi
              cpu: 500m
            requests:
              memory: 256Mi
              cpu: 250m
          volumeMounts:
          - name: tmp
            mountPath: /tmp
          - name: var-run
            mountPath: /var/run
        volumes:
        - name: tmp
          emptyDir: {}
        - name: var-run
          emptyDir: {}
  ```
- **Rationale:** `runAsNonRoot: true` prevents root execution; `readOnlyRootFilesystem: true` prevents filesystem tampering; `capabilities: drop: ALL` removes dangerous kernel capabilities; `emptyDir` volumes provide writable storage for temporary files without modifying the container root filesystem.

### Priority: 🔴 CRITICAL — Network Policy

**Action 3: Deploy Network Policies**
- Create a default-deny ingress policy and explicit allow rules:
  ```yaml
  apiVersion: networking.k8s.io/v1
  kind: NetworkPolicy
  metadata:
    name: insecure-app-default-deny
    namespace: insecure-app
  spec:
    podSelector: {}
    policyTypes:
    - Ingress
    - Egress
  ---
  apiVersion: networking.k8s.io/v1
  kind: NetworkPolicy
  metadata:
    name: insecure-app-allow-ingress
    namespace: insecure-app
  spec:
    podSelector:
      matchLabels:
        app: insecure-app
    policyTypes:
    - Ingress
    ingress:
    - from:
      - podSelector:
          matchLabels:
            app: frontend
      ports:
      - protocol: TCP
        port: 8080
  ---
  apiVersion: networking.k8s.io/v1
  kind: NetworkPolicy
  metadata:
    name: insecure-app-allow-egress
    namespace: insecure-app
  spec:
    podSelector:
      matchLabels:
        app: insecure-app
    policyTypes:
    - Egress
    egress:
    - to:
      - namespaceSelector: {}
      ports:
      - protocol: UDP
        port: 53  # DNS
    - to:
      - podSelector:
          matchLabels:
            app: database
      ports:
      - protocol: TCP
        port: 5432  # PostgreSQL (example)
  ```
- **Validation:** Test connectivity restrictions using `kubectl exec` and `curl` or `nc` from the pod.
