# Infrastructure Security Review: Container Security (Kubernetes)

## Executive Summary

The Kubernetes Security Review covered the `api-server` workload and its supporting resources in the `secure-app` namespace. The `api-server` Deployment has a solid container hardening baseline: it runs as non-root, uses a read-only root filesystem, drops all capabilities, and sets resource limits. The namespace-level controls are weaker. There is no default-deny NetworkPolicy, so database and frontend pods send and receive unrestricted traffic. API token automounting and seccomp profiles are also unconfigured. The proposed default-deny fix was rejected by the reviewer because applying it as written would block DNS and application traffic in production. The default-deny policy must be paired with explicit allow policies before rollout. Immediate actions are to map the required traffic flows, deploy the DNS and application allow policies, then enforce default-deny, and to disable or justify API token automounting and add seccomp `RuntimeDefault`.

## Container Security (Kubernetes) Findings

Risk Level: **HIGH**

The `api-server` workload has a solid container hardening baseline (non-root, read-only root filesystem, all capabilities dropped, resource limits). The namespace lacks a default-deny network policy, and API token automounting and seccomp profiles are not configured.

### RBAC Issues

- **`api-server-role` (Role) in `secure-app`: `list` verb on `configmaps` with `resourceNames`**
  - **Severity:** LOW
  - **Issue:** Kubernetes cannot restrict `list` requests by `resourceName`. The rule therefore grants the ability to list all ConfigMaps in `secure-app`, not only the named ones.
  - **Why it matters:** The intended least-privilege restriction does not hold. Any token bound to this Role can read every ConfigMap in the namespace, which may contain configuration or secrets-adjacent data.
  - **Fix needed:** Remove `list` from the rule. Keep `get` with the explicit `resourceNames`. If the application needs to enumerate ConfigMaps, grant `list` in a separate Role without `resourceNames`, and accept that it covers the whole namespace.

- **`api-server` (ServiceAccount) in `secure-app`: token automounting not disabled**
  - **Severity:** MEDIUM
  - **Issue:** `automountServiceAccountToken` is not set to `false`, so a Kubernetes API token is mounted into pods that use this ServiceAccount.
  - **Why it matters:** A compromised container can use the mounted token to call the Kubernetes API with whatever permissions `api-server-role` grants.
  - **Fix needed:** Set `automountServiceAccountToken: false` on the ServiceAccount if `api-server` does not call the Kubernetes API. Note that `api-server-role` grants ConfigMap access, which suggests the application does call the API. In that case, keep the token mounted, confirm the required API calls, and narrow the Role as described above.

### Network Policies

- **Namespace `secure-app`: no default-deny policy**
  - **Severity:** HIGH
  - **Issue:** No NetworkPolicy selects all pods in `secure-app`. Pods without the `app=api-server` label, including database and frontend pods, accept and send unrestricted traffic.
  - **Why it matters:** A compromised frontend or database pod can reach any pod in the namespace and any destination outside it. Lateral movement is unrestricted.
  - **Fix needed:** Deploy allow policies for all required flows first, then add a default-deny policy. The default-deny policy must not be applied alone (see Unified Recommendations).

- **`api-server-policy` (NetworkPolicy) in `secure-app`: DNS egress rule uses `namespaceSelector: {}`**
  - **Severity:** LOW
  - **Issue:** The DNS egress rule selects `k8s-app: kube-dns` pods in any namespace, not only `kube-system`.
  - **Why it matters:** An attacker-controlled pod in another namespace labeled `k8s-app: kube-dns` could receive DNS traffic from `api-server` pods, which could be used for DNS-based data exfiltration or spoofing.
  - **Fix needed:** Restrict the namespace selector to `kubernetes.io/metadata.name: kube-system`.

### Security Contexts

- **Deployment `api-server` in `secure-app`: no seccomp profile**
  - **Severity:** MEDIUM
  - **Missing settings:** `seccompProfile.type: RuntimeDefault` is not set at the pod level or on the `api` container.
  - **Why it matters:** Without a seccomp profile, the container has no syscall filter, which increases the kernel attack surface available to an attacker who achieves code execution.
  - **Fix needed:** Add `securityContext.seccompProfile.type: RuntimeDefault` at the pod level in the Deployment template.

### Resource Limits

No issues found. The `api-server` container has resource limits configured.

### Pod Security

- **Deployment `api-server` in `secure-app`: API token auto-mounted into the `api` container**
  - **Severity:** MEDIUM
  - **Issue:** The pod template does not set `automountServiceAccountToken: false`, so the API token is mounted into the `api` container.
  - **Why it matters:** The same exposure as the ServiceAccount finding applies at the pod level. Pod-level settings take effect even if the ServiceAccount is configured differently.
  - **Fix needed:** Set `automountServiceAccountToken: false` in the pod spec if the application does not need API access. If it does, document the required API calls and keep the token mounted with the narrowed Role.

### Verdict: ESCALATE

The reviewer rejected the proposed `default-deny-all` NetworkPolicy. The policy selects every pod in `secure-app` and sets both Ingress and Egress with no allow rules. Applied as written, it would remove DNS resolution and application traffic for frontend and database pods, which currently have no policy and function today. No companion allow policies were proposed to restore those flows. Because this change would affect a production namespace, a human must confirm the required traffic flows before any network policy is applied.

## Unified Recommendations

### HIGH

1. **Map required traffic flows in `secure-app` before applying any default-deny policy.**
   - Identify every pod label set in the namespace (`api-server`, frontend, database, and any others).
   - For each pod group, list required ingress sources, egress destinations, and ports. Confirm these with the application owners.
   - Verify that the `api-server` Service port and the frontend-to-api-server and api-server-to-database paths match the policy rules.

2. **Deploy DNS egress allow policy for all pods in `secure-app` before default-deny.**
   Without this, default-deny blocks name resolution for every pod. Example:

   ```yaml
   apiVersion: networking.k8s.io/v1
   kind: NetworkPolicy
   metadata:
     name: allow-dns-egress
     namespace: secure-app
   spec:
     podSelector: {}
     policyTypes: [Egress]
     egress:
       - to:
           - namespaceSelector:
               matchLabels:
                 kubernetes.io/
