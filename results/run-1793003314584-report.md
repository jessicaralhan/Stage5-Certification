## Container Security (Kubernetes) Findings

**Risk Level: HIGH**

The manifests demonstrate strong baseline security hygiene with non-root execution, read-only filesystems, resource limits, and capability dropping, but contain three notable issues: overly permissive egress in NetworkPolicy allowing cross-namespace traffic, missing seccomp profiles, and imagePullPolicy set to Always in production.

### Network Policies

❌ **HIGH**: Overly permissive NetworkPolicy egress rule
   - **Resource**: `api-server-policy` (namespace: `secure-app`, kind: NetworkPolicy)
   - **Issue**: Egress rule allows all traffic to any namespace via empty `namespaceSelector`, creating an overly permissive egress path beyond the intended database and DNS destinations
   - **Impact**: Enables lateral movement and potential data exfiltration across namespace boundaries; violates principle of least privilege for egress filtering
   - **Recommendation**: Restrict egress to explicit destinations: database pods (PostgreSQL on port 5432 in `secure-app` namespace), DNS servers (UDP port 53 to any namespace), and HTTPS services (TCP port 443 to specific pods only). The proposed remediation allows unrestricted egress to port 443 on any pod within the cluster—this requires validation that legitimate HTTPS destinations are scoped correctly and that no unintended internal services are exposed.

### Security Contexts

⚠️ **MEDIUM**: Missing seccomp profile configuration
   - **Resource**: `api-server` (namespace: `secure-app`, kind: Deployment)
   - **Issue**: Container lacks `seccomp` profile configuration, leaving syscall filtering to cluster defaults and missing defense-in-depth protection against kernel-level attacks
   - **Impact**: Increases attack surface by allowing unrestricted syscalls; no mitigation against container escape exploits at the kernel level
   - **Recommendation**: Add `securityContext.seccomp.type: RuntimeDefault` to the deployment spec. The remediation YAML includes this; ensure your cluster has RuntimeDefault profiles enabled or explicitly define a custom seccomp profile that restricts dangerous syscalls (`execve`, `ptrace`, `clone` with CLONE_NEWUSER, etc.).

### Pod Security

⚠️ **MEDIUM**: Insecure image pull policy
   - **Resource**: `api-server` (namespace: `secure-app`, kind: Deployment)
   - **Issue**: Deployment uses `imagePullPolicy: Always`, forcing image re-pull on every pod restart, increasing attack surface and deployment latency
   - **Impact**: Each pod restart re-fetches the image from the registry, multiplying exposure to registry-level compromise, network interception, or image tampering; increases pod startup time and API latency
   - **Recommendation**: Change `imagePullPolicy` to `IfNotPresent` and pin the container image to a specific digest (e.g., `myregistry.azurecr.io/api-server@sha256:abc123def456`). The remediation YAML includes both changes; ensure the digest matches your image scanning and signing pipeline.

### RBAC Issues

⚠️ **MEDIUM**: Overly broad secret access with insufficient granularity
   - **Resource**: `api-server-role` (namespace: `secure-app`, kind: Role)
   - **Issue**: Role grants `get` access to the `db-password` secret with only `resourceNames` restriction, but lacks granular audit logging configuration and does not enforce least privilege at the verb level; proposed fix silently introduces `list` permission on `configmaps` not mentioned in original findings
   - **Impact**: Allows the service account to retrieve sensitive database credentials; the `list` permission grants enumeration rights beyond the original scope
   - **Recommendation**: Keep the role scoped to `get` on the specific `db-password` secret only. If configmap access is required, explicitly document the business justification and add it as a separate rule with only necessary verbs (`get` or `list`, not both unless required). The remediation YAML adds configmap permissions—verify these are intentional with the service owner before applying. Enable audit logging on secret access by configuring `audit.k8s.io/level: RequestResponse` in the audit policy for the `secrets` resource.
