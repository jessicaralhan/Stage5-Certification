## Access Control (IAM) Findings

Risk Level: **CRITICAL**

The production policy grants unrestricted administrative access to all actions and resources with no MFA, conditions, or session limits, which is a critical least-privilege failure.

### Overly Broad Permissions

❌ **CRITICAL**: Statement `AllowEverything` grants every API action on every resource.
- **Principal**: Not identified in the policy document. The principal bound to this statement must be determined before any change.
- **Current Scope**: `Action: "*"`, `Resource: "*"`
- **Impact**: Permits all AWS API actions, including IAM privilege escalation, data deletion, encryption key operations, and network changes.
- **Least-Privilege Target**: Replace `"Action": "*"` with the minimum set required by the workload:
  `s3:GetObject`, `s3:PutObject`, `s3:ListBucket`, `dynamodb:GetItem`, `dynamodb:PutItem`, `dynamodb:Query`, `kms:Decrypt`, `kms:GenerateDataKey`, `logs:CreateLogStream`, `logs:PutLogEvents`
- **Reviewer Caveat**: This action set has not been validated against the actual workload. Missing actions will cause production failures, and it omits any delete or update operations the application may require.

⚠️ **LOW**: Principal ownership is undocumented, so the policy's usage cannot be verified.
- **Policy**: `AllowEverything`
- **Issue**: The document does not identify any role or user it is bound to.
- **Impact**: The business need for this access cannot be confirmed. The policy may be unused, which would make removal the safest option.
- **Recommendation**: Confirm the attached principal through IAM attachment records (for example, `aws iam list-entities-for-policy`) and either document its owner or remove the attachment.

### Missing Resource Boundaries

❌ **CRITICAL**: Statement `AllowEverything` applies to every resource in the production account.
- **Affected Resources**: All resources, including data stores, KMS keys, security groups, and IAM entities
- **Impact**: A compromised credential can read, modify, or destroy any production resource.
- **Recommended Scoping**: Replace `"Resource": "*"` with the named resources the application uses:
  - `arn:aws:s3:::prod-app-data` and `arn:aws:s3:::prod-app-data/*`
  - `arn:aws:dynamodb:us-east-1:111122223333:table/prod-app-orders`
  - `arn:aws:kms:us-east-1:111122223333:key/1234abcd-12ab-34cd-56ef-1234567890ab`
  - `arn:aws:logs:us-east-1:111122223333:log-group:/prod/app:*`
- **Reviewer Caveat**: The scoped list is incomplete. `dynamodb:Query` requires index ARNs (for example, `.../table/prod-app-orders/index/*`), and `logs:PutLogEvents` requires log-stream ARNs (for example, `.../log-group:/prod/app:log-stream:*`). Without these, the scoped policy will fail for the application.

### Missing MFA/Conditions

❌ **CRITICAL**: No MFA requirement on `AllowEverything`.
- **Principal**: Unidentified principal bound to `AllowEverything`
- **Gap**: Create, modify, and delete actions, including all `iam:*` actions, succeed without MFA.
- **Impact**: A stolen access key or session token can alter IAM and destroy production resources with no second factor.
- **Proposed Fix**: Add `aws:MultiFactorAuthPresent: true` and `aws:MultiFactorAuthAge < 3600` to the human-facing scoped statement, with service or workload roles kept in a separate statement without this condition.
- **Reviewer Caveat**: The separate workload statement is not defined in the proposal. As written, the MFA condition would block automated workloads. Do not apply this condition until that statement exists and has been tested.

⚠️ **HIGH**: No origin or context conditions on `AllowEverything`.
- **Principal**: Unidentified principal bound to `AllowEverything`
- **Gap**: No IP range, time-of-day, source VPC or VPC endpoint, or principal-tag conditions.
- **Impact**: Credentials can be used from any network location at any time.
- **Recommendation**: Add `aws:SourceVpce` or `aws:SourceIp` conditions matching the application's network path, and evaluate time-of-day restrictions for human access. This was not addressed in the proposed fix.

### Session Credential Issues

⚠️ **MEDIUM**: No session constraints on `AllowEverything`.
- **Policy**: `AllowEverything`
- **Gap**: No `aws:MultiFactorAuthAge` bound and no bounded role session duration.
- **Impact**: Credentials issued under this policy may remain valid for the maximum session duration, extending exposure after a compromise.
- **Recommendation**: Set `MaxSessionDuration` on the attached role to the shortest value the workload tolerates (for example, 3600 seconds for human roles). Session constraints were not addressed in the proposed fix and should be added as a separate change.

### Privilege Escalation Risks

❌ **CRITICAL**: `Action: "*"` permits IAM privilege escalation.
- **Path**: Any principal bound to `AllowEverything` can call `iam:*` actions, including creating or attaching policies, creating access keys, and modifying trust policies. This allows the principal to grant itself or others any permission in the account. The analyzer identified this capability but did not enumerate a specific sequence of calls.
- **Mitigation**: Removing `"Action": "*"` (as proposed) denies `iam:*` by default. For defense in depth, add an explicit Deny on `iam:CreatePolicyVersion`, `iam:AttachRolePolicy`, `iam:PutRolePolicy`, `iam:UpdateAssumeRolePolicy`, `iam:CreateAccessKey`, and `iam:PassRole` for all principals except a designated administrative role, and enable IAM Access Analyzer to detect any remaining escalation paths.

### Verdict: ESCALATE

The affected principal is unidentified, so the blast radius of narrowing `AllowEverything` in production cannot be verified. The MFA condition on the scoped statement would block automated workloads unless a separate workload statement exists, and that statement is not defined. The proposed action set leaves session TTL, IP and time conditions, and the unused-role finding unaddressed. The scoped actions also lack required resource ARNs, such as DynamoDB index ARNs and CloudWatch Logs log-stream ARNs. A human owner must confirm the principal, its service dependencies, and the rollout plan before any change is applied.
