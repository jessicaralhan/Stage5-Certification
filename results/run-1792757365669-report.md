## Container Security (Kubernetes) Findings

Risk Level: **CRITICAL**

The `insecure-app` workload has critical cluster-wide RBAC over-privilege. The wildcard ClusterRole `admin-like-role` is bound to ServiceAccount `app-sa` through `app-admin-binding`, so a compromise of any pod in `insecure-app` could lead to full cluster takeover. The workload also lacks network policies, a hardened security context, resource limits, and pod-level controls, which leaves the production deployment highly exposed.

### RBAC Issues

❌ **CRITICAL**: ClusterRole `admin-like-role` grants all verbs on all resources in all API groups.
- **Resource**: ClusterRole `admin-like-role` (cluster-wide)
- **Issue**: `apiGroups`, `resources`, and `verbs` are all set to `*`, which is equivalent to `cluster-admin`.
- **Impact**: Any identity bound to this role can read all secrets, modify workloads, and alter RBAC across the cluster.
- **Fix needed**: Delete the ClusterRole. The generated fix creates a namespaced Role but does not remove this ClusterRole, so the over-privilege remains in place.

❌ **CRITICAL**: ClusterRoleBinding `app-admin-binding` grants the wildcard role to `app-sa`.
- **Resource**: ClusterRoleBinding `app-admin-binding` binding `admin-like-role` to ServiceAccount `insecure-app/app-sa`
- **Issue**: Grants cluster-wide full control to the application's identity.
- **Impact**: Cluster-wide access persists for `app-sa` regardless of any namespaced role added alongside it.
- **Fix needed**: Delete the ClusterRoleBinding. Confirm no other subjects depend on it before removal.

❌ **CRITICAL**: ServiceAccount `app-sa` holds cluster-wide wildcard permissions.
- **Resource**: ServiceAccount `app-sa` in namespace `insecure-app`
- **Issue**: Permissions are inherited through `app-admin-binding`, and the token is mounted into the pod by default.
- **Impact**: Compromise of the pod, or any process inside it, yields full cluster control.
- **Fix needed**: Remove the cluster-wide binding, replace it with a least-privilege namespaced Role, and disable token automount where API access is not required.

### Network Policies

❌ **HIGH**: No NetworkPolicy exists in namespace `insecure-app`.
- **Namespace**: `insecure-app`
- **Policy gap**: No ingress or egress restrictions apply to the `insecure-app` pods.
- **Impact**: All east-west and north-south traffic is allowed by default. A compromised pod can reach any service in the cluster and any external endpoint, which enables lateral movement and data exfiltration.
- **Fix needed**: Apply a default-deny policy, then add explicit allow rules for the traffic the application actually requires.

### Security Contexts

❌ **HIGH**: Deployment `insecure-app` container `app` has no `securityContext` and no `runAsNonRoot` setting.
- **Missing settings**: `runAsNonRoot: true`, `runAsUser` (non-zero)
- **Impact**: The container may run as root (UID 0). Combined with other weaknesses, this raises the likelihood and severity of container escape.

❌ **MEDIUM**: Deployment `insecure-app` container `app` does not set `readOnlyRootFilesystem`.
- **Missing settings**: `readOnlyRootFilesystem: true`
- **Impact**: An attacker can write to the container filesystem, for example to persist malware or modify binaries.

❌ **MEDIUM**: Deployment `insecure-app` container `app` does not set `allowPrivilegeEscalation: false`.
- **Missing settings**: `allowPrivilegeEscalation: false`
- **Impact**: Processes can gain more privileges than their parent through setuid binaries.

❌ **MEDIUM**: Deployment `insecure-app` does not set a `seccompProfile`.
- **Missing settings**: `seccompProfile: {type: RuntimeDefault}` at the pod or container level
- **Impact**: Default syscall filtering is not explicitly enforced, so the runtime's behavior depends on node defaults.

### Resource Limits

❌ **HIGH**: Deployment `insecure-app` container `app` has a memory request of 64Mi and no memory limit.
- **Missing limits**: `resources.limits.memory`
- **Impact**: The container can consume unbounded node memory and trigger node-level OOM events that affect other workloads.

❌ **MEDIUM**: Deployment `insecure-app` container `app` has a CPU request of 50m and no CPU limit.
- **Missing limits**: `resources.limits.cpu`
- **Impact**: The container can consume unbounded CPU and starve other workloads on the same node.

### Pod Security

❌ **MEDIUM**: Deployment `insecure-app` container `app` does not drop Linux capabilities.
- **Affected resource**: Deployment `insecure-app`, container `app`
- **Missing settings**: `capabilities: {drop: ["ALL"]}`
- **Impact**: The container runs with the runtime's default capability set, which is broader than most application workloads need.

❌ **MEDIUM**: Pod does not set `automountServiceAccountToken: false`.
- **Affected resource**: Pods of Deployment `insecure-app`, using ServiceAccount `app-sa`
- **Impact**: The cluster-admin-equivalent token for `app-sa` is mounted and readable by any process in the container. This amplifies the RBAC issues above.

❌ **MEDIUM**: Deployment `insecure-app` uses the mutable image tag `app:latest` with `imagePullPolicy: Always`.
- **Affected resource**: Deployment `insecure-app`, container `app`
- **Impact**: Deployments are not reproducible, and an attacker who can replace the image in the registry can tamper with the workload on its next pull.

### Verdict: ESCALATE

The reviewer determined that the generated fixes do not resolve the core risk and that the change requires human sign-off:

- The ClusterRole `admin-like-role` and ClusterRoleBinding `app-admin-binding` are not deleted or patched, so `app-sa` retains cluster-wide wildcard access. The new namespaced Role and RoleBinding are additive only.
- Setting `automountServiceAccountToken: false` on `app-sa` prevents the token from being mounted into the Deployment. This breaks ConfigMap access the application needs, unless the pod spec explicitly overrides the setting.
- The application's actual Kubernetes API requirements are unverified. Because this is a production RBAC change, a human must confirm those requirements before any change is applied.
