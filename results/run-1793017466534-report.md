## Container Security (Kubernetes) Findings

**Risk Level:** 🔴 **HIGH**

The manifests demonstrate strong baseline security posture with pod-level security contexts, resource limits, and RBAC restrictions in place. However, a critical egress policy gap and three medium-severity configuration issues present operational and security risks.

### Network Policies

❌ **HIGH**: NetworkPolicy egress misconfiguration allows unrestricted lateral movement.
   - **Resource:** `api-server-policy` (Namespace: `secure-app`, Kind: `NetworkPolicy`)
   - **Issue:** The egress rule contains an empty `namespaceSelector`, permitting unrestricted access to all namespaces and external destinations.
   - **Impact:** Compromised application containers can communicate laterally with workloads across all namespaces and exfiltrate data to external systems without network-level restrictions.
   - **Recommendation:** Define explicit egress rules with specific `namespaceSelector` and `podSelector` constraints. Restrict egress to required namespaces only (e.g., kube-system for DNS, specific service namespaces for inter-service communication). Deny-all egress by default, then explicitly allow only necessary destinations.

### RBAC Issues

⚠️ **MEDIUM**: Role permissions lack granularity for secrets access.
   - **Resource:** `api-server-role` (Namespace: `secure-app`, Kind: `Role`)
   - **Issue:** Role grants access to the `secrets` resource without specifying `resourceNames`, allowing potential access to any secret in the namespace if RBAC enforcement is bypassed or misconfigured.
   - **Impact:** If RBAC controls are inadvertently weakened or a vulnerability allows unauthorized access, application pods could read unrelated secrets beyond their functional requirements.
   - **Recommendation:** Add explicit `resourceNames` constraints to the Role to limit access only to required secrets (e.g., `["api-server-credentials", "database-password"]`). Follow the principle of least privilege: grant access only to the specific secrets the application needs.

### Security Contexts

⚠️ **MEDIUM**: Syscall filtering not explicitly hardened.
   - **Resource:** `api-server` (Namespace: `secure-app`, Kind: `Deployment`)
   - **Issue:** Container `securityContext` does not explicitly define `seccompProfile`, relying on cluster defaults for syscall filtering.
   - **Impact:** Attack surface is not minimized; if cluster defaults are permissive, a compromised container has access to a broader set of system calls than necessary, increasing exploit opportunities.
   - **Recommendation:** Explicitly set `securityContext.seccompProfile` to `type: RuntimeDefault` (or `type: Localhost` with a hardened profile). For stricter hardening in production, use `type: Localhost` with a custom profile restricting syscalls to essential operations only (e.g., audit, process management, networking).

### Pod Security

⚠️ **MEDIUM**: Image pull policy not optimized for production.
   - **Resource:** `api-server` (Namespace: `secure-app`, Kind: `Deployment`)
   - **Issue:** Container `imagePullPolicy` is set to `Always`, causing every pod restart to pull the image from the registry.
   - **Impact:** Increases pod startup latency, unnecessary registry I/O load, and dependency on registry availability. In production, this introduces potential availability risk and performance degradation.
   - **Recommendation:** Change `imagePullPolicy` to `IfNotPresent` for production deployments. This ensures images are used from the node cache when already present, reducing registry dependency and improving startup performance. Use `Always` only in development or when frequent image updates are required without tag changes.

### Verdict: **ESCALATE**

**Reasoning:** The critical network policy vulnerability enabling unrestricted egress must be remediated immediately before deployment. The HIGH risk level combined with the severity of potential lateral movement and data exfiltration requires human review and approval before proceeding. While medium-severity issues are remediable, the network policy gap represents an unacceptable security posture for production workloads.

## Unified Recommendations

### Priority 1: CRITICAL
1. **Remediate NetworkPolicy `api-server-policy` egress rules**
   - Replace empty `namespaceSelector` with explicit namespace and pod selectors
   - Define allow-list of target namespaces (e.g., `kube-system` for DNS, `secure-app` for intra-service, specific external APIs only)
   - Implement deny-all-egress default with explicit permits
   - Test the policy in a non-production environment before deployment
   - Coordinate with network and application teams to identify all legitimate egress destinations

### Priority 2: HIGH
2. **Add explicit `resourceNames` to Role `api-server-role`**
   - List every secret the application requires by name
   - Example: `resourceNames: ["api-server-tls-cert", "database-credentials"]`
   - Validate with application owners that no additional secrets are needed

### Priority 3: MEDIUM
3. **Add explicit seccompProfile to `api-server` Deployment**
   - Set `securityContext.seccompProfile.type: RuntimeDefault` as baseline
   - Consider custom Localhost profile for hardened environments; audit required syscalls first
   - Test pod startup and application functionality after applying

4. **Update imagePullPolicy in `api-server` Deployment**
   - Change `imagePullPolicy: Always` to `imagePullPolicy: IfNotPresent`
   - Verify all required image tags are immutable (use specific versions, not `latest`)
