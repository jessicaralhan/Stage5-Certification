## Container Security (Kubernetes) Findings

Risk Level: **CRITICAL**

The deployment has critical RBAC exposure from a wildcard ClusterRole bound cluster-wide to the app ServiceAccount, plus missing network isolation, weak container hardening, and unbounded resource consumption, so it is not safe for production as written.

### RBAC Issues

❌ **CRITICAL**: Wildcard ClusterRole grants cluster-admin privileges
- **Resource**: ClusterRole `admin-like-role` (cluster-wide)
- **Issue**: Grants wildcard `apiGroups`, `resources`, and `verbs`, which is equivalent to cluster-admin.
- **Impact**: Any workload bound to this role can read secrets, modify workloads, and alter RBAC across every namespace.
- **Fix needed**: Delete `admin-like-role` once no bindings depend on it. The generated replacement `Role` `app-least-privilege` (namespace `insecure-app`, read-only access to `configmaps` and `pods`) is a starting point, but its permissions must be verified against what `insecure-app` actually calls.

❌ **CRITICAL**: Cluster-wide binding grants app-sa admin-like access
- **Resource**: ClusterRoleBinding `app-admin-binding` → ServiceAccount `app-sa` (namespace `insecure-app`)
- **Issue**: Binds `app-sa` to `admin-like-role` across all namespaces.
- **Impact**: The application identity can act as a cluster administrator. The binding remains active even after the generated RoleBinding `app-sa-least-privilege` is added.
- **Fix needed**: Delete the ClusterRoleBinding `app-admin-binding`. The generated RoleBinding `app-sa-least-privilege` (namespace `insecure-app`, referencing Role `app-least-privilege`) should replace it. If the application needs no Kubernetes API access at all, omit the RoleBinding entirely.

### Network Policies

⚠️ **HIGH**: No NetworkPolicy isolates the insecure-app namespace
- **Namespace**: `insecure-app`
- **Policy gap**: No NetworkPolicy selects the `insecure-app` pods, so all ingress and egress is allowed by default.
- **Impact**: Any pod in the cluster can reach `insecure-app`, and a compromised pod can make arbitrary outbound connections, including to the Kubernetes API, metadata endpoints, and other namespaces.
- **Fix needed**: Apply the generated NetworkPolicy `insecure-app-default-deny`, but only after validating its assumptions. It selects pods labeled `app: insecure-app`, allows ingress from the `ingress-nginx` namespace and pods labeled `app.kubernetes.io/name: ingress-nginx` on TCP 8080, and allows egress only to kube-dns on UDP and TCP 53. The reviewer flagged that this egress rule breaks any other outbound dependency, and that the labels and port 8080 are unverified. Before applying it, confirm the actual pod labels, the ingress controller labels, and every outbound dependency of the application, then add explicit egress rules for each. Rename the policy to reflect that it is an allow-list, not a true default-deny.
