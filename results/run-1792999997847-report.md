## Container Security (Kubernetes) Findings

**Risk Level: HIGH**

The manifest demonstrates strong baseline security controls with proper RBAC scoping, read-only filesystem, and non-root execution, but has overly permissive egress network policy and missing seccomp restrictions for production use.

### Network Policies

❌ **HIGH SEVERITY**: NetworkPolicy allows unrestricted egress to all namespaces.
   - **Resource**: `api-server-policy` (namespace: `secure-app`)
   - **Issue**: Egress rule uses an empty `namespaceSelector`, allowing the `api-server` pod to communicate with any pod in any namespace without restriction.
   - **Impact**: Attackers who compromise the API server container can perform lateral movement across the cluster, exfiltrate data to unauthorized namespaces, or pivot to other workloads.
   - **Why It Matters**: Network policies are a critical defense-in-depth control in Kubernetes. Unrestricted egress violates the principle of least privilege and exposes the cluster to container breakout scenarios.

### Security Context Configuration

⚠️ **MEDIUM SEVERITY**: Container image pull policy allows untrusted or compromised images.
   - **Resource**: `api-server` Deployment, container `api` (namespace: `secure-app`)
   - **Issue**: `imagePullPolicy: Always` pulls the container image on every restart, even if the image tag is mutable (e.g., `latest` or `v1.2`). This can introduce compromised or tampered images between restarts.
   - **Impact**: Vulnerability: if an image tag is reused or the registry is compromised, a restarted pod may pull malicious code without detection.
   - **Why It Matters**: Immutable image digests and `IfNotPresent` policy prevent supply chain attacks and reduce blast radius from registry compromises.

⚠️ **LOW SEVERITY**: Deployment lacks seccomp profile configuration.
   - **Resource**: `api-server` Deployment (namespace: `secure-app`)
   - **Issue**: No `seccompProfile` is defined, allowing all system calls to execute without restriction.
   - **Impact**: A compromised container can invoke dangerous system calls (e.g., `ptrace`, `mount`, raw socket creation) to escalate privileges or exfiltrate kernel state.
   - **Why It Matters**: Seccomp (secure computing mode) is a kernel-level attack surface reducer. `RuntimeDefault` or a custom profile blocks syscalls not needed by the application, improving defense-in-depth.

### RBAC Configuration

⚠️ **MEDIUM SEVERITY**: Role grants overly broad access to ConfigMaps without resourceNames restriction.
   - **Resource**: `api-server-role` Role (namespace: `secure-app`)
   - **Issue**: The role grants the `list` verb on `configmaps` without restricting to specific resource names via `resourceNames`. This allows the pod to enumerate and view metadata about all ConfigMaps in the namespace, potentially exposing sensitive configuration key names or data patterns.
   - **Impact**: An attacker or compromised pod can discover the names and structure of ConfigMap objects, revealing application configuration architecture and possibly sensitive data keys.
   - **Why It Matters**: RBAC should follow least-privilege principles: only `get` access to explicitly named secrets and ConfigMaps is required; `list` access is rarely necessary and introduces reconnaissance attack surfaces.

## Unified Recommendations

### PRIORITY 1 — HIGH SEVERITY

**1. Restrict NetworkPolicy egress to specific namespaces and ports**

Implement the corrected `api-server-policy` NetworkPolicy:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-server-policy
  namespace: secure-app
spec:
  podSelector:
    matchLabels:
      app: api-server
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          name: secure-app
    ports:
    - protocol: TCP
      port: 8080
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          name: secure-app
    ports:
    - protocol: TCP
      port: 5432
  - to:
    - podSelector: {}
      namespaceSelector:
        matchLabels:
          name: kube-system
    ports:
    - protocol: TCP
      port: 53
    - protocol: UDP
      port: 53
```

**Action**: Replace the existing NetworkPolicy with this corrected version. This restricts egress to:
- The `secure-app` namespace on port 5432 (database connectivity)
- The `kube-system` namespace for DNS resolution (ports 53 TCP/UDP)

**Validation**: After deployment, verify DNS resolution works by exec'ing into a pod and running `nslookup kubernetes.default.svc.cluster.local`. Confirm external namespace access is blocked by attempting a connection to a pod in a different namespace.

### PRIORITY 2 — MEDIUM SEVERITY

**2. Update container image pull policy and add seccomp profile**

Apply the corrected security context to the `api-server` Deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-server
  namespace: secure-app
spec:
  template:
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        fsGroup: 2000
        seccompProfile:
          type: RuntimeDefault
      containers:
      - name: api
        image: myregistry/api:v1.2.3
        imagePullPolicy: IfNotPresent
        securityContext:
          allowPrivilegeEscalation: false
          readOnlyRootFilesystem: true
          runAsNonRoot: true
          capabilities:
            drop:
            - ALL
        resources:
          requests:
            cpu: 100m
            memory: 256Mi
          limits:
            cpu: 500m
            memory: 512Mi
```

**Key changes**:
- Change `imagePullPolicy` from `Always` to `IfNotPresent` to avoid re-pulling on restart.
- Add `seccompProfile: type: RuntimeDefault` at pod level to enable kernel syscall filtering.
- Ensure image is tagged with an immutable digest (e.g., `v1.2.3`, not `latest`).

**Action**: Apply this manifest via `kubectl apply -f <file>` or your GitOps workflow. This will trigger a rolling restart of the `api-server` pods.

**Validation**: After rollout completes, verify pod restarts do not pull a new image by checking the image digest in `kubectl describe pod <pod-name>` before and after a pod restart. Confirm that seccomp is active by checking pod events for seccomp-related logs.
