# Infrastructure Security Review: Container Security

**Scope:** Kubernetes manifests for the `secure-app` namespace, including the `api-server` Deployment, ServiceAccount, Role, and NetworkPolicy.
**Triggered Workflows:** Kubernetes Security Review (Container Security)
**Combined Risk Level:** **HIGH**
**Overall Verdict:** **ESCALATE**

The review found seven issues in the `secure-app` namespace: one HIGH, three MEDIUM, and three LOW. The `api-server` workload has strong container hardening (non-root execution, read-only root filesystem, dropped capabilities, and resource limits). However, the namespace has no default-deny network policy, so any pod in `secure-app` can send and receive traffic without restriction. The pod and ServiceAccount also leave API token mounting and seccomp unrestricted. The proposed default-deny fix was escalated because applying it without matching allow rules could break legitimate traffic, including the existing `api-server` paths and kubelet probes. Human review is needed before the fix is applied. The priority actions are to add scoped allow rules alongside a namespace-wide default-deny, then disable API token automounting and set a seccomp profile.

---

## Container Security (Kubernetes) Findings

Risk Level: **HIGH**

The `api-server` workload has solid container hardening (non-root, read-only root filesystem, dropped capabilities, and resource limits), but the namespace lacks a default-deny network policy and the pod and ServiceAccount do not restrict seccomp or API token mounting.

### RBAC Issues

- **Role `api-server-role`** (namespace `secure-app`), **LOW**
  - **Issue:** The `configmaps` rule grants `list` with `resourceNames: ["api-config"]`. RBAC does not enforce `resourceNames` on `list` requests, so the restriction has no effect and the subject can list every ConfigMap in `secure-app`.
  - **Why it matters:** The intended least-privilege boundary does not exist. Any ConfigMap in the namespace, including any that hold credentials or sensitive configuration, is readable by this role.
  - **Fix needed:** Split the rule. Grant `get` on `configmaps` with `resourceNames: ["api-config"]`. Remove `list` unless the workload requires it. If `list` is required, move it to a separate rule that is justified explicitly, because it cannot be scoped to one ConfigMap.

### Network Policies

- **NetworkPolicy `api-server-policy`** (namespace `secure-app`), **HIGH**
  - **Gap:** The policy selects only pods labeled `app: api-server`. No namespace-wide default-deny exists, so every other pod in `secure-app` accepts and initiates traffic without restriction.
  - **Impact:** A compromised or misconfigured pod outside `api-server` can reach the API or any other pod in the namespace, and can make unrestricted outbound connections. Lateral movement is not contained.
  - **Fix needed:** Add a namespace-wide default-deny policy, but only together with allow rules for every legitimate flow (see Unified Recommendations, item 1).

- **NetworkPolicy `api-server-policy`** (namespace `secure-app`), **LOW**
  - **Gap:** The DNS egress rule uses `namespaceSelector: {}` with `podSelector: k8s-app: kube-dns`. This permits DNS egress to kube-dns pods in any namespace, not only `kube-system`.
  - **Impact:** Limited, but a pod in another namespace that carries the `k8s-app: kube-dns` label could receive DNS traffic from `api-server`, which is an unnecessary trust boundary.
  - **Fix needed:** Replace `namespaceSelector: {}` with `namespaceSelector.matchLabels: kubernetes.io/metadata.name: kube-system`.

### Security Contexts

- **Deployment `api-server`** (namespace `secure-app`), **MEDIUM**
  - **Missing setting:** `seccompProfile` is not set at the pod level. The container runs without a syscall filter.
  - **Impact:** The container can invoke the full set of Linux syscalls, which widens the kernel attack surface available after a container compromise.
  - **Fix needed:** Set `spec.template.spec.securityContext.seccompProfile.type: RuntimeDefault`.
  - **Existing controls (confirmed):** Non-root execution, read-only root filesystem, dropped capabilities.

### Resource Limits

- **Deployment `api-server`** (container `api`), no findings. CPU and memory limits are set. No action required.

### Pod Security

- **ServiceAccount `api-server`** (namespace `secure-app`), **MEDIUM**
  - **Issue:** `automountServiceAccountToken` is not set to `false`, so an API token is mounted into pods that do not need Kubernetes API access.
  - **Impact:** A compromised pod receives a token that can be used against the Kubernetes API within the permissions of `api-server-role`.
  - **Fix needed:** Set `automountServiceAccountToken: false` on the ServiceAccount. Enable token mounting only on pods that call the Kubernetes API.

- **Deployment `api-server`** (container `api`), **MEDIUM**
  - **Issue:** The pod spec does not set `automountServiceAccountToken: false`, so the default API token is mounted into the `api` container.
  - **Impact:** The same token exposure as above applies to the running container, even if the ServiceAccount setting is later changed.
  - **Fix needed:** Set `spec.template.spec.automountServiceAccountToken: false` in the Deployment, unless the `api` container calls the Kubernetes API. The pod-level setting takes precedence over the ServiceAccount setting.

- **Deployment `api-server`** (image `api-server:v1.2.3`), **LOW**
  - **Issue:** The image uses a mutable tag with no registry or digest.
  - **Impact:** The tag can be repointed to a different image without a change to the manifest, which weakens provenance and makes rollbacks unverifiable.
  - **Fix needed:** Pin the image to a fully qualified registry path and digest, for example `registry.example.com/api-server@sha256:<digest>`, and keep the tag as an informational comment.

### Verdict: ESCALATE

The reviewer escalated this workflow for the following reasons. The proposed `default-deny-all` policy (`podSelector: {}` with both Ingress and Egress) applies to every pod in the production namespace `secure-app`. Without allow rules for the existing `api-server` ingress and egress paths, kubelet probes, and other workloads, it could break legitimate traffic. The proposed fix also addresses only one of seven findings. The RBAC, seccomp, token automount, and image tag issues remain unresolved. A human owner must confirm the traffic flows before the default-deny policy is applied.

## Unified Recommendations

Items are ordered by priority.

### 1. HIGH: Add a namespace default-deny with explicit allow rules (`secure-app`)

Do not apply `default-deny-all` alone. Deploy it in the same change as the following allow rules:

- **`allow-dns-kube-system`** (from the existing fix): permits UDP and TCP port 53 egress from all pods to kube-dns pods in `kube-system`. This rule is required, or DNS resolution fails once default-deny takes effect.
- **Ingress to `app: api-server`:** allow ingress only from the pods that currently call the API, selected by their actual labels, on the port the API serves. Identify these flows from current connection logs or a network flow tool before applying the policy. Do not guess the labels or ports.
- **Egress from `app: api-server`:** allow only the destinations the service currently reaches (for example, the database or external API endpoints), selected by label or CIDR and port.
