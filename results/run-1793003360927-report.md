## Container Security (Kubernetes) Findings

**Risk Level**: 🔴 **CRITICAL**

Production deployment exhibits critical RBAC over-provisioning, missing security contexts, absent resource limits, and no network policy controls, creating severe cluster-wide security exposure.

### RBAC Issues

❌ **CRITICAL**: Cluster-wide administrative role binding  
- **Resource**: `ClusterRole` named `admin-like-role` (cluster-wide scope)
- **Issue**: Grants wildcard permissions (`*`) on all API groups, resources, and verbs, equivalent to `cluster-admin` access
- **Impact**: Any pod using the bound service account can read/write/delete any cluster resource, including secrets, RBAC definitions, and workloads across all namespaces
- **Recommendation**: Replace with narrowly scoped role granting only necessary verbs on specific resources (e.g., read-only access to pods, deployments, services in the application namespace)

❌ **CRITICAL**: Over-privileged cluster role binding  
- **Resource**: `ClusterRoleBinding` named `app-admin-binding` (cluster-wide scope)
- **Binding**: Grants `admin-like-role` to `ServiceAccount` `app-sa` in namespace `insecure-app`
- **Issue**: Binds the cluster-wide administrative role to a single application service account, extending cluster-admin privileges to user workloads
- **Impact**: Container breakout or application compromise directly compromises the entire cluster; lateral movement to other namespaces is unrestricted
- **Recommendation**: Replace with a namespaced `RoleBinding` that grants only the minimum permissions required for the application (e.g., read access to `ConfigMaps` and `Secrets` needed by the application)

### Security Contexts

❌ **HIGH**: Missing pod-level security context  
- **Resource**: `Deployment` named `insecure-app` (namespace `insecure-app`)
- **Issue**: Pod spec lacks a `securityContext` definition; containers inherit all default Linux capabilities and run with the container image's default user (typically root)
- **Impact**: Containers run as root (UID 0) with full capability set (`CAP_SYS_ADMIN`, `CAP_NET_ADMIN`, etc.), enabling trivial privilege escalation and system compromise
- **Recommendation**: Add pod-level `securityContext` with `runAsNonRoot: true`, `runAsUser: 1000`, and `fsGroup: 2000`

❌ **HIGH**: Container runs as root user  
- **Resource**: `Deployment` named `insecure-app`, container `app` (namespace `insecure-app`)
- **Issue**: Container spec does not define `runAsNonRoot: true`; if no default user is baked into the image, execution defaults to UID 0 (root)
- **Impact**: Root-level process can modify files, install packages, and escalate privileges within the container and potentially to the host
- **Recommendation**: Add container-level `securityContext` with `runAsNonRoot: true` and `runAsUser: 1000`; ensure the application supports running as non-root or add a non-root user to the container image

❌ **HIGH**: Writable root filesystem  
- **Resource**: `Deployment` named `insecure-app`, container `app` (namespace `insecure-app`)
- **Issue**: Container spec does not define `readOnlyRootFilesystem: true`; root filesystem (/) is writable by the container process
- **Impact**: Compromised application can write malware, modify system binaries, or create persistence mechanisms; forensics are hindered by mutation of runtime state
- **Recommendation**: Set `readOnlyRootFilesystem: true` and mount writable `emptyDir` volumes at `/tmp` and `/var/tmp` for application temporary file needs

### Resource Limits

❌ **HIGH**: Missing resource constraints  
- **Resource**: `Deployment` named `insecure-app`, container `app` (namespace `insecure-app`)
- **Issue**: Container spec lacks `resources.requests` and `resources.limits` for CPU and memory
- **Impact**: Workload can consume unbounded cluster resources, causing denial of service to other pods; no scheduler guarantee of baseline resources; node memory exhaustion triggers OOMKill with unpredictable victim selection
- **Recommendation**: Define `requests` (guaranteed floor) and `limits` (hard ceiling):
  - CPU requests: 100m, limits: 500m
  - Memory requests: 128Mi, limits: 512Mi
  - Baseline these values on actual application profiling under production load

### Network Policies

❌ **HIGH**: No network isolation  
- **Resource**: Namespace `insecure-app`; no `NetworkPolicy` defined
- **Issue**: Default-allow network posture; pods accept ingress traffic from all sources (all namespaces, external networks) by default
- **Impact**: Lateral movement between workloads is unrestricted; compromised pod can scan and attack other services; external attacks can probe internal services if cluster network is partially exposed
- **Recommendation**: Create a `NetworkPolicy` in namespace `insecure-app` that:
  - Denies all ingress by default (`podSelector: {}`, `ingress: []`)
  - Allows ingress only from specific pods/namespaces with required labels (e.g., allow ingress from `frontend` namespace pods on port 8080 if this is a backend service)
  - Allows egress to Kubernetes API server and external services as needed by the application
  - Example: `policyTypes: [Ingress]`, `ingress: [from: [{namespaceSelector: {matchLabels: {name: frontend}}}], ports: [{protocol: TCP, port: 8080}]]`

### Pod Security

⚠️ **MEDIUM**: Non-reproducible container image  
- **Resource**: `Deployment` named `insecure-app`, container `app` (namespace `insecure-app`)
- **Issue**: Container image uses `latest` tag with `imagePullPolicy: Always`
- **Impact**: Each pod restart pulls a potentially different image version; breaks reproducibility, complicates security scanning, and prevents pinning to known-good versions; supply-chain attacks are harder to detect
- **Recommendation**: Pin image to a specific digest or version tag (e.g., `app:v1.2.3` or `app@sha256:abcd1234...`); set `imagePullPolicy: IfNotPresent` for stable deployments; use image scanning in CI/CD to validate images before tagging release versions

   - apiGroups: [""]

  name: insecure-app
  namespace: insecure-app
spec:
  template:
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        fsGroup: 2000
      containers:
      - name: app
        image: app:v1.2.3  # Pin to specific version, remove "latest"
        imagePullPolicy: IfNotPresent
        securityContext:
          runAsNonRoot: true
          runAsUser: 1000
          readOnlyRootFilesystem: true
          allowPrivilegeEscalation: false
          capabilities:
            drop: ["ALL"]
        resources:
          requests:
            cpu: 100m
            memory: 128Mi
          limits:
            cpu: 500m
            memory: 512Mi
        volumeMounts:
        - name: tmp
          mountPath: /tmp
        - name: var-tmp
          mountPath: /var/tmp
      volumes:
      - name: tmp
        emptyDir: {}
      - name: var-tmp
        emptyDir: {}

## Verdict Summary

**Reasoning**:

The provided remediation YAML for security contexts and resource limits introduces non-trivial changes to the runtime behavior of the `insecure-app` workload:

- **emptyDir mounts** at `/tmp` and `/var/tmp` may conflict with application expectations (e.g., if the app expects `/tmp` to be shared across container restarts or with init containers)
- **Resource requests** (128Mi memory) are baseline estimates and require validation against actual production profiling; undersized memory may cause OOMKill during load spikes
- **runAsUser: 1000** assumes the application supports non-root execution; if the image does not have a non-root user configured, startup will fail with permission errors
- **readOnlyRootFilesystem** requires the application to tolerate immutable system directories; applications that attempt to write to `/etc`, `/lib`, or other system paths will fail

The RBAC remediation changes the ClusterRoleBinding to a RoleBinding and introduces a new Role with configmaps and secrets access, but lacks explicit justification for the selected permissions against the actual application code or runtime behavior.

4. **Application Changes**: If the application cannot run as non-root, either update the application or adjust the security context to an acceptable user UID
