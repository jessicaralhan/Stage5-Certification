# Infrastructure Security Report: Insecure-App Production Workload

## Executive Summary

This report covers the Kubernetes Security Review (Container Security) of the `insecure-app` workload in production, which ran as correlation ID `1792990890134` on 2026-10-26. The review found a **CRITICAL** combined risk. The `app-sa` ServiceAccount holds cluster-admin-equivalent privileges through the wildcard ClusterRole `admin-like-role`, bound by the ClusterRoleBinding `app-admin-binding`, so a compromise of the application would give an attacker full control of the cluster. The workload also has no NetworkPolicy, no security context hardening, and no resource limits. The reviewer issued an **ESCALATE** verdict because the proposed fixes are not safe to apply as written. Immediate action is needed on the RBAC exposure, and a human owner should validate the remediation plan before any change reaches production.

## Findings by Domain

## Container Security (Kubernetes) Findings

Risk Level: **CRITICAL**

The `insecure-app` workload in production has critical RBAC exposure through a wildcard ClusterRole bound to its ServiceAccount, plus missing network isolation, security context hardening, and resource limits.

### RBAC Issues

❌ **CRITICAL**: ClusterRole `admin-like-role` grants cluster-admin equivalence.
   - **Resource**: ClusterRole `admin-like-role` (cluster-wide)
   - **Issue**: Grants wildcard verbs (`*`) on wildcard resources (`*`) across all API groups (`*`).
   - **Impact**: Any principal bound to this role can read or modify every resource in the cluster, including Secrets in all namespaces. Compromise of the application yields full cluster control.
   - **Fix needed**: Delete the ClusterRole after confirming no other bindings reference it. Replace it with a namespaced Role scoped to the workload's actual needs.

❌ **CRITICAL**: ClusterRoleBinding `app-admin-binding` binds the admin-equivalent role to the application.
   - **Resource**: ClusterRoleBinding `app-admin-binding`
   - **Issue**: Binds `admin-like-role` to ServiceAccount `app-sa` in namespace `insecure-app`, granting cluster-wide access.
   - **Impact**: The application runs with full control of the cluster. This is the direct path from a container compromise to cluster takeover.
   - **Fix needed**: Delete the ClusterRoleBinding. The proposed fix only includes this deletion as a YAML comment, so it must be run manually with `kubectl delete clusterrolebinding app-admin-binding`.

⚠️ **HIGH**: ServiceAccount `app-sa` carries excessive privileges and auto-mounts its token.
   - **Resource**: ServiceAccount `app-sa` (namespace `insecure-app`)
   - **Issue**: Used by the workload with cluster-wide wildcard privileges, and its API token is auto-mounted by default.
   - **Impact**: The token gives any attacker who reaches the container an authenticated identity with cluster-wide reach.
   - **Fix needed**: Reduce the permissions to a namespaced Role (see Unified Recommendations) and disable token auto-mounting at the ServiceAccount and Pod level.

### Network Policies

⚠️ **HIGH**: No NetworkPolicy exists in namespace `insecure-app`.
   - **Namespace**: `insecure-app`
   - **Policy gap**: All ingress and egress traffic to and from the `insecure-app` Deployment is allowed by default.
   - **Impact**: Any pod in the cluster can reach the application, and the application can reach any destination, including the Kubernetes API, other namespaces, and external endpoints. This allows lateral movement and data exfiltration.
   - **Fix needed**: Apply a default-deny NetworkPolicy with explicit allow rules. The proposed policy `insecure-app` is a starting point but needs revision (see Unified Recommendations).

### Security Contexts

⚠️ **HIGH**: Container `app` has no securityContext.
   - **Resource**: Deployment `insecure-app`, container `app` (image `app:latest`)
   - **Missing settings**: `runAsNonRoot: true`, `runAsUser`, and `allowPrivilegeEscalation: false`.
   - **Impact**: The image may run as root. Root in a container, combined with a writable filesystem and no privilege restrictions, makes container escape and host compromise easier.

⚠️ **MEDIUM**: Root filesystem is writable.
   - **Resource**: Deployment `insecure-app`, container `app`
   - **Missing settings**: `readOnlyRootFilesystem: true`
   - **Impact**: An attacker can write malware, modify binaries, or persist changes inside the container.

⚠️ **MEDIUM**: Privilege escalation is not blocked.
   - **Resource**: Deployment `insecure-app`, container `app`
   - **Missing settings**: `allowPrivilegeEscalation: false`
   - **Impact**: Processes can gain more privileges than their parent, for example through setuid binaries.

⚠️ **MEDIUM**: Mutable image tag with `imagePullPolicy: Always`.
   - **Resource**: Deployment `insecure-app`, image `app:latest`
   - **Impact**: Deployments are not reproducible, and a tampered or unintended image at the tag is pulled automatically on every restart.
   - **Fix needed**: Pin the image to an immutable version tag or digest.

### Resource Limits

⚠️ **MEDIUM**: Container `app` has requests but no limits.
   - **Resource**: Deployment `insecure-app`, container `app`
   - **Missing settings**: CPU and memory `limits`
   - **Impact**: The container can consume unbounded node resources, which risks noisy-neighbor outages and node instability.

### Pod Security

⚠️ **HIGH**: No Pod-level securityContext, seccomp profile, or capability drops.
   - **Resource**: Deployment `insecure-app`, Pod spec
   - **Missing settings**: `seccompProfile: {type: RuntimeDefault}`, `capabilities: {drop: ["ALL"]}`
   - **Impact**: The container runs with the default, broader syscall and capability set, which increases the attack surface.

⚠️ **MEDIUM**: ServiceAccount token is mounted into the container.
   - **Resource**: Deployment `insecure-app`, Pod spec, ServiceAccount `app-sa`
   - **Missing settings**: `automountServiceAccountToken: false`
   - **Impact**: The `app-sa` token is available to the application even though it likely does not need Kubernetes API access. Any code execution in the container can use it.

### Verdict: ESCALATE

The reviewer escalated this report to a human because the proposed fixes are not safe to apply as written.

- **RBAC fixes are incomplete.** The deletions of `ClusterRole/admin-like-role` and `ClusterRoleBinding/app-admin-binding` appear only as YAML comments. The generated manifests create a namespaced `Role` and `RoleBinding`, so the cluster-admin-equivalent binding would remain in place unless it is deleted manually.
- **NetworkPolicy egress is likely too restrictive.** The proposed egress rule allows only DNS (UDP/TCP 53). It does not allow the Kubernetes API or external dependencies the application may need, so applying it could cause an outage. The ingress rule also assumes the ingress controller runs in the `ingress-nginx` namespace and that the application listens on port 8080. Neither assumption was verified.
- **Hardening findings have no fixes.** Seven findings for `Deployment/insecure-app` have no remediation: four security context findings, one resource limits finding, and two pod security findings. The reviewer's text cites eight, but the analyzer output contains seven.
