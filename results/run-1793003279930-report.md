❌ **CRITICAL**: Production RDS cluster destruction and recreation forced by subnet group modification.

- **Resource**: `aws_rds_cluster.prod`

- **Forcing Attribute**: `db_subnet_group_name`
- **Environment**: Production
- **Impact**: This change will cause immediate production downtime. The RDS cluster will be destroyed and a new cluster created, resulting in service unavailability and potential data consistency issues during the transition window. Automated backups and snapshots may not capture in-flight transactions.
- **Current State**: The Terraform plan shows the subnet group name changing, which AWS treats as a replacement-required attribute for RDS clusters.

### Security Exposure

⚠️ **HIGH**: Production RDS cluster encryption does not utilize customer-managed KMS key.

- **Resource**: `aws_rds_cluster.prod`
- **Issue**: Storage encryption is enabled (`storage_encrypted = true`), but no `kms_key_id` is specified in the configuration. This defaults encryption to AWS-managed keys rather than customer-managed keys. A new `aws_kms_key.rds` resource has been created in the plan but is not referenced by the cluster.
- **Impact**: Encryption keys are managed by AWS, not your organization. This limits audit trail visibility, key rotation policies, and compliance posture for regulated workloads. The newly created KMS key represents wasted infrastructure investment and ongoing monthly costs with no operational benefit.
- **Compliance Risk**: Many regulatory frameworks (PCI-DSS, HIPAA, SOC 2) require customer-managed encryption keys for sensitive data at rest.

### Cost Impact

- **KMS Key Creation & Rotation**: New `aws_kms_key.rds` will incur monthly AWS KMS key storage and key rotation fees (~$1 USD/month per key), plus API call costs.
- **RDS Cluster Replacement**: Destroying and recreating the cluster incurs:
  - Temporary compute and storage charges during migration
  - Potential data transfer costs if the cluster spans availability zones
  - Loss of automated backup continuity during downtime window

## Unified Recommendations

### Priority 1: CRITICAL — Prevent Production Downtime

**Action**: Implement lifecycle rule to prevent unintended RDS cluster replacement.

**Implementation**:
```hcl
resource "aws_rds_cluster" "prod" {
  # ... existing configuration ...
  
  lifecycle {
    ignore_changes = [db_subnet_group_name]
  }
}
```

**Rationale**: If the subnet group must change, this lifecycle rule prevents Terraform from forcing a cluster replacement. Manual subnet group migration can then be performed in a controlled, blue-green deployment pattern:
1. Create new subnet group with desired configuration
2. Update `db_subnet_group_name` reference in code
3. Run `terraform apply` (no replacement occurs due to lifecycle rule)
4. Manually remove old subnet group after validation

**Timeline**: Must be applied before any production apply. Recommend code review and staging environment validation first.

---

### Priority 2: HIGH — Enable Customer-Managed Encryption

**Action**: Configure RDS cluster to use the newly created customer-managed KMS key.

**Implementation**:
```hcl
resource "aws_rds_cluster" "prod" {
  # ... existing configuration ...
  
  kms_key_id = aws_kms_key.rds.arn
}
```

**Rationale**: This change connects the unused KMS key to the RDS cluster, enabling customer-managed encryption. This is a configuration change that does **not** force a cluster replacement; AWS applies the new key to the cluster in-place during the next maintenance window.

**Security Benefit**: 
- Grants your organization direct control over encryption key lifecycle
- Enables KMS key policies, audit logging, and key rotation schedules
- Satisfies compliance requirements for customer-managed encryption keys

**Timeline**: Can be applied in the same change set as the lifecycle rule fix if both are implemented before apply.
