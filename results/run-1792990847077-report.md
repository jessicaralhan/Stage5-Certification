## Executive Summary

This review covered the Kubernetes manifests for the `api-server` workload in the `secure-app` namespace. The combined risk level is **HIGH**, and the verdict is **ESCALATE**. The `api-server` workload has a sound baseline: it runs as non-root, uses a read-only root filesystem, drops capabilities, sets resource limits, and has scoped RBAC. The main gap is that namespace `secure-app` has no default-deny NetworkPolicy, so the frontend and database pods are open to unrestricted traffic. The lower-severity gaps are a missing seccomp profile, an auto-mounted ServiceAccount token, an overly broad DNS egress rule, and a misleading RBAC rule. The proposed `default-deny-all` fix must not be applied as written. It would block frontend-to-api-server and api-server-to-database traffic in production, so it needs human review and companion allow rules before rollout. Key actions are to author those allow rules, scope the DNS egress rule, and apply the pod-level hardening changes.

## Findings by Domain

### Container Security (Kubernetes) Findings

Risk Level: **HIGH**

The api-server workload has a solid baseline (non-root, read-only root filesystem, dropped capabilities, resource limits, and scoped RBAC), but the namespace lacks a default-deny network policy and has minor gaps in seccomp, token automount, and DNS egress scoping.

#### RBAC Issues

- **LOW**: Role `api-server-role` (namespace `secure-app`)
  - **Issue**: The `list` verb on `configmaps` is combined with `resourceNames`. RBAC does not enforce `resourceNames` on list requests, so the rule grants broader access than it appears to.
  - **Why it matters**: The rule implies a restriction that does not exist. Reviewers and auditors may trust it, and the effective access is wider than intended.
  - **Fix needed**: Remove the `list` verb. Replace it with `get` only, and keep `resourceNames` scoped to the specific ConfigMaps the workload reads.

#### Network Policies

- **HIGH**: Namespace `secure-app`, no default-deny policy
  - **Gap**: No default-deny NetworkPolicy exists. `api-server-policy` selects only pods labeled `app: api-server`, so frontend and database pods, and any other pods in the namespace, have unrestricted ingress and egress.
  - **Impact**: Lateral movement within the namespace is unrestricted. A compromised pod can reach the database directly.
  - **Fix needed**: Add a default-deny policy together with explicit allow rules (see Unified Recommendations). Do not apply the generated `default-deny-all` policy alone.

- **MEDIUM**: NetworkPolicy `api-server-policy` (namespace `secure-app`)
  - **Gap**: The DNS egress rule uses `namespaceSelector: {}` with `podSelector: k8s-app: kube-dns`. This allows UDP 53 to kube-dns pods in any namespace rather than only `kube-system`.
  - **Impact**: Pods labeled `app: api-server` can send DNS traffic to any namespace that hosts a pod with the `k8s-app: kube-dns` label. A malicious workload there could receive DNS queries and exfiltrate data through them.
  - **Fix needed**: Replace the `namespaceSelector` with `kubernetes.io/metadata.name: kube-system`.

#### Security Contexts

- **MEDIUM**: Deployment `api-server` (namespace `secure-app`)
  - **Missing settings**: Neither the pod nor the `api` container sets `seccompProfile`.
  - **Impact**: The container does not run under the RuntimeDefault seccomp profile, so it has access to more syscalls than necessary.
  - **Fix needed**: Add `seccompProfile: {type: RuntimeDefault}` to the pod-level `securityContext`.

#### Resource Limits

- No issues identified. The `api` container has resource limits set.

#### Pod Security

- **MEDIUM**: ServiceAccount `api-server` and pods of Deployment `api-server` (namespace `secure-app`)
  - **Issue**: Neither the ServiceAccount nor the pod spec sets `automountServiceAccountToken: false`.
  - **Impact**: A Kubernetes API token is mounted into the pod even though the workload only needs narrow ConfigMap and Secret reads. If the container is compromised, the token can be used against the API server.
  - **Fix needed**: Set `automountServiceAccountToken: false` on the ServiceAccount, and set it again on the pod spec. Use a projected token volume only if the workload needs API access.

### Verdict: ESCALATE

The proposed default-deny fix would break production traffic. The `default-deny-all` policy selects every pod in `secure-app`, including the frontend and database pods, but the fix includes no allow rules for frontend-to-api-server or api-server-to-database traffic. The fix also leaves the overly broad DNS rule in `api-server-policy` unchanged and does not address the seccomp, `automountServiceAccountToken`, or RBAC findings. It is not a complete remediation and requires human sign-off because of the production blast radius.

## Unified Recommendations

### HIGH

1. **Add a default-deny policy with explicit allow rules, not the generated policy alone.**
   - Apply `default-deny-all` (`podSelector: {}`, `policyTypes: [Ingress, Egress]`) to namespace `secure-app` only after the following allow rules are in place:
     - An ingress rule on pods labeled `app: api-server` that allows traffic from the frontend pods' labels on the port the API listens on.
     - An egress rule on frontend pods that allows traffic to the api-server pods' labels on that same port.
     - An egress rule on pods labeled `app: api-server` that allows traffic to the database pods' labels on the database port.
     - An ingress rule on database pods that allows traffic from `app: api-server` on the database port.
   - The frontend and database pod labels and ports are not included in the review input. Confirm them from the live manifests before writing these rules.
   - Keep the `allow-dns-kube-system` policy from the generated fix. It gives all pods in the namespace DNS egress to kube-dns in `kube-system`, which the default-deny policy would otherwise block.
   - Test in a staging namespace first, and confirm frontend-to-API and API-to-database connectivity before promoting to production.

### MEDIUM

2. **Scope the DNS egress rule in `api-server-policy`.**
   - Replace `namespaceSelector: {}` with `namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: kube-system}}`, keeping `podSelector: {matchLabels: {k8s-app: kube-dns}}` and the UDP and TCP port 53 rules.

3. **Set the seccomp profile on the `api-server` Deployment.**
   - Add the following to the pod-level `securityContext`:
     ```yaml
     securityContext:
       seccompProfile:
         type: RuntimeDefault
     ```

4. **Disable ServiceAccount token automount for `api-server`.**
   - Set `automountServiceAccountToken: false`
