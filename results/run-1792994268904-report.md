#### RBAC Issues

❌ **CRITICAL**: Wildcard ClusterRole grants cluster-admin-equivalent access.
- **Resource**: ClusterRole `admin-like-role` (cluster-wide)
- **Issue**: `apiGroups`, `resources`, and `verbs` are all set to `*`.
- **Impact**: Any principal bound to this role can read, modify, or delete every resource in the cluster, including Secrets in all namespaces.
- **Fix needed**: Delete `admin-like-role`, or replace it with a role that lists only the specific API groups, resources, and verbs the workload requires.

❌ **CRITICAL**: Cluster-wide binding grants admin-equivalent role to the workload ServiceAccount.
- **Resource**: ServiceAccount `app-sa` in namespace `insecure-app`, via ClusterRoleBinding `app-admin-binding`
- **Issue**: The ClusterRoleBinding attaches `admin-like-role` to `app-sa` across the entire cluster.
- **Impact**: Compromising any `insecure-app` pod yields full cluster control.
- **Fix needed**: Delete the ClusterRoleBinding `app-admin-binding`. Determine the API calls `insecure-app` actually makes, then create a namespaced Role in `insecure-app` with only those permissions and bind it to `app-sa` with a RoleBinding.

#### Network Policies

⚠️ **HIGH**: No NetworkPolicy governs the workload.
- **Namespace**: `insecure-app`
- **Policy gap**: No NetworkPolicy exists, so all ingress and egress traffic to and from the `insecure-app` Deployment is allowed by default.
- **Impact**: Any pod in the cluster can reach `insecure-app`, and a compromised pod can make arbitrary outbound connections, including to the Kubernetes API and external hosts. This enables lateral movement and data exfiltration.
- **Fix needed**: Apply a default-deny NetworkPolicy in `insecure-app` covering both `Ingress` and `Egress`. Then add explicit allow rules for only the required sources, destinations, and ports. Egress to the cluster DNS service must be permitted explicitly, or name resolution will fail.

#### Security Contexts

⚠️ **HIGH**: Container does not enforce a non-root user.
- **Resource**: Deployment `insecure-app`, container `app`
- **Missing settings**: No `securityContext` and no `runAsNonRoot`.
- **Impact**: The container may run as UID 0 in production. A container escape or application flaw would then grant root-level access on the node.
- **Fix needed**: Set `runAsNonRoot: true` and a non-zero `runAsUser` at the pod or container level.

- **Impact**: An attacker can modify binaries and configuration inside the container, including persistence mechanisms.
