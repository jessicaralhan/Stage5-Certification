## Container Security (Kubernetes) Findings

Risk Level: **CRITICAL**

The manifests grant a workload cluster-admin-equivalent privileges through a wildcard ClusterRole, lack any NetworkPolicy, and run the container without hardening, which is unacceptable for production.

### RBAC Issues

- **CRITICAL**: `admin-like-role` (ClusterRole, cluster-wide)
  - **Issue:** Grants wildcard `apiGroups`, `resources`, and `verbs` (`*/*/*`), which is effectively cluster-admin.
  - **Why it matters:** Any compromise of the `insecure-app` pod gives the attacker full control of the cluster, including every namespace, Secret, and workload.
  - **Fix needed:** Delete this ClusterRole once no other subjects depend on it. The generated `app-role` Role is a replacement, not a removal, so the wildcard grant remains until this step is done.

- **CRITICAL**: `app-admin-binding` (cluster-wide binding; analyzer recorded the kind as ClusterRole but described it as a ClusterRoleBinding)
  - **Issue:** Binds `admin-like-role` to ServiceAccount `app-sa` in namespace `insecure-app`.
  - **Why it matters:** This binding is what makes the wildcard role apply to the workload. The generated `app-role-binding` is namespaced and does not remove it.
  - **Fix needed:** Delete this ClusterRoleBinding. Confirm its kind with `kubectl get clusterrolebinding app-admin-binding` before deletion.

- **HIGH**: `app-sa` (ServiceAccount, namespace `insecure-app`)
  - **Issue:** Does not set `automountServiceAccountToken: false`, so its privileged token is mounted into the pod by default.
  - **Why it matters:** Any process in the container can read the token and use the cluster-admin-equivalent permissions above.
  - **Fix needed:** Set `automountServiceAccountToken: false` on the ServiceAccount, and set it on the Deployment's pod spec as well if the application does not call the Kubernetes API.

### Network Policies

- **HIGH**: `insecure-app` (namespace `insecure-app`, no NetworkPolicy exists)
  - **Issue:** All ingress and egress traffic to and from `insecure-app` pods is allowed by default.
  - **Why it matters:** Any pod in the cluster can reach the application, and the application can reach any service, which enables lateral movement.
  - **Fix needed:** Apply the generated `default-deny-allow-dns` policy, but only after adding the ingress rules described in the Unified Recommendations. As generated, it contains no ingress allow rules, so it would block all inbound traffic to the production workload.

### Security Contexts

- **HIGH**: `insecure-app` Deployment, container `app`
  - **Missing:** No `securityContext`, no `runAsNonRoot`.
  - **Why it matters:** The container may run as root, so a container escape would give root on the node.
  - **Fix needed:** Set `runAsNonRoot: true` and a non-zero `runAsUser`.

- **MEDIUM**: `insecure-app` Deployment, container `app`
  - **Missing:** `readOnlyRootFilesystem: true`.
  - **Why it matters:** An attacker can write to the root filesystem, including binaries and configuration.
  - **Fix needed:** Set `readOnlyRootFilesystem: true`, and mount writable `emptyDir` volumes at any paths the application writes to.

- **MEDIUM**: `insecure-app` Deployment, container `app`
  - **Missing:** `allowPrivilegeEscalation: false`.
  - **Why it matters:** Processes can gain more privileges than their parent, for example through setuid bin
