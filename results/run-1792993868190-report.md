### Destructive Changes

❌ **CRITICAL**: Production database cluster is planned for destroy-and-recreate.
- **Resource**: `aws_rds_cluster.prod`
- **Action**: `destroy_and_recreate`
- **Forcing Attribute**: `db_subnet_group_name`
- **Environment**: Production
- **Why It Matters**: Recreating the cluster deletes the existing database. Without a verified snapshot and a maintenance window, this risks permanent data loss and production outage. Restoring from snapshot adds time and cost.
- **Recommendation**: Do not apply this plan. Keep `db_subnet_group_name` pointed at the existing subnet group, and add `lifecycle { prevent_destroy = true }` to `aws_rds_cluster.prod`. If a new subnet group is required, create it as a separate resource and migrate during a planned maintenance window after a verified snapshot.

### Security Exposure

❌ **HIGH**: Production cluster can be deleted without a guard.
- **Resource**: `aws_rds_cluster.prod`
- **Exposure**: `deletion_protection` is not set and defaults to `false`.
- **Impact**: A single `terraform destroy` or console action can delete the production database.
- **Recommendation**: Set `deletion_protection = true`.

❌ **HIGH**: Cluster falls back to the default VPC security group.
- **Resource**: `aws_rds_cluster.prod`
- **Exposure**: `vpc_security_group_ids` is not set, so the default VPC security group applies.
- **Impact**: The default group may permit broader network access than the database requires.
- **Recommendation**: Create a dedicated `aws_security_group.rds_prod` that allows ingress only on the engine port (5432 for PostgreSQL or 3306 for MySQL) from the application security group, then set `vpc_security_group_ids = [aws_security_group.rds_prod.id]`.

⚠️ **UNRATED** (analyzer did not assign severity): No audit log export for production database.
- **Resource**: `aws_rds_cluster.prod`
- **Exposure**: `enabled_cloudwatch_logs_exports` is not set, so audit, error, and slow query logs are not exported.
- **Impact**: Security investigations and incident forensics lack database-level audit data.
- **Recommendation**: Set `enabled_cloudwatch_logs_exports` to the log types supported by the engine (for example, `["audit", "error", "slowquery"]` for Aurora MySQL, or `["postgresql"]` for Aurora PostgreSQL).

⚠️ **UNRATED** (analyzer did not assign severity): Static password is the only authentication method.
- **Resource**: `aws_rds_cluster.prod`
- **Exposure**: `iam_database_authentication_enabled` is not set and defaults to `false`.
- **Impact**: Access depends solely on a static master password, which is harder to rotate and audit.
- **Recommendation**: Set `iam_database_authentication_enabled = true`, and use IAM roles for application database access where the engine supports it.

⚠️ **UNRATED** (analyzer did not assign severity): Default master username.
- **Resource**: `aws_rds_cluster.prod`
- **Exposure**: `master_username` is set to the common default `admin`.
- **Impact**: Attackers can target a known username during credential guessing.
- **Recommendation**: Replace `admin` with a non-default username. Where supported, set `manage_master_user_password = true` so AWS Secrets Manager manages the password. Changing `master_username` on an existing cluster can force replacement, so validate with the plan before applying.

⚠️ **UNRATED** (analyzer did not assign severity): Short KMS recovery window and implicit key policy.
- **Resource**: `aws_kms_key.rds`
- **Exposure**: `deletion_window_in_days` is set to the minimum of 7, and no explicit key policy is defined.
- **Impact**: Accidental key scheduling for deletion leaves little time to recover, and the default key policy may grant broader access than intended.
- **Recommendation**: Set `deletion_window_in_days = 30`, and define an explicit `policy` on `aws_kms_key.rds` that grants only the required administrators and the RDS service principal.
