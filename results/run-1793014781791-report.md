## Container Security (Kubernetes) Findings

**Risk Level: HIGH**

Manifests demonstrate strong core security hardening with proper RBAC scoping, security contexts, and resource limits, but contain a HIGH-severity overly-permissive DNS egress rule and medium-severity image pull and secrets access concerns.

### Network Policies

❌ **HIGH**: DNS egress rule permits unrestricted external resolution and potential data exfiltration.
   - **Resource**: `NetworkPolicy` named `api-server-policy` in namespace `secure-app`
   - **Issue**: Egress rule uses empty `namespaceSelector`, allowing all DNS queries to any namespace without restriction
   - **Impact**: Pods can perform DNS lookups to arbitrary external destinations, enabling DNS-based data exfiltration, command-and-control callbacks, and reconnaissance of external services
   - **Recommendation**: Replace the overly-permissive egress rule with a scoped policy. Explicitly allow DNS only to the `kube-system` namespace (CoreDNS) on port 53/UDP, and deny egress to external nameservers. Example: add an egress rule that selects only pods with `k8s-app: kube-dns` in the `kube-system` namespace.

### RBAC Issues

⚠️ **MEDIUM**: Role grants direct access to secrets, increasing exposure risk.
   - **Resource**: `Role` named `api-server-role` in namespace `secure-app`
   - **Issue**: Role grants `get` permission on the `secrets` resource, allowing pods to read sensitive data stored as Kubernetes Secrets
   - **Impact**: If the `api-server` pod is compromised, all secrets accessible to this role (e.g., database credentials, API tokens) can be exfiltrated
   - **Recommendation**: Migrate to an external secret management system (HashiCorp Vault, AWS Secrets Manager, or Azure Key Vault) to decouple secrets from Kubernetes RBAC. If secrets must remain in Kubernetes, restrict the role to only the specific secret names required (e.g., `resourceNames: ["api-db-credential"]`) and remove the blanket `get` permission.

### Pod Security

⚠️ **MEDIUM**: Image pull policy and tag mutability create supply chain attack surface.
   - **Resource**: `Deployment` named `api-server` in namespace `secure-app`
   - **Issue**: Container uses `imagePullPolicy: Always`, which bypasses local image cache and re-pulls the image on every restart; image is tagged `v1.2.3` (mutable tag), not an immutable digest
   - **Impact**: On each pod restart, the image is re-fetched from the registry. If the tag is re-pushed with malicious code or a registry is compromised, pods will pull a poisoned image. This increases vulnerability to supply chain attacks and makes auditing difficult.
   - **Recommendation**: Use immutable image digests instead of tags. Update the container spec to reference `image: <registry>/<repository>@sha256:<digest>` (e.g., `image: gcr.io/myapp/api-server@sha256:abc123def456...`). Change `imagePullPolicy` to `IfNotPresent` to leverage local caches after initial pull. Document the image digest in your deployment pipeline and automate digest updates through your CI/CD system.
