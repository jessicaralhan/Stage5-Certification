## Infrastructure (Terraform) Findings

Risk Level: **HIGH**

### Destructive Changes

No destructive changes were identified. The plan creates new resources only and does not replace or delete existing infrastructure.

### Security Exposure

❌ **HIGH**: Plaintext master password variable on production database
- **Resource**: `aws_rds_cluster.prod`
- **Exposure Type**: Credential exposure in Terraform logs, plan output, and state files
- **Current Configuration**: `master_password = var.master_password`
- **Impact**: The database master credential can be written to CI/CD logs, plan artifacts, and the Terraform state file. Anyone with read access to state gains full administrative access to the production cluster.
- **Recommendation**: Generate the password with `random_password` and manage it through AWS Secrets Manager. See Unified Recommendations for implementation details.

⚠️ **MEDIUM**: KMS key deletion window below recommended minimum
- **Resource**: `aws_kms_key.rds`
- **Exposure Type**: Accidental or malicious key deletion with reduced recovery time
- **Current Configuration**: `deletion_window_in_days = 7`
- **Impact**: If the key is scheduled for deletion, the window to cancel is 7 days. Data encrypted with that key, including production database snapshots and backups, becomes unrecoverable after the window closes. A 30-day window gives operators more time to detect and cancel an erroneous or unauthorized deletion request.
- **Recommendation**: Set `deletion_window_in_days = 30`.

### Cost Impact

- `aws_rds_cluster.prod`: Ongoing charges for RDS cluster instances, storage, and backup storage.
- `aws_db_subnet_group.prod`: No direct charge. The subnets it references may carry networking costs.
- `aws_kms_key.rds`: Monthly key charge plus per-request encryption and decryption charges. Costs scale with database and backup activity.

## Unified Recommendations

### HIGH Priority

❌ **HIGH**: Remove the plaintext master password from `aws_rds_cluster.prod`
- **Resource**: `aws_rds_cluster.prod`
- **Action**: Replace `master_password = var.master_password` with `master_password = random_password.rds.result`, and add the following to the resource block:
  ```hcl
  lifecycle {
    ignore_changes = [master_password]
  }
  ```
- **Store the credential**: Add an `aws_secretsmanager_secret` and an `aws_secretsmanager_secret_version` that holds the generated password. Set the secret value from `random_password.rds.result` after the cluster is created.
- **Required additions**: The fix references `random_password.rds`, which is not defined in the reviewed plan. Add this resource before applying:
  ```hcl
  resource "random_password" "rds" {
    length           = 32
    special          = true
    override_special = "!#$%&*()-_=+[]{}<>:?"
  }
  ```
  Exclude characters that RDS rejects (`/`, `@`, `"`, and space).
- **Important limitation**: The generated password is still written to Terraform state. Removing the variable reduces exposure in logs and plan output, but it does not eliminate state exposure. Before apply, confirm that the state backend is encrypted at rest, uses restricted IAM access, and has versioning enabled.
- **Rotation**: After apply, enable automatic rotation on the Secrets Manager secret so the credential does not remain static.

### MEDIUM Priority

⚠️ **MEDIUM**: Increase the KMS deletion window on `aws_kms_key.rds`
- **Resource**: `aws_kms_key.rds`
- **Action**: Change `deletion_window_in_days = 7` to `deletion_window_in_days = 30`.
- **Verification**: After apply, confirm with `aws kms describe-key --key-id <key-id>` that `DeletionWindowInDays` reflects the new value on the key's pending-deletion schedule.

### Process Recommendations

- **Re-run the review**: After the password and KMS changes are made, regenerate the plan and run the Terraform Safety Review again. The re-run should use a plan that includes the `random_password` resource and the Secrets Manager resources.
- **Confirm the reviewer input**: Fix the `{{remediations}}` template substitution in the adversarial reviewer step so future reviews receive populated remediation data.
- **Apply approval**: Require explicit sign-off from the database owner and a security reviewer for the production apply.
