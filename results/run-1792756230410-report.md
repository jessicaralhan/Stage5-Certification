# Infrastructure Security Review: Kubernetes Workloads

**Scope:** Kubernetes Security Review (Container Security) of the `insecure-app` workload in namespace `insecure-app`, including the cluster-scoped ClusterRole `admin-like-role` and the ClusterRoleBinding `app-admin-binding`.
**Combined Risk Level:** **CRITICAL**

The review found that the `app-sa` ServiceAccount in `insecure-app` holds cluster-admin-equivalent access through `app-admin-binding` and the wildcard ClusterRole `admin-like-role`. A compromise of the application would give an attacker control of the whole cluster. The workload also lacks a NetworkPolicy, security contexts, resource limits, and pod-level hardening, so it is not production-ready. The proposed fixes for the RBAC and NetworkPolicy findings were rejected by the reviewer as unsafe to apply directly, and several findings have no fix yet. Human review is required before any change is made. The immediate actions are to audit every binding of `admin-like-role`, remove the cluster-wide grant from `app-sa`, and restrict the workload's network access with a policy validated against its real traffic.

## Container Security (Kubernetes) Findings

Risk Level: **CRITICAL**

The `insecure-app` workload has critical RBAC exposure from a wildcard ClusterRole bound to its ServiceAccount, plus missing network policies, security contexts, and resource limits, so it is not production-ready.

### RBAC Issues

❌ **CRITICAL**: Wildcard ClusterRole grants cluster-admin-equivalent access.
- **Resource**: `ClusterRole/admin-like-role` (cluster-wide)
- **Issue**: Grants all verbs on all resources in all API groups.
- **Impact**: Any principal bound to this role can read Secrets, modify workloads, and escalate to full cluster control. Because it is cluster-scoped, every binding that references it inherits this power.
- **Fix needed**: Replace the rules with least-privilege rules. The proposed fix narrows the role to `get/list/watch` on `configmaps` in the core API group. Before applying, list every binding that references this role, because the reviewer noted other bindings or workloads may depend on it:
  ```bash
  kubectl get clusterrolebindings,rolebindings -A -o json \
    | jq -r '.items[] | select(.roleRef.name=="admin-like-role") | "\(.kind) \(.metadata.namespace // "cluster-wide")/\(.metadata.name)"'
  ```

❌ **CRITICAL**: Cluster-wide admin binding for ServiceAccount `app-sa`.
- **Resource**: `ServiceAccount/app-sa` (namespace `insecure-app`), via `ClusterRoleBinding/app-admin-binding`
- **Issue**: The ClusterRoleBinding grants `app-sa` cluster-admin-level access across all namespaces.
- **Impact**: A compromised application container can read every Secret, create privileged pods, and take over the cluster.
- **Fix needed**: Delete `ClusterRoleBinding/app-admin-binding`, then bind `app-sa` to a namespaced `Role` named `app-role` with `get/list/watch` on `configmaps` only, using a `RoleBinding` named `app-sa-binding` in `insecure-app`. Confirm first that the application does not depend on the removed permissions, since deleting the binding will break any operation that relied on it.

### Network Policies

⚠️ **HIGH**: No NetworkPolicy in namespace `insecure-app`.
- **Resource**: `Namespace/insecure-app` (affects `Deployment/insecure-app`)
- **Issue**: No policy selects the pods, so all ingress and egress is allowed by default.
- **Impact**: Any pod in the cluster can reach `insecure-app`, and the application can reach any internal service or external endpoint. This enables lateral movement from a compromised pod.
- **Fix needed**: The proposed `NetworkPolicy/insecure-app-default-deny` is **not safe to apply as written**. Its `ingress: []` blocks all inbound Service traffic, and its egress allows only DNS to `kube-system` and therefore blocks every other outbound call the application makes. Before applying, do the following:
  1. Confirm the pod labels match `app: insecure-app`.
  2. Identify the real callers of the application (for example, a frontend namespace and port) and add explicit ingress rules for those sources and ports.
  3. Identify the real outbound dependencies (databases, APIs, message queues) and add explicit egress rules for each destination and port.
  4. Keep the DNS egress rule to `kube-system` on UDP and TCP port 53.
  5. Verify in a non-production namespace before applying to `insecure-app`.

### Security Contexts

⚠️ **HIGH**: Container may run as root.
- **Resource**: `Deployment/insecure-app`, app container
- **Missing settings**: No `securityContext`, `runAsNonRoot`, or `runAsUser`.
- **Impact**: A container breakout or application compromise gives root privileges inside the container, which makes host escape easier.
- **Fix needed**: Set `runAsNonRoot: true` and a non-zero `runAsUser` (for example, `10001`) on the container. Verify that the image supports a non-root user and that the process can write to any paths it requires.

⚠️ **MEDIUM**: Writable root filesystem.
- **Resource**: `Deployment/insecure-app`, app container
- **Missing settings**: `readOnlyRootFilesystem` is not set to `true`.
- **Impact**: An attacker can modify binaries and configuration inside the container, which makes persistence easier.
- **Fix needed**: Set `readOnlyRootFilesystem: true`. Mount `emptyDir` volumes at any path the application writes to, such as `/tmp`.

⚠️ **MEDIUM**: Privilege escalation not disabled.
- **Resource**: `Deployment/insecure-app`, app container
- **Missing settings**: `allowPrivilegeEscalation` is not set to `false`.
- **Impact**: Processes can gain more privileges than their parent, for example through setuid binaries.
- **Fix needed**: Set `allowPrivilegeEscalation: false`.

### Resource Limits

⚠️ **MEDIUM**: No CPU or memory limits.
- **Resource**: `Deployment/insecure-app`, app container
- **Missing settings**: Requests are set, but `resources.limits` for CPU and memory are not.
- **Impact**: A memory leak or runaway process can exhaust the node and affect other workloads on it.
- **Fix needed**: Add `resources.limits` for CPU and memory. Size the values from observed usage, for example with `kubectl top pod` over a representative period, and keep the limits at or above the current requests.

### Pod Security

⚠️ **MEDIUM**: No pod-level seccomp profile.
- **Resource**: `Deployment/insecure-app`, pod spec
- **Missing settings**: No pod-level `securityContext`, so no `seccompProfile` is enforced.
- **Impact**: The container can make any system call the runtime permits, which expands the attack surface for kernel exploits.
- **Fix needed**: Set `spec.template.spec.securityContext.seccompProfile.type: RuntimeDefault`.

⚠️ **MEDIUM**: Linux capabilities not dropped.
- **Resource**: `Deployment/insecure-app`, app container
- **Missing settings**: `capabilities.drop` is not set.
- **Impact**: The container keeps the runtime's default capability set, which is broader than most applications need.
- **Fix needed**: Set `capabilities.drop: [ALL]` and add back only specific capabilities the application proves it needs.

⚠️ **MEDIUM**: ServiceAccount token auto-mounted.
- **Resource**: `ServiceAccount/app-sa` (namespace `insecure-app`)
- **Missing settings**: `automountServiceAccountToken` is not set to `false`.
- **Impact**: The API token is mounted into the pod even though the application likely does not call the Kubernetes API. Combined with the RBAC exposure above, this gives an attacker a ready-made credential.
