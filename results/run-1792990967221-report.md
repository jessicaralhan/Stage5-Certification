## Container Security (Kubernetes) Findings

Risk Level: **HIGH**

The `api-server` workload has solid container hardening and scoped RBAC, but lacks a namespace default-deny network policy, a seccomp profile, and token automount controls, and its DNS egress rule is broader than needed.

### RBAC Issues

❌ **LOW**: Unnecessary `list` verb on ConfigMaps
- **Resource**: Role `api-server-role` (namespace `secure-app`)
- **Issue**: The `list` verb is granted on `configmaps`, but the `resourceNames` restriction does not apply to `list` requests, so the grant is misleading and implies a scoping that does not exist.
- **Fix needed**: Remove `list` from the `configmaps` rule unless the workload requires it. Retain `get` (and `watch` only if needed) with `resourceNames` set.

### Network Policies

❌ **HIGH**: No namespace-wide default-deny
- **Namespace**: `secure-app`
- **Policy gap**: No default-deny NetworkPolicy exists. Pods without the label `app: api-server` accept and send all traffic without restriction.
- **Impact**: Any compromised or misconfigured pod in `secure-app` can reach `api-server` and any other service, and can make arbitrary outbound connections. Lateral movement is unrestricted.
- **Note**: The generated fix (`default-deny-all` with `podSelector: {}` and both `Ingress` and `Egress` policy types) is **not safe to apply as-is**. It isolates every pod in the namespace, including DNS resolution, and it does not account for `api-server`'s own traffic. See Unified Recommendations.

⚠️ **MEDIUM**: DNS egress rule is cluster-wide in scope
- **Resource**: NetworkPolicy `api-server-policy` (namespace `secure-app`)
- **Policy gap**: The DNS egress rule uses `namespaceSelector: {}` with `podSelector: k8s-app: kube-dns`, which permits UDP 53 to kube-dns pods in every namespace rather than only `kube-system`.
- **Impact**: Pods in `api-server` can send DNS queries to any namespace that runs a pod labeled `k8s-app: kube-dns`. This widens the DNS-based exfiltration and misdirection surface beyond what the workload needs.

### Security Contexts

⚠️ **MEDIUM**: seccomp profile not set
- **Resource**: Deployment `api-server` (namespace `secure-app`)
- **Missing settings**: `seccompProfile.type: RuntimeDefault` is absent at both the pod level and the `api` container level.
- **Impact**: The container runs without a syscall filter, so it can invoke any kernel syscall permitted by its capabilities. Enabling `RuntimeDefault` removes a large class of kernel attack surface with minimal compatibility risk.

### Resource Limits

⚠️ **LOW**: Unbounded ephemeral storage
- **Resource**: Deployment `api-server`, container `api`
- **Missing limits**:
  - `emptyDir` volume `tmp` has no `sizeLimit`.
  - `emptyDir` volume `cache` has no `sizeLimit`.
  - Container `api` has no `ephemeral-storage` request or limit.
- **Impact**: A runaway process or a log/cache growth event can consume unbounded node disk, which can cause node-level eviction or disruption for co-located workloads.

### Pod Security

⚠️ **MEDIUM**: Service account token auto-mounted in the pod
- **Resource**: Deployment `api-server` (pod spec)
- **Issue**: `automountServiceAccountToken: false` is not set, so the Kubernetes API token is mounted into the container even though the workload does not need API access.
- **Impact**: A compromised container can use the token to query or act on the Kubernetes API within the permissions of `api-server-role`.

⚠️ **MEDIUM**: Service account auto-mounts tokens into every consuming pod
- **Resource**: ServiceAccount `api-server` (namespace `secure-app`)
- **Issue**: `automountServiceAccountToken: false` is not set on the ServiceAccount, so its token is auto-mounted into every pod that uses it, including pods added later.
- **Impact**: Token exposure extends beyond the intended Deployment to any future workload bound to this ServiceAccount.
