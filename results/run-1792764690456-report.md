## Findings by Domain

### Kubernetes (Container Security)

Risk Level: **HIGH**

The `api-server` workload's container settings are sound. The gaps sit at the namespace network boundary and in several pod-level settings.

#### RBAC Issues

**MEDIUM: Unscoped ConfigMap listing in `api-server-role`**
- **Resource:** Role `api-server-role` (namespace `secure-app`)
- **Role binding:** Bound to the `api-server` ServiceAccount
- **Issue:** The `list` verb on `configmaps` has no `resourceNames` constraint, so the ServiceAccount can list every ConfigMap in `secure-app`, not only `api-config`.
- **Why it matters:** ConfigMaps in the namespace may hold settings, endpoints, or other sensitive configuration that the API does not need. A compromised api-server pod could enumerate all of them.
- **Fix needed:** Replace the broad `list` with a `get` rule scoped to `resourceNames: ["api-config"]` if the application fetches the ConfigMap by name. Note that Kubernetes RBAC does not reliably restrict `list` or `watch` by `resourceNames`, so if the application truly requires listing, the permission must be re-evaluated rather than assumed to be constrained.

#### Network Policies

**HIGH: No default-deny baseline in `secure-app`**
- **Resource:** Namespace `secure-app`, NetworkPolicy `api-server-policy`
- **Policy gap:** No default-deny policy exists. Pods not selected by `api-server-policy`, including any frontend or database pods, accept and send unrestricted traffic.
- **Impact:** Any compromised pod in the namespace can reach any other pod and any external destination. Lateral movement is unrestricted.
- **Required action (not the generated fix as-is):**
  1. Inventory actual traffic between frontend, `api-server`, and database pods, including sidecar, init-container, and service-mesh traffic. The reviewer noted these flows are unverified.
  2. Add explicit allow policies first. For example, create a NetworkPolicy that selects pods labeled `app: api-server` and permits ingress only from pods carrying the frontend workload's labels, on the TCP port the `api-server` container exposes. Confirm the labels and port from the live Deployment and Service manifests.
  3. Add allow rules for each other workload's required flows (for example, `api-server` to the database on its service port).
  4. Only then apply `default-deny-all` (`podSelector: {}`, `policyTypes: [Ingress, Egress]`) and `allow-dns-egress`, and validate in a non-production namespace or staging first.

**LOW: Overly broad DNS egress in `api-server-policy`**
- **Resource:** NetworkPolicy `api-server-policy` (namespace `secure-app`)
- **Policy gap:** The DNS egress rule uses `namespaceSelector: {}`, which permits UDP 53 to kube-dns pods in any namespace rather than only `kube-system`.
- **Impact:** Pods can send DNS queries to DNS-capable pods in other namespaces, which widens the exfiltration and discovery surface.
- **Fix needed:** Restrict the rule to `kubernetes.io/metadata.name: kube-system` with `k8s-app: kube-dns`. Note that the generated `allow-dns-egress` policy does not remove this rule. NetworkPolicies are additive, so the broad allowance remains in effect until `api-server-policy` itself is edited.

#### Security Contexts

**MEDIUM: Missing seccomp profile**
- **Resource:** Deployment `api-server` (namespace `secure-app`)
- **Missing setting:** Pod-level `securityContext.seccompProfile.type` is not set to `RuntimeDefault`.
- **Impact:** The pod does not meet the restricted Pod Security Standard, and the container runs without the default syscall filter.
- **Fix needed:** Add the following under `spec.template.spec.securityContext`:
  ```yaml
  seccompProfile:
    type: RuntimeDefault
  ```

#### Resource Limits

No findings. The `api-server` container's resource bounds were assessed as part of the baseline hardening and no issues were reported.

#### Pod Security

**MEDIUM: API token automatically mounted**
- **Resource:** ServiceAccount `api-server` (namespace `secure-app`)
- **Issue:** `automountServiceAccountToken` is not set to `false`, so the API token is mounted into `api-server` pods even when the application does not call the Kubernetes API.
- **Impact:** A compromised container can use the token to query the API within the permissions of `api-server-role`.
- **Fix needed:** Set `automountServiceAccountToken: false` on the ServiceAccount. If the application does require API access, keep the token mounted and rely on the RBAC scoping fix above.

**LOW: Mutable image tag**
- **Resource:** Deployment `api-server` (namespace `secure-app`)
- **Issue:** The container image `api-server:v1.2.3` uses a mutable tag with no registry or digest pinning.
- **Impact:** The tag can be repointed to a different image without a manifest change, which weakens supply-chain integrity.
- **Fix needed:** Pin the image to its full registry path and immutable digest (`<registry>/api-server@sha256:<digest>`) and record the digest in the release process.
