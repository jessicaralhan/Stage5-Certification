## Container Security (Kubernetes) Findings

**Risk Level: CRITICAL**

Production deployment exhibits critical RBAC misconfigurations granting cluster-admin privileges and high-severity security context vulnerabilities with no network isolation.

### RBAC Issues

❌ **CRITICAL**: ClusterRole `admin-like-role` grants unrestricted cluster-wide access
   - **Resource Kind**: ClusterRole
   - **Resource Name**: `admin-like-role`
   - **Scope**: Cluster-wide
   - **Issue**: ClusterRole grants wildcard permissions on all API groups (`*`), resources (`*`), and verbs (`*`), equivalent to cluster-admin access
   - **Impact**: Any ServiceAccount bound to this role has unrestricted permissions to create, modify, and delete any Kubernetes resource across all namespaces, including RBAC rules themselves
   - **Severity**: CRITICAL

❌ **CRITICAL**: ClusterRoleBinding `app-admin-binding` assigns cluster-admin privileges to application service account
   - **Resource Kind**: ClusterRoleBinding
   - **Resource Name**: `app-admin-binding`
   - **Subject**: ServiceAccount `app-sa` in namespace `insecure-app`
   - **Issue**: ClusterRoleBinding binds the overly permissive `admin-like-role` to the `app-sa` ServiceAccount, granting cluster-wide admin privileges to the running application
   - **Impact**: The application container inherits cluster-admin permissions; a vulnerability or compromise within the application grants an attacker complete cluster control
   - **Severity**: CRITICAL

### Security Contexts

❌ **HIGH**: Deployment `insecure-app` lacks pod-level securityContext
   - **Resource Kind**: Deployment
   - **Resource Name**: `insecure-app`
   - **Namespace**: `insecure-app`
   - **Issue**: Pod spec lacks a securityContext; container will run as root with all capabilities by default
   - **Impact**: Containers execute with UID 0 (root) and retain all Linux capabilities (CAP_SYS_ADMIN, CAP_NET_ADMIN, etc.), enabling privilege escalation and system-level attacks
   - **Severity**: HIGH

❌ **HIGH**: Container `app` in Deployment `insecure-app` runs as root
   - **Resource Kind**: Deployment
   - **Resource Name**: `insecure-app`
   - **Container Name**: `app`
   - **Namespace**: `insecure-app`
   - **Issue**: Container does not specify `runAsNonRoot: true`, allowing execution as root user (UID 0)
   - **Impact**: Root-level execution increases blast radius of container escape or application vulnerability; attacker gains host-level capabilities
   - **Severity**: HIGH

❌ **HIGH**: Container `app` in Deployment `insecure-app` lacks read-only filesystem enforcement
   - **Resource Kind**: Deployment
   - **Resource Name**: `insecure-app`
   - **Container Name**: `app`
   - **Namespace**: `insecure-app`
   - **Issue**: Container lacks `readOnlyRootFilesystem: true`, permitting runtime modification of the root filesystem
   - **Impact**: Compromised application can install persistence mechanisms, malware, or backdoors directly to the container layer; detection and forensics are impeded
   - **Severity**: HIGH

### Network Policies

❌ **HIGH**: Deployment `insecure-app` has no NetworkPolicy enforcement
   - **Resource Kind**: Deployment
   - **Resource Name**: `insecure-app`
   - **Namespace**: `insecure-app`
   - **Issue**: No NetworkPolicy is defined; pod accepts inbound and outbound traffic from all sources by default
   - **Impact**: Application receives unfiltered traffic from all pods and external sources; no egress controls prevent data exfiltration or lateral movement to other services

### Verdict: **ESCALATE**

**Reasoning**: The provided remediation fixes address individual issues but exhibit incomplete coordination and untested integration:

1. **Fix 1 (ClusterRole scoping)** correctly restricts the `admin-like-role` to read-only access on pods, deployments, and services; however, it does not validate whether the application's actual operational requirements align with this reduced scope.

2. **Fix 2 (RoleBinding downscope)** converts the cluster-wide `ClusterRoleBinding` to a namespace-scoped `RoleBinding` and introduces a new Role `app-reader-role` granting only configmaps and secrets read access. This introduces a **breaking change**: the permissions in Fix 1 (pods/logs, deployments, services) and Fix 2 (configmaps, secrets) do not overlap, risking silent operational failure if the application requires mixed access patterns.

3. **Fix 3 (Security contexts)** applies `readOnlyRootFilesystem: true` with an `/tmp` emptyDir workaround but does not validate whether the application writes to additional runtime directories (e.g., `/var`, `/home`) that would then fail under read-only constraints.

All three fixes directly modify production RBAC and security contexts with no demonstrated testing against application workload requirements. The misalignment between Fix 1 and Fix 2 role definitions indicates incomplete coordination. **Human reconciliation is required** to:
- Audit application code and runtime behavior to determine actual RBAC requirements
- Verify that scoped permissions align with all application workflows
- Test security context changes in staging before production rollout
- Validate NetworkPolicy implementation against application connectivity needs

### Priority 1: CRITICAL – Remediate RBAC Misconfigurations (Immediate)

1. **Revoke cluster-admin-equivalent permissions from `app-sa`**
   - **Action**: Delete or replace the existing `ClusterRoleBinding` `app-admin-binding` immediately to prevent cluster-wide compromise
   - **Implementation**: 
     ```bash
     kubectl delete clusterrolebinding app-admin-binding
     ```
   - **Validation**: Confirm the ServiceAccount is no longer bound to `admin-like-role`
   - **Timeline**: Within 24 hours; coordinate with application owners to test during maintenance window

2. **Audit and restrict the `admin-like-role` ClusterRole**
   - **Action**: Review application logs and code to identify minimum required API groups, resources, and verbs
   - **Recommended approach**: Apply the principle of least privilege by binding a namespace-scoped Role (not ClusterRole) with only required permissions
   - **Example minimal Role** (requires application-specific validation):
     ```yaml
     apiVersion: rbac.authorization.k8s.io/v1
     kind: Role
     metadata:
       name: app-minimal-role
       namespace: insecure-app
     rules:
     - apiGroups: [""]
       resources: ["configmaps"]
       verbs: ["get", "list"]
     - apiGroups: [""]
       resources: ["secrets"]
       verbs: ["get"]
     ```
   - **Timeline**: Complete within 48 hours; include application development team review

3. **Replace ClusterRoleBinding with namespace-scoped RoleBinding**
   - **Action**: Create a new RoleBinding in the `insecure-app` namespace binding `app-sa` to the restricted Role
   - **Validation**: Run application integration tests to confirm all required API operations succeed

### Priority 2: HIGH – Enforce Security Contexts (Within 1 Week)

4. **Add pod and container security contexts to `insecure-app` Deployment**
   - **Action**: Apply the following security context settings to both pod and container levels
   - **Implementation**:
     ```yaml
     spec:
       securityContext:
         runAsNonRoot: true
         runAsUser: 1000
         fsGroup: 2000
       containers:
       - name: app
         securityContext:
           allowPrivilegeEscalation: false
           runAsNonRoot: true
           runAsUser: 1000
           readOnlyRootFilesystem: true
           capabilities:
             drop: ["ALL"]
         volumeMounts:
         - name: tmp
           mountPath: /tmp
         - name: var-cache
           mountPath: /var/cache
       volumes:
       - name: tmp
         emptyDir: {}
       - name: var-cache
         emptyDir: {}
     ```
   - **Pre-deployment testing**: 
     - Deploy to non-production environment and validate application startup
     - Verify application does not require write access to additional paths (check logs for permission denied errors)
     - Monitor for 24–48 hours for runtime failures
   - **Staging validation**: Confirm all application features (logging, data processing, cache operations) function under read-only root filesystem
   - **Timeline**: Test in staging immediately; deploy to production after successful validation

5. **Identify and mount writable volumes for application writes**
   - **Action**: Audit application source code or run logs to determine all write paths (beyond `/tmp`)
   - **Common paths to check**: `/var`, `/home`, `/app/data`, `/logs`
   - **Implementation**: Create `emptyDir` volumes for each required path and mount them (as done for `/tmp` above)
   - **Validation**: Confirm application-written files persist during pod lifetime and are cleaned on pod termination

### Priority 3: HIGH – Implement Network Policies (Within 1 Week)

6. **Create a NetworkPolicy for the `insecure-app` namespace**
   - **Action**: Restrict inbound and outbound traffic to only required sources/destinations
