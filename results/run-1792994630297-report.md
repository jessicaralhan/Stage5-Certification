## Unified Recommendations

### CRITICAL

1. **Block the current plan.** Do not apply any plan that shows `destroy_and_recreate` for `aws_rds_cluster.prod`.
2. **Revert `db_subnet_group_name`** in the `aws_rds_cluster.prod` configuration to the subnet group name currently recorded in Terraform state. Confirm with `terraform plan` that the cluster shows no replacement.
3. **Add `lifecycle { prevent_destroy = true }`** to `aws_rds_cluster.prod`. This makes Terraform refuse any plan that would destroy the cluster.
4. **If the subnet group must change**, follow this sequence:
   - Create the new subnet group as its own resource.
   - Take a manual snapshot of `aws_rds_cluster.prod`.
   - Schedule a maintenance window and communicate the expected endpoint impact.
   - Migrate using a controlled approach, such as restoring from the snapshot into a new cluster and cutting over application connections.
   - Confirm the plan shows the expected actions before applying.

### MEDIUM

5. **Set `deletion_protection = true`** on `aws_rds_cluster.prod`. This can be applied in-place without replacing the cluster and blocks accidental deletion at the AWS layer.
6. **Set `vpc_security_group_ids`** on `aws_rds_cluster.prod` to a dedicated security group that allows inbound traffic only on the database port from the specific application security groups that require access. This update can be applied in-place.
7. **Set `enabled_cloudwatch_logs_exports`** on `aws_rds_cluster.prod` to the log types supported by the engine, such as `["audit", "error"]` for MySQL-family engines or `["postgresql"]` for PostgreSQL. This update can be applied in-place. Confirm the engine type before setting the value.

### LOW

8. **Replace the `admin` master username** only as part of a planned migration. In Terraform, `master_username` is a replacement-forcing attribute on RDS clusters, so changing it in the current configuration would trigger the same destroy-and-recreate risk. Prefer `manage_master_user_password = true` so the password is managed by AWS Secrets Manager, and handle the username change with the migration in recommendation 4.

### Cost Monitoring

9. **Review the 30-day backup retention** against recovery point objectives and budget. Confirm that the retention period is required and set an AWS Budgets alert on backup storage.
10. **Plan for instance costs** before adding `aws_rds_cluster_instance` resources, and include them in the production budget forecast.
11. **Track KMS usage** for `aws_kms_key.rds` in Cost Explorer to confirm that per-request charges match expected application traffic.
