## Access Control (IAM) Findings

Risk Level: **CRITICAL**

The policy grants unrestricted administrative access to all actions and resources in production with no MFA, condition, or session constraints, which is a critical least-privilege failure.

### Overly Broad Permissions

❌ **CRITICAL**: Wildcard action and resource grant in `AllowEverything`
- **Principal**: Not identified in the policy document (must be determined from the attachment)
- **Current scope**: `Action: "*"`, `Resource: "*"`; permits every AWS API action, including `iam:*`, `kms:*`, and `ec2:AuthorizeSecurityGroupIngress`
- **Why it matters**: The principal can grant itself further privileges, disable security controls, or delete production data without restriction. Any compromise of its credentials gives full account control.
- **Least-privilege target**: Replace with the enumerated read-scoped actions in the generated fix (`rds:DescribeDBInstances`, `rds:DescribeDBClusters`, `ec2:DescribeInstances`, `ec2:DescribeSecurityGroups`, `kms:DescribeKey`, `kms:Decrypt`, `s3:GetObject`, `logs:GetLogEvents`). Write, delete, and all IAM actions are removed.

⚠️ **LOW**: Principal may be unused
- **Principal**: Not identified in the policy document
- **Current scope**: Unrestricted, with no recorded usage data
- **Why it matters**: An unrestricted policy on an inactive principal is unnecessary attack surface.
- **Least-privilege target**: Check last-used data for the principal. If it has been inactive, detach the policy and remove the principal.

### Missing Resource Boundaries

❌ **CRITICAL**: `AllowEverything` has no ARN scoping
- **Policy**: `AllowEverything` statement
- **Affected resources**: All production RDS databases, KMS keys, security groups, and other account resources
- **Why it matters**: Access is not limited to any named production asset, so a single credential exposes the entire environment.
- **Recommendation**: Scope resource-level actions to named ARNs (for example, `arn:aws:rds:us-east-1:123456789012:db:prod-*`, `arn:aws:kms:us-east-1:123456789012:key/1a2b3c4d-5e6f-7a8b-9c0d-1e2f3a4b5c6d`, `arn:aws:s3:::prod-app-data/*`). Resources outside this list are denied by default.

⚠️ **Implementation caveat**: `ec2:Describe*` and most `rds:Describe*` actions do not support resource-level permissions. Scoping them to ARNs has no effect. Place these actions in a separate statement with `Resource: "*"`, limited by the MFA and source-IP conditions described below.

### Missing MFA/Conditions

❌ **CRITICAL**: No MFA requirement on destructive and privilege-escalating actions
- **Principal**: Not identified in the policy document
- **Gap**: No `aws:MultiFactorAuthPresent` condition; `iam:DeleteUser`, `kms:ScheduleKeyDeletion`, and `iam:AttachUserPolicy` can run without MFA
- **Why it matters**: Credentials obtained through phishing or key leakage can perform irreversible actions immediately.
- **Recommendation**: Add `"Bool": {"aws:MultiFactorAuthPresent": "true"}` and `"NumericLessThan": {"aws:MultiFactorAuthAge": "3600"}` to the scoped statement.

❌ **CRITICAL**: No source network or time restriction
- **Principal**: Not identified in the policy document
- **Gap**: No `aws:SourceIp`, time-based, or source-tag condition; access is unrestricted by origin in production
- **Why it matters**: Credentials can be used from any location on the internet.
- **Recommendation**: Add `"IpAddress": {"aws:SourceIp": ["<corporate egress CIDR>"]}`. The generated fix uses `203.0.113.0/24`, which must be replaced with the verified corporate egress range before deployment. Note that `aws:SourceIp` does not match requests made through VPC endpoints or by AWS service principals. Use `aws:SourceVpce` or `aws:ViaAWSService` in a separate statement for those callers.

### Session Credential Issues

⚠️ **MEDIUM**: No session duration limit
- **Policy**: `AllowEverything`, plus the role's `MaxSessionDuration` setting
- **TTL/scope problem**: Any credentials issued to the principal carry full administrative access for the default or maximum session lifetime.
