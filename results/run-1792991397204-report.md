## Access Control (IAM) Findings

Risk Level: **CRITICAL**

The policy grants unrestricted administrator access to all actions on all resources with no MFA, source, or session constraints, which is unacceptable for a production environment.

### Overly Broad Permissions

❌ **CRITICAL**: Statement `AllowEverything` grants every AWS API action on every resource.
- **Principal**: Not identified in the policy document. Must be determined before remediation.
- **Current scope**: `Action: "*"`, `Resource: "*"`
- **Issue**: Permits every AWS API action, including IAM actions that enable privilege escalation and destructive changes in production.
- **Least-privilege target**: Remove `AllowEverything`. Replace it with a scoped statement limited to the operations the principal actually performs (for example, `ec2:DescribeInstances`, `ec2:DescribeSecurityGroups`, `s3:GetObject`, `s3:PutObject` on the application artifact bucket, and `logs:*` writes to the application log group).
- **Note on the proposed fix**: The replacement statement `ScopedProdOperations` in the generated fix still grants `s3:PutObject` and `logs:PutLogEvents` without an MFA condition. It does not fully achieve least privilege until the issues in the MFA section are corrected.

### Missing Resource Boundaries

❌ **CRITICAL**: Statement `AllowEverything` applies to all account resources.
- **Affected resources**: All resources in the account, including databases, KMS keys, security groups, and other accounts' resources reachable through trust relationships.
- **Issue**: No ARN scoping exists, so the principal can read, modify, or delete any resource type.
- **Required correction**:
  - Scope mutating actions to explicit ARNs, such as `arn:aws:s3:::prod-app-artifacts/*` and `arn:aws:logs:us-east-1:<account-id>:log-group:/prod/app/*`.
  - Do not scope `ec2:Describe*` or `cloudwatch:GetMetricData` to specific ARNs. These actions generally do not support resource-level permissions and must use `"Resource": "*"`. The proposed ARN list would break them.
  - Confirm the account ID. The proposed ARNs use `123456789012`, which must be verified against the real account before use.
  - Remove the unresolved reference `"<see resource_scoping fix>"` from `ScopedProdOperations` and substitute the final resource list.

### Missing MFA/Conditions

❌ **CRITICAL**: Create, delete, and modify actions have no MFA requirement.
- **Principal**: Not identified in the policy document.
- **Gap**: No `aws:MultiFactorAuthPresent` condition on mutating actions.
- **Issue with proposed fix**: The fix adds a `RequireMFAForMutations` statement using `BoolIfExists` on `aws:MultiFactorAuthPresent`. `BoolIfExists` evaluates to true when the key is absent, so the condition does not enforce MFA. In addition, `s3:PutObject` and `logs:PutLogEvents` remain granted without MFA in the unconditioned `ScopedProdOperations` statement. The MFA control can therefore be bypassed entirely.
- **Required correction**: Remove `s3:PutObject` and `logs:PutLogEvents` from the unconditioned statement. Grant them only in a statement that uses `Bool` (not `BoolIfExists`) with `"aws:MultiFactorAuthPresent": "true"` and `NumericLessThan` on `aws:MultiFactorAuthAge` set to `3600`.

❌ **HIGH**: No contextual conditions restrict where, when, or how permissions are used.
- **Gap**: No `aws:SourceIp`, `aws:SourceVpce`, `aws:RequestedRegion`, or `aws:PrincipalTag` conditions.
- **Impact**: The permissions can be exercised from any network location, in any region, by any tagged or untagged session.
- **Required correction**: Add `aws:RequestedRegion` restricted to `us-east-1` (or the approved regions) and, where workloads run in known networks, `aws:SourceVpce` or `aws:SourceIp`. Validate that global services used by the principal are handled correctly by the region condition.
