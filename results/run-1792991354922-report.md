## Executive Summary

This review covered the Kubernetes manifests for the `insecure-app` workload in the `insecure-app` namespace, including the `app-sa` ServiceAccount, the `admin-like-role` ClusterRole, the `app-admin-binding` ClusterRoleBinding, and the `insecure-app` Deployment. The analyzer identified 12 findings: 2 CRITICAL, 4 HIGH, 4 MEDIUM, and 2 LOW. The most serious issue is that `app-sa` holds cluster-wide wildcard permissions through `admin-like-role` and `app-admin-binding`, so a compromise of the application would give an attacker full control of the cluster. The workload also has no NetworkPolicy, may run as root, permits privilege escalation, and has no resource limits. ## Findings by Domain

### RBAC Issues

❌ **CRITICAL**: Wildcard ClusterRole grants cluster-admin-equivalent privileges.
- **Resource**: `admin-like-role` (ClusterRole, cluster-wide)
- **Issue**: Grants wildcard `apiGroups`, `resources`, and `verbs`.
- **Impact**: Any principal bound to this role can read, modify, or delete any resource in the cluster, including Secrets in every namespace.
- **Fix needed**: Delete the ClusterRole after replacing its bindings with a namespaced Role. The generated fix does not delete it (see Verdict section).

❌ **CRITICAL**: Cluster-wide binding grants the wildcard role to the application's ServiceAccount.
- **Resource**: `app-admin-binding` (ClusterRoleBinding, cluster-wide)
- **Issue**: Binds `admin-like-role` to `ServiceAccount/app-sa` in `insecure-app`. The analyzer lists this resource kind as ClusterRole, but its description and the fix comment identify it as a ClusterRoleBinding. The manifest should be confirmed before remediation.
- **Impact**: The application runs with cluster-wide admin rights, so a single application compromise becomes full cluster compromise.
- **Fix needed**: Delete the ClusterRoleBinding and replace it with a namespaced RoleBinding to a least-privilege Role.

⚠️ **HIGH**: ServiceAccount holds cluster-wide wildcard permissions.
- **Resource**: `app-sa` (ServiceAccount, `insecure-app`)
- **Issue**: Inherits cluster-wide wildcard access through `app-admin-binding`.
- **Impact**: Workload compromise yields full cluster control. The blast radius extends to every namespace.
- **Fix needed**: Re-scope permissions to a namespaced Role limited to the resources the application actually uses. The generated fix proposes `configmaps` with `get`, `list`, and `watch`, but this is a guess and must be verified against the application's real API calls.

### Network Policies

⚠️ **HIGH**: No NetworkPolicy in the namespace.
- **Namespace**: `insecure-app`
- **Policy gap**: No NetworkPolicy selects pods in `insecure-app`, so all ingress and egress is allowed by default.
- **Impact**: A compromised pod can reach any service in the cluster and any external endpoint. It can also be reached from any pod in the cluster.
- **Fix needed**: The generated policy `insecure-app-default-deny-allow` selects `app: insecure-app` and allows ingress only from `ingress-nginx` on TCP 8080 and egress only to `kube-system` on TCP and UDP 53. Its assumed ports, namespaces, and labels must be confirmed against the actual Service, Ingress, and dependency map before applying. Without that verification, it may break legitimate traffic (for example, to databases, external APIs, or message queues). The policy also restricts only pods matching `app: insecure-app`; it does not establish namespace-wide default deny.

### Security Contexts

❌ **CRITICAL/HIGH**: Container may run as root.
- **Resource**: `insecure-app` (Deployment, container `app`)
- **Missing settings**: No `securityContext`, no `runAsNonRoot: true`, no `runAsUser`.
- **Severity**: HIGH
- **Impact**: A container breakout would land on the node with root-level privileges.

⚠️ **HIGH**: Privilege escalation is permitted.
- **Resource**: `insecure-app` (Deployment, container `app`)
- **Missing setting**: `allowPrivilegeEscalation: false`
- **Impact**: Processes can gain more privileges than their parent, for example through setuid binaries.

⚠️ **MEDIUM**: Writable root filesystem.
- **Resource**: `insecure-app` (Deployment, container `app`)
- **Missing setting**: `readOnlyRootFilesystem: true`
- **Impact**: An attacker can modify binaries and configuration inside the container. Writable paths should be provided as explicit `emptyDir` volumes.

🔹 **LOW**: Mutable image reference.
- **Resource**: `insecure-app` (Deployment, container `app`)
- **Issue**: Uses `app:latest` with `imagePullPolicy: Always`.
- **Impact**: Deployments are not reproducible, and a tampered tag is pulled automatically.
- **Fix needed**: Pin to an immutable digest (`app@sha256:...`) or a versioned tag, and use `IfNotPresent` or digest pinning.

### Resource Limits

⚠️ **MEDIUM**: CPU and memory limits are missing.
- **Resource**: `insecure-app` (Deployment, container `app`)
- **Issue**: Requests are set, but no `limits` are defined.
- **Impact**: The container can consume unbounded CPU and memory and starve other workloads on the node, which can cause a noisy-neighbor or denial-of-service condition.
- **Fix needed**: Add limits based on observed p95 or p99 usage. Set the memory limit at or slightly above the observed peak to avoid OOM kills.

### Pod Security

⚠️ **MEDIUM**: No pod-level securityContext and no seccomp profile.
- **Resource**: `insecure-app` (Deployment, pod template)
- **Missing settings**: Pod-level `securityContext` and `seccompProfile`.
- **Impact**: No syscall filtering is applied, which expands the kernel attack surface available to a compromised process.
