## Container Security (Kubernetes) Findings

**Risk Level: CRITICAL**

Production deployment has critical RBAC misconfigurations granting cluster-admin privileges to a service account, combined with containers running as root without resource limits or network policies.

### RBAC Issues

❌ **CRITICAL**: ClusterRole `admin-like-role` grants unrestricted cluster access
   - **Resource**: `admin-like-role` (ClusterRole, cluster-wide)
   - **Issue**: ClusterRole grants wildcard permissions (`*`) on all API groups, resources, and verbs
   - **Impact**: Any pod using this role can perform any action on any Kubernetes resource cluster-wide, equivalent to cluster-admin access
   - **Recommendation**: Replace with minimally scoped ClusterRole containing only required verbs and API groups. Example: limit to `["get", "list", "watch"]` on specific resource kinds like `pods`, `services`, `deployments` in relevant API groups

❌ **CRITICAL**: ClusterRoleBinding `app-admin-binding` binds overly permissive role to application service account
   - **Resource**: `app-admin-binding` (ClusterRoleBinding, cluster-wide)
   - **Binding**: Attaches `admin-like-role` to ServiceAccount `app-sa` in namespace `insecure-app`
   - **Issue**: Application gains unrestricted cluster access through binding to wildcard-permissioned role
   - **Impact**: Application compromise results in complete cluster compromise; attacker can create/modify/delete any resource, steal secrets, pivot to other namespaces
   - **Recommendation**: (1) Immediately replace `admin-like-role` with least-privilege role containing only required operations; (2) Use RoleBinding scoped to `insecure-app` namespace instead of ClusterRoleBinding where possible; (3) Audit all existing ClusterRoleBindings to ServiceAccounts in application namespaces

### Security Contexts

❌ **HIGH**: Deployment `insecure-app` lacks pod-level securityContext
   - **Resource**: `insecure-app` (Deployment, namespace `insecure-app`)
   - **Issue**: Pod spec does not define securityContext; container will run with unrestricted privileges
   - **Impact**: Container runs as root (UID 0) with full filesystem write access and capability to execute privileged operations
   - **Recommendation**: Add pod-level securityContext:
     ```yaml
     securityContext:
       runAsNonRoot: true
       runAsUser: 1000
       fsGroup: 2000
       seccompProfile:
         type: RuntimeDefault
     ```

❌ **HIGH**: Container `app` in Deployment `insecure-app` has no runAsNonRoot constraint
   - **Resource**: `insecure-app` (Deployment, namespace `insecure-app`)
   - **Container**: `app`
   - **Issue**: Container has no explicit `runAsUser` and no `runAsNonRoot: true` enforcement; defaults to root (UID 0)
   - **Impact**: Container runs as root, enabling direct filesystem modification, privilege escalation, and host access if combined with other vulnerabilities
   - **Recommendation**: Add container-level securityContext: `runAsNonRoot: true`, `runAsUser: 1000`, `allowPrivilegeEscalation: false`

❌ **MEDIUM**: Container `app` in Deployment `insecure-app` does not set readOnlyRootFilesystem
   - **Resource**: `insecure-app` (Deployment, namespace `insecure-app`)
   - **Container**: `app`
   - **Issue**: Root filesystem is writable; container can modify system files, plant malware, or degrade host security
   - **Impact**: Attacker can persist malicious changes to container filesystem; supply chain attack surface increases
   - **Recommendation**: Add `readOnlyRootFilesystem: true` to container securityContext. Mount ephemeral or persistent volumes at `/tmp` and `/var/log` if application requires write access to specific paths

### Resource Limits

❌ **HIGH**: Container `app` in Deployment `insecure-app` has no resource limits
   - **Resource**: `insecure-app` (Deployment, namespace `insecure-app`)
   - **Container**: `app`
   - **Issue**: Container has resource `requests` defined but no corresponding `limits`; memory and CPU consumption is unbounded
   - **Impact**: Runaway container can consume all cluster resources, causing denial of service to other workloads and potential node crashes
   - **Recommendation**: Add resource limits:
     ```yaml
     resources:
       requests:
         memory: "256Mi"
         cpu: "250m"
       limits:
         memory: "512Mi"
         cpu: "500m"
     ```
     Adjust values based on application profiling; limits should be 1.5–2× requests

### Network Policies

❌ **HIGH**: Namespace `insecure-app` has no NetworkPolicy; pods accept all traffic
   - **Resource**: Deployment `insecure-app` (namespace `insecure-app`)
   - **Issue**: No NetworkPolicy exists in namespace; pod accepts all ingress and egress traffic by default
   - **Impact**: Lateral movement from compromised pods in other namespaces; uncontrolled egress enables data exfiltration and command-and-control communication
   - **Recommendation**: Implement NetworkPolicy to restrict traffic:
     ```yaml
     apiVersion: networking.k8s.io/v1
     kind: NetworkPolicy
     metadata:
       name: insecure-app-policy
       namespace: insecure-app
     spec:
       podSelector:
         matchLabels:
           app: insecure-app
       policyTypes:
         - Ingress
         - Egress
       ingress:
         - from:
           - namespaceSelector:
               matchLabels:
                 name: ingress-nginx
           ports:
           - protocol: TCP
             port: 8080
       egress:
         - to:
           - podSelector:
               matchLabels:
                 app: database
           ports:
           - protocol: TCP
             port: 5432
         - to:
           - namespaceSelector: {}
             podSelector:
               matchLabels:
                 k8s-app: kube-dns
           ports:
           - protocol: UDP
             port: 53
     ```
     Tailor ingress sources and egress destinations to actual application requirements

### Pod Security

❌ **MEDIUM**: Deployment `insecure-app` pod spec lacks explicit pod-level securityContext enforcement
   - **Resource**: `insecure-app` (Deployment, namespace `insecure-app`)
   - **Issue**: Pod spec does not explicitly set `hostNetwork`, `hostPID`, or `hostIPC` to false; no pod-level securityContext defined
   - **Impact**: While Kubernetes defaults are safe, explicit enforcement ensures cluster-wide policy compliance and prevents accidental misconfigurations
   - **Recommendation**: Add explicit pod securityContext (see Security Contexts section above) and ensure cluster-wide Pod Security Standards or Pod Security Policy enforcement is active

❌ **LOW**: Container image in Deployment `insecure-app` uses `latest` tag
   - **Resource**: `insecure-app` (Deployment, namespace `insecure-app`)
   - **Container**: `app`
   - **Issue**: Image tag is `latest` with `imagePullPolicy: Always`; deployment will pull unpredictable image versions on each pod restart
   - **Impact**: Supply chain risk; attackers who compromise image registry can inject malicious code; uncontrolled image updates may introduce vulnerabilities or incompatibilities
   - **Recommendation**: Replace `latest` tag with specific semantic version (e.g., `v1.2.3`). Change `imagePullPolicy` to `IfNotPresent` or implement image pull-through cache with vulnerability scanning
