## Container Security (Kubernetes) Findings

Risk Level: **CRITICAL**

The `insecure-app` workload contains a critical cluster-admin-equivalent RBAC grant, no network segmentation, and missing hardening controls. It is not safe for production deployment.

### RBAC Issues

❌ **CRITICAL**: Cluster-admin-equivalent ClusterRole
- **Resource**: ClusterRole `admin-like-role` (cluster-wide)
- **Issue**: Grants wildcard `apiGroups`, `resources`, and `verbs`, which is equivalent to `cluster-admin`.
- **Impact**: Any principal bound to this role can read all secrets, modify workloads in every namespace, create privileged pods, and alter RBAC itself.
- **Fix status**: The proposed fix creates a new namespaced Role `app-reader` but does **not** remove or modify `admin-like-role`. The privileged role remains in place.
- **Recommendation**: Delete `admin-like-role` after confirming no other subjects depend on it (`kubectl get clusterrolebindings,rolebindings -A -o wide | grep admin-like-role`).

❌ **CRITICAL**: Cluster-wide admin binding on ServiceAccount
- **Resource**: ServiceAccount `app-sa` (namespace `insecure-app`), via ClusterRoleBinding `app-admin-binding`
- **Issue**: The ClusterRoleBinding grants `admin-like-role` cluster-wide to `app-sa`, so the application can control the entire cluster.
- **Impact**: A single application compromise (for example, remote code execution in `insecure-app`) becomes full cluster takeover.
- **Fix status**: The proposed RoleBinding `app-sa-reader` adds a least-privilege grant but leaves `app-admin-binding` active.
- **Recommendation**: Delete ClusterRoleBinding `app-admin-binding` as part of the same change window as the `admin-like-role` removal. Then apply the `app-reader` Role and `app-sa-reader` RoleBinding. Verify with `kubectl auth can-i --list --as=system:serviceaccount:insecure-app:app-sa -n insecure-app`.

### Network Policies

❌ **HIGH**: No NetworkPolicy in namespace
- **Resource**: Namespace `insecure-app`, pods selected by `app: insecure-app`
- **Issue**: No NetworkPolicy exists, so all ingress and egress is allowed by default.
- **Impact**: Any pod in the cluster can reach `insecure-app`, and the application can reach any destination, which enables lateral movement and data exfiltration.
- **Fix status**: The proposed policy `insecure-app-default-deny` is **unsafe as written**:
  - `ingress: []` with `policyTypes: ["Ingress", "Egress"]` blocks all inbound traffic, including traffic from the ingress controller or other clients that the app serves.
  - The egress rule permits only DNS (UDP/TCP 53) to `kube-system`/`kube-dns`. Any database, cache, message queue, or external API call would be blocked.
- **Recommendation**:
  1. Inventory the application's real dependencies with its owning team (ingress sources, ports, databases, caches, external APIs, and whether it needs the Kubernetes API).
  2. Replace `ingress: []` with explicit ingress rules, for example allowing TCP 8080 from pods labeled `app: frontend` in the namespace that hosts the frontend.
  3. Add one egress rule per confirmed dependency with an exact port. For example, if the app connects to PostgreSQL in namespace `data` on port 5432, add a `namespaceSelector` for `kubernetes.io/metadata.name: data` plus a `podSelector` matching the database pods, with `port: 5432`.
  4. Keep the DNS egress rule.
  5. Validate in a non-production namespace before applying to `insecure-app`.

❌ **HIGH**: No securityContext on container `app` (Deployment `insecure-app`)
- **Missing settings**: `runAsNonRoot`, `runAsUser`
- **Impact**: The container may run as root, so a container escape or application compromise has elevated host-level impact.
- **Recommendation**: Set `runAsNonRoot: true` and a non-zero `runAsUser` (for example, `10001`) in the container securityContext. Confirm the image supports a non-root UID.
