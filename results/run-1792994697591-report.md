# Container Security (Kubernetes) Report: `secure-app`

## Executive Summary

This report covers the Kubernetes Security Review of the `secure-app` namespace, specifically the `api-server` Deployment, its ServiceAccount, Role, and the `api-server-policy` NetworkPolicy. The combined risk level is **HIGH**. The workload has strong container hardening, resource limits, and a scoped Role, but the namespace lacks a default-deny NetworkPolicy, and the pod does not restrict its seccomp profile or Kubernetes API token mounting. The generated fix, a namespace-wide `default-deny-all` policy, **must not be applied as written**. It has no allow rules, so it would block DNS and the traffic that frontend and database pods depend on, and it addresses only one of the six findings. The reviewer returned **ESCALATE**. Engineering should first define the required traffic flows, then implement the corrected changes in the priority order below.

## Findings by Domain

### Container Security (Kubernetes): Workload `api-server`

Risk Level: **HIGH**

The `api-server` workload has tight container hardening, resource limits, and a scoped Role. It lacks a namespace default-deny policy, a seccomp profile, and token automount restrictions.

### RBAC Issues

- ❌ **LOW**: Role `api-server-role` (namespace `secure-app`)
  - **Resource**: `configmaps` rule
  - **Issue**: The rule grants the `list` verb with `resourceNames`. Kubernetes does not apply `resourceNames` restrictions to `list` requests, so the name restriction gives a false sense of scoping. Any ConfigMap in the namespace can be listed, including its contents.
  - **Impact**: The intended least-privilege boundary on ConfigMaps is not enforced.
  - **Fix needed**: Remove the `list` verb from the `configmaps` rule. If the workload needs specific ConfigMaps, grant `get` with explicit `resourceNames`. If it needs listing, scope access another way, such as a dedicated namespace or a label-scoped design.

### Network Policies

- ❌ **HIGH**: No namespace default-deny in `secure-app`
  - **Resource**: Namespace `secure-app` (no default-deny NetworkPolicy exists)
  - **Issue**: Pods not selected by `api-server-policy`, including any frontend or database pods, accept and send all traffic.
  - **Impact**: Lateral movement is unrestricted within and from the namespace. A compromised pod can reach any service and any external endpoint.
  - **Fix needed**: Add a default-deny policy only together with explicit allow rules for every legitimate flow, as described in Unified Recommendations. The generated `default-deny-all` manifest alone is unsafe.

- ⚠️ **MEDIUM**: DNS egress is not restricted to `kube-system`
  - **Resource**: NetworkPolicy `api-server-policy`
  - **Issue**: The DNS egress rule uses an empty `namespaceSelector`, which permits UDP/53 to kube-dns in any namespace.
  - **Impact**: Pods selected by this policy can send DNS queries to any DNS service in the cluster, which enables DNS-based data exfiltration and lookups against unintended resolvers.
  - **Fix needed**: Restrict the DNS egress destination to the `kube-system` namespace and the kube-dns pods.

### Security Contexts

- ⚠️ **MEDIUM**: Seccomp profile not set
  - **Resource**: Deployment `api-server`
  - **Missing setting**: `securityContext.seccompProfile.type` (set `RuntimeDefault`)
  - **Issue**: The container runs without a syscall filter.
  - **Impact**: The attack surface available to a compromised container is larger than necessary.

### Resource Limits

No issues identified. The Deployment `api-server` defines resource limits, which the analyzer recorded as part of its tight container hardening.

### Pod Security

- ⚠️ **MEDIUM**: Kubernetes API token mounted into the pod
  - **Resource**: Deployment `api-server`
  - **Issue**: `automountServiceAccountToken: false` is not set at the pod spec level, so the API token is mounted even though the workload does not need it.
  - **Impact**: A compromised container can use the token to query or act on the Kubernetes API within the permissions of `api-server-role`.

- ⚠️ **MEDIUM**: ServiceAccount auto-mounts tokens
  - **Resource**: ServiceAccount `api-server` (namespace `secure-app`)
  - **Issue**: `automountServiceAccountToken: false` is not set, so the token is auto-mounted into every pod that uses this ServiceAccount, not just `api-server`.
  - **Impact**: Any future workload that adopts this ServiceAccount inherits token exposure by default.

### Verdict: ESCALATE

The reviewer escalated this report for the following reasons:

- The proposed `default-deny-all` NetworkPolicy in `secure-app` selects every pod and denies all ingress and egress. It has no allow rules for frontend or database pods, and it blocks DNS (UDP/53). Applying it would break those workloads.
- The proposed fix leaves five of six findings unaddressed: the DNS `namespaceSelector`, seccompProfile, automount on the Deployment, automount on the ServiceAccount, and the `configmaps` list/`resourceNames` RBAC rule.

A human decision is required on the traffic flows that must be allowed before a default-deny policy is rolled out.

## Unified Recommendations

### HIGH

1. **Map required traffic flows before enforcing default-deny.** Identify every legitimate flow in `secure-app`: frontend to `api-server`, `api-server` to database, DNS, and any external egress. Record the pod labels for each. Do this first, because the current manifests do not provide these labels.

2. **Apply default-deny only with matching allow rules, in staging first.** Replace the generated `default-deny-all` with the following pattern, adjusted to the labels confirmed in step 1. Roll out in a non-production namespace before `secure-app`, and monitor for dropped connections.

   ```yaml
   apiVersion: networking.k8s.io/v1
   kind: NetworkPolicy
   metadata:
     name: default-deny-all
     namespace: secure-app
   spec:
     podSelector: {}
     policyTypes:
     - Ingress
     - Egress
   ```

   Add allow policies alongside it, for example:
   - Ingress to `api-server` pods (`app: api-server`) from frontend pods on the service port.
   - Egress from `api-server` pods to database pods on the database port.
   - Egress from all pods to kube-dns (see the next item).

### MEDIUM

3. **Scope DNS egress to kube-dns in `kube-system`.** In `api-server-policy` (and in every allow policy that permits DNS), replace the empty `namespaceSelector` with the following. This assumes the standard `k8s-app: kube-dns` label, which should be verified in the cluster.

   ```yaml
   egress:
   - to:
     - namespaceSelector:
         matchLabels:
           kubernetes.io/metadata.name: kube-system
       podSelector:
         matchLabels:
           k8s-app: kube-dns
     ports:
     - protocol: UDP
       port: 53
   ```

4. **Set a seccomp profile on `api-server`.** Add the following to the Deployment's pod spec:

   ```yaml
   spec:
     template:
       spec:
         securityContext:
           seccompProfile:
             type: RuntimeDefault
   ```

5. **Disable token automount on the ServiceAccount and the pod.** Set `automountServiceAccountToken: false` on ServiceAccount `api-server`, and also set it in the Deployment's pod spec. Setting it on both prevents accidental mounting from either direction. If a workload later needs API access, enable it explicitly for that workload only.

### LOW

6. **Remove the `list` verb from the `configmaps` rule in `api-server-role`.** Grant `get` only, with `resourceNames` listing the specific ConfigMaps the workload reads. Confirm with the application team that it does not depend on listing ConfigMaps.
