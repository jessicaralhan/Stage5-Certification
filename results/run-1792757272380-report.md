# Infrastructure Security Review Report

## Executive Summary

This review analyzed the Terraform plan for the production Aurora database cluster and its supporting KMS key. The combined risk level is **CRITICAL**. The plan forces a destroy-and-recreate of the production cluster `aws_rds_cluster.prod` because `db_subnet_group_name` changed, which would risk data loss and downtime. The cluster also lacks deletion protection and has several security gaps, including missing audit and error log exports, no explicit security group, a master password stored in state, and a default administrator username. The verdict is **ESCALATE**. Before any apply, a human owner must approve the change, the subnet group reference must be restored or the change otherwise validated, and `prevent_destroy` must be in place on the production cluster.

## Infrastructure (Terraform) Findings

Risk Level: **CRITICAL**

### Destructive Changes

❌ **CRITICAL**: Production Aurora cluster is scheduled for destroy-and-recreate.
- **Resource**: `aws_rds_cluster.prod`
- **Action**: `destroy_and_recreate`
- **Forcing Attribute**: `db_subnet_group_name`
- **Environment**: production
- **Impact**: Destroying the cluster deletes the live database and its data, causing data loss and extended downtime for production workloads. Recreation also requires restoring data from a snapshot or from scratch, depending on the procedure used.

### Security Exposure

❌ **HIGH**: Deletion protection is disabled on the production cluster.
- **Resource**: `aws_rds_cluster.prod`
- **Exposure**: `deletion_protection` is not set
- **Impact**: The production cluster can be deleted with a single API call or Terraform command, with no safeguard against accidental or malicious removal.

⚠️ **MEDIUM**: Audit and error logs are not exported.
- **Resource**: `aws_rds_cluster.prod`
- **Exposure**: `enabled_cloudwatch_logs_exports` is not configured
- **Impact**: Audit and error logs are not shipped to CloudWatch, which weakens detection of unauthorized access and slows incident investigation.

⚠️ **MEDIUM**: No explicit security group is assigned.
- **Resource**: `aws_rds_cluster.prod`
- **Exposure**: `vpc_security_group_ids` is not specified, so the cluster uses the VPC default security group
- **Impact**: Network access is governed by a group that is not explicitly scoped, which makes it difficult to audit which sources can reach the database.

⚠️ **MEDIUM**: Master password is stored in Terraform state.
- **Resource**: `aws_rds_cluster.prod`
- **Exposure**: `master_password` is written to the state file
- **Impact**: Anyone with read access to the state can retrieve the database master credential. The state must be encrypted at rest and access-restricted, and the credential should be managed outside Terraform state where possible.

ℹ️ **LOW**: IAM database authentication is disabled.
- **Resource**: `aws_rds_cluster.prod`
- **Exposure**: `iam_database_authentication_enabled` is not set to `true`
- **Impact**: All access depends on a static password, with no short-lived, IAM-issued credentials.

ℹ️ **LOW**: Master username is the default `admin`.
- **Resource**: `aws_rds_cluster.prod`
- **Exposure**: `master_username` is `admin`
- **Impact**: A well-known username reduces the effort needed for credential-guessing attacks.

ℹ️ **LOW**: KMS key deletion window is at the minimum.
- **Resource**: `aws_kms_key.rds`
- **Exposure**: `deletion_window_in_days` is 7
- **Impact**: A mistaken key deletion gives only seven days to cancel, which leaves little margin to recover encrypted data.

### Cost Impact

- **`aws_rds_cluster.prod`, backup retention**: A 30-day `backup_retention_period` increases Aurora backup storage charges above the 1-day default.
- **`aws_rds_cluster.prod`, compute**: No `aws_rds_cluster_instance` resources appear in the plan. The main compute cost is not represented here and will be incurred separately once instances are added.
- **`aws_kms_key.rds`**: The new key adds a flat monthly fee plus per-request charges. The increase is minor.
- **`aws_rds_cluster.prod`, replacement**: Recreating the cluster would run duplicate storage and snapshot costs until the old resources are removed.

### Verdict: ESCALATE

The change forces replacement of a production database, which requires human sign-off regardless of any proposed fix. The adversarial reviewer escalated the review, and the reviewer's reasoning states that the `{{remediations}}` field was an unfilled template placeholder. The remediation output does contain two populated proposed fixes, so the reviewer should confirm whether those fixes were evaluated before approval.

## Unified Recommendations

**CRITICAL**

1. **Eliminate the forced replacement of `aws_rds_cluster.prod`.**
   - Change `db_subnet_group_name` to `data.aws_db_subnet_group.existing.name` so it points back to the existing subnet group. Confirm the data source resolves to the group currently attached to the cluster.
   - Re-run `terraform plan` and confirm the output shows no `destroy` or `replace` action for `aws_rds_cluster.prod`. Do not apply until this is confirmed.
   - Add `lifecycle { prevent_destroy = true }` to `aws_rds_cluster.prod`. This causes Terraform to fail any plan that would destroy the cluster, which acts as a guardrail for future changes.
   - Obtain explicit sign-off from the database owner before applying any change to this resource.

**HIGH**

2. **Enable deletion protection on `aws_rds_cluster.prod`.**
   - Set `deletion_protection = true`. This blocks deletion through the API and Terraform until the flag is cleared.
   - Apply this change separately from the subnet group fix so its effect is isolated and verifiable.

**MEDIUM**

3. **Export audit and error logs from `aws_rds_cluster.prod`.**
   - Set `enabled_cloudwatch_logs_exports` to the log types supported by the cluster's engine, such as `["audit", "error"]` for Aurora MySQL, and confirm that a CloudWatch log group receives entries.

4. **Assign an explicit security group to `aws_rds_cluster.prod`.**
   - Create a dedicated security group for the cluster and set `vpc_security_group_ids` to reference it. Allow inbound traffic only on the database port from the specific application security groups that require access.

5. **Remove the master password from Terraform state.**
   - Set `manage_master_user_password = true` on `aws_rds_cluster.prod` so that RDS manages the credential in AWS Secrets Manager. Plan this carefully, since it changes how the credential is provisioned and may require coordination with the applications that read it.
   - Until then, confirm the state backend is encrypted and restrict read access to the state to the minimum set of operators.

**LOW**

6. **Enable IAM database authentication on `aws_rds_cluster.prod`.**
   - Set `iam_database_authentication_enabled = true` and grant the application roles the `rds-db:connect` permission for the specific database user.

7. **Replace the default master username on `aws_rds_cluster.prod`.**
   - Change `master_username` from `admin` to a non-default name. Because this may force replacement, perform it only after the subnet group fix and only with the same approval controls as Recommendation 1.

8. **Increase the KMS deletion window on `aws_kms_key.rds`.**
   - Set `deletion_window_in_days` to 30 to allow more time to cancel an accidental deletion.

9. **Review cost assumptions before apply.**
   - Confirm that the 30-day backup retention is required, and budget for the Aurora instance compute that will be added separately.

|---|---|---|---|
| Terraform Safety Review | **ESCALATE** | CRITICAL | Human review of the forced replacement of `aws_rds_cluster.prod`, verification of the subnet group fix in a fresh plan, and sign-off before apply |
