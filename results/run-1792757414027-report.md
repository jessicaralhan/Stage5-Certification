# Infrastructure Security Review: IAM Policy Audit

## Executive Summary

This review covered a single IAM policy document, `AllowEverything`, which contains one statement that grants `Action: "*"` on `Resource: "*"` in a production account. That is equivalent to full administrator access. The policy defines no Principal, so the affected identity is unknown until the policy's attachment point is confirmed. The combined risk level is **CRITICAL**. The statement permits destructive actions, IAM and KMS administration, and privilege escalation, with no MFA, network, time, or session constraints. The reviewer verdict is **ESCALATE**. The proposed remediation is directionally correct but contains defects that must be fixed before it can be applied. Human sign-off is required. Immediate actions are to identify every entity this policy is attached to, remove the wildcard grant under change control, and correct the MFA deny logic before deployment.

---

## Access Control (IAM) Findings

Risk Level: **CRITICAL**

The policy grants unrestricted administrator access to all actions on all resources in production with no MFA, network, or time conditions, making it a severe over-privilege risk.

### Overly Broad Permissions

❌ **CRITICAL**: Statement `AllowEverything` grants full administrator access.
- **Principal**: Not defined in the policy document. The grant applies to any entity the policy is attached to. The attachment point must be identified before remediation.
- **Current scope**: `Action: "*"`, `Resource: "*"`
- **Impact**: Any holder of this grant can read, modify, or delete any resource in the production account.
- **Least-privilege target**: Replace with an enumerated action list. The reviewer's proposed set (`ec2:DescribeInstances`, `ec2:DescribeInstanceStatus`, `ec2:StartInstances`, `ec2:StopInstances`, `cloudwatch:GetMetricData`, `cloudwatch:DescribeAlarms`, `logs:DescribeLogGroups`, `logs:GetLogEvents`) covers read-only inspection and instance start/stop only.

❌ **CRITICAL**: Wildcard action enables IAM and KMS administration.
- **Affected resources**: `arn:aws:iam::*:role/*`, `arn:aws:iam::*:policy/*`, `arn:aws:kms:*:*:key/*`
- **Impact**: Permits role and policy modification, which allows privilege escalation to permanent full control, and KMS key administration, which allows decryption of protected data.
- **Least-privilege target**: Remove all `iam:*` and `kms:*` actions. If the principal needs KMS access for a specific workload, grant only `kms:Decrypt` on named key ARNs.

### Missing Resource Boundaries

❌ **CRITICAL**: Statement `AllowEverything` has no ARN scoping.
- **Affected resources**: `*` (databases, KMS keys, security groups, IAM entities, and all other resources in the account)
- **Impact**: No resource-level constraint limits the blast radius of any action. A single compromised credential can affect every service in production.
- **Least-privilege target**: Scope each statement to specific account and region ARNs, for example `arn:aws:ec2:us-east-1:${aws:PrincipalAccount}:instance/*` and `arn:aws:logs:us-east-1:${aws:PrincipalAccount}:log-group:/prod/*`. Confirm the correct region before applying. The proposed region `us-east-1` is an assumption.

### Missing MFA/Conditions

❌ **CRITICAL**: Destructive actions have no MFA requirement.
- **Affected actions**: `iam:DeleteRole`, `ec2:TerminateInstances`, `kms:ScheduleKeyDeletion`
- **Impact**: Irreversible deletion of IAM roles, production instances, and KMS keys can be performed with a session that has no MFA.
- **Required fix**: The reviewer-proposed deny is defective (see Verdict Reasoning). The standard pattern is a Deny statement with `"BoolIfExists": {"aws:MultiFactorAuthPresent": "false"}`. This denies the destructive actions whenever MFA is absent from the session, including when the key itself is missing. Remove the `NumericGreaterThan` on `aws:MultiFactorAuthAge` from the proposed deny. Its interaction with the absent key causes the deny to never match.

❌ **HIGH**: No network, time, or tag conditions.
- **Gap**: No `aws:SourceIp`, `aws:SourceVpc`, time-of-day, or request tag conditions are present.
- **Impact**: The grant is usable from any network location at any time, including unmanaged networks.
- **Recommendation**: Add `aws:SourceVpc` or `aws:SourceIp` conditions limited to corporate or VPC CIDR ranges on any statement that remains after narrowing. Add a time-of-day condition if operational requirements allow.

### Session Credential Issues

⚠️ **MEDIUM**: No session duration constraint.
- **Policy**: `AllowEverything`
- **Gap**: No session policy or `MaxSessionDuration` is defined. Credentials may remain valid for the 12-hour default or longer.
- **Impact**: A stolen or leaked session token retains full access for an extended period.
- **Recommendation**: Set `MaxSessionDuration` on the role this policy is attached to to 3600 seconds (1 hour), or the shortest value compatible with operational needs.

⚠️ **LOW**: Usage of this grant cannot be confirmed.
- **Gap**: The policy names no role or user, and no usage data was provided.
- **Impact**: This full-access grant may be a stale leftover that is unnecessary but still exploitable.
- **Recommendation**: Pull IAM last-accessed data (`GenerateServiceLastAccessedDetails`) for the attached entity. If the grant has not been used within the review window, remove it rather than narrowing it.

### Privilege Escalation Risks

❌ **CRITICAL**: Role and policy modification paths.
- **Paths**: `iam:AttachRolePolicy`, `iam:PutRolePolicy`, `iam:CreatePolicyVersion`, `iam:SetDefaultPolicyVersion`, `sts:AssumeRole`
- **Impact**: Even after the first two proposed fixes, these actions allow a principal to attach `AdministratorAccess` to itself or to a role it can assume, restoring full control.
- **Mitigation**: Attach a permissions boundary to every IAM role in scope that caps effective permissions at the enumerated actions. Add an explicit Deny on IAM policy-modification actions unless the request carries an approved boundary. Enforce the same restriction through an SCP at the organization level where feasible.

❌ **HIGH**: Destructive key and role deletion.
- **Paths**: `kms:ScheduleKeyDeletion` and `iam:DeleteRole`
- **Impact**: Deleting a KMS key renders data encrypted under it permanently unrecoverable after the waiting period. Deleting a role can break production workloads.
- **Mitigation**: Apply the MFA-based Deny described above. Add `kms:ScheduleKeyDeletion` to a Deny for all principals except a break-glass role, and require change approval for key deletion.

## Unified Recommendations

Priority-ordered. Items are sequenced so that each step is safe to take before the next.

**CRITICAL**

1. **Identify all attachment points for `AllowEverything`.** Enumerate the users, groups, and roles the policy is attached to. Record which of them are in use. This must happen before any change, so that remediation does not break a live workload without notice.
2. **Correct the proposed fixes before applying them.**
   - Rename the duplicate `AllowScopedOps` Sid in the first two fixes.
