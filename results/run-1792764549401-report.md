## Access Control (IAM) Findings

Risk Level: **CRITICAL**

The policy grants unrestricted administrative access to all actions and resources in a production account with no MFA, network, time, or session conditions. This is a critical access posture failure.

### Overly Broad Permissions

❌ **CRITICAL**: Wildcard administrative grant on all actions and resources
- **Principal**: Unidentified principal attached to policy statement `AllowEverything`
- **Current Scope**: `Action: "*"`, `Resource: "*"`, production account
- **Impact**: Every AWS API action is permitted, including destructive operations and IAM administration.
- **Least-Privilege Target**: Replace `AllowEverything` with a statement limited to the actions the principal actually uses. Based on the proposed fix, this would be S3 object read/write and bucket listing on `prod-app-data-bucket`, CloudWatch Logs writes to `/prod/app/*`, and `cloudwatch:PutMetricData`. Confirm the actual usage in CloudTrail before finalizing the list.

❌ **CRITICAL**: IAM wildcard enables privilege escalation and persistent backdoors
- **Principal**: Unidentified principal attached to policy statement `AllowEverything`
- **Current Scope**: `Action: "*"` on `arn:aws:iam::*:*` includes `iam:CreateAccessKey`, `iam:AttachUserPolicy`, and `iam:PassRole`
- **Impact**: The principal can attach administrator policies to itself or other identities, create long-lived access keys for persistence, and pass privileged roles to services.
- **Least-Privilege Target**: Remove all `iam:*` actions from the principal. If IAM write access is genuinely required, scope it to specific role ARNs and deny `iam:PassRole` except to named roles.

### Missing Resource Boundaries

❌ **CRITICAL**: No ARN scoping on any resource
- **Policy**: `AllowEverything`
- **Affected Resources**: `arn:aws:*:*:*:*`, which covers production databases (RDS), KMS keys, EC2 security groups, and all other resources in the production account
- **Impact**: No resource is protected by this policy. A compromised credential can read, modify, or delete any production data or security control.
- **Least-Privilege Target**: Restrict `Resource` to explicit ARNs, such as `arn:aws:s3:::prod-app-data-bucket`, `arn:aws:s3:::prod-app-data-bucket/*`, and `arn:aws:logs:us-east-1:123456789012:log-group:/prod/app/*`. No RDS, KMS, or EC2 resources should appear in this principal's grant.

- **Principal**: Unidentified principal attached to policy statement `AllowEverything`
- **Gap**: No `aws:MultiFactorAuthPresent` condition on create, modify, or delete actions
- **Impact**: Destructive operations succeed with any valid credential, with no second factor.

🔴 **HIGH**: No network, time, or tag conditions

### Session Credential Issues

🔴 **HIGH**: Unbounded credential scope and lifetime
- **Policy**: `AllowEverything`
- **TTL/Scope Problem**: No session policy and no `aws:TokenIssueTime` constraint. Any credentials issued to this principal keep full wildcard access for their entire lifetime.
- **Impact**: A stolen session token or access key provides unrestricted production access until it expires or is revoked. Revocation is the only containment option.

### Privilege Escalation Risks

❌ **CRITICAL**: Self-escalation and persistence via IAM actions
- **Path**: The principal calls `iam:AttachUserPolicy` or `iam:PutUserPolicy` to attach `AdministratorAccess` to itself or another identity, calls `iam:CreateAccessKey` on a privileged user to mint persistent credentials, or calls `iam:PassRole` to launch a privileged service role.

- **Mitigation**: Remove all `iam:*` actions from `AllowEverything`. Add an organization-level service control policy (SCP) that denies `iam:CreateAccessKey`, `iam:AttachUserPolicy`, `iam:PutUserPolicy`, and `iam:PassRole` for all principals except an approved administration role.
