## Access Control (IAM) Findings

**Risk Level**: 🔴 **CRITICAL**

Production IAM policy grants unrestricted root-equivalent access with no resource boundaries, MFA enforcement, or access conditions, creating critical security exposure.

### Overly Broad Permissions

❌ **CRITICAL**: `AllowEverything` policy grants all AWS actions on all resources  
- **Affected Principal**: `AllowEverything`  
- **Affected Resources**: `*` (entire AWS account)  
- **Current Scope**: `Action: "*"` on `Resource: "*"`  
- **Severity**: CRITICAL  
- **Why This Matters**: This grants unrestricted administrative access equivalent to AWS root account credentials. Any principal attached to this policy can perform any action on any AWS service, including:
  - Delete all EC2 instances, RDS databases, and storage buckets
  - Modify IAM permissions and create backdoor credentials
  - Access and exfiltrate data from encrypted KMS resources
  - Disable security controls, logging, and monitoring
  - Incur unlimited costs through resource provisioning

### Missing Resource Boundaries

❌ **CRITICAL**: No resource ARN constraints exist  
- **Affected Principal**: `AllowEverything`  
- **Affected Resources**: All AWS services (IAM, KMS, RDS, S3, EC2 security groups, etc.)  
- **Severity**: CRITICAL  
- **Why This Matters**: Without ARN-level scoping, the policy applies blanket permissions to all resources in the account. An attacker or insider can:
  - Modify all S3 buckets including those containing backups and archives
  - Terminate production RDS instances across all regions and accounts
  - Decrypt all KMS-protected secrets and data keys
  - Create and attach security groups that expose internal systems
  - Modify IAM roles and policies without detection

### Missing MFA/Conditions

❌ **CRITICAL**: No MFA requirements for sensitive actions  
- **Affected Principal**: `AllowEverything`  
- **Gap**: Policy lacks MFA enforcement for `iam:*`, `kms:*`, `ec2:*`, and `s3:*` actions  
- **Severity**: CRITICAL  
- **Why This Matters**: Sensitive actions that can modify, delete, or exfiltrate production data are not protected by multi-factor authentication. This means:
  - Compromised credentials or API keys alone can trigger destructive actions
  - No additional verification step prevents unauthorized automation or scripts from causing damage
  - Compliance requirements (SOC 2, PCI-DSS, ISO 27001) mandate MFA for privileged operations
  - Insider threats can act without leaving an audit trail requiring a second factor

❌ **CRITICAL**: No condition keys limit access scope  
- **Affected Principal**: `AllowEverything`  
- **Missing Conditions**: No IP restrictions, time-based access, VPC endpoints, source tags, or request context validation  
- **Severity**: CRITICAL  
- **Why This Matters**: Without conditions, the policy applies from any source at any time. An attacker with stolen credentials can:
  - Access production systems from untrusted networks or geographies
  - Execute privileged actions during off-hours when monitoring is reduced
  - Bypass network isolation and VPC endpoint policies
  - Use automation to perform actions outside normal business processes

### Privilege Escalation Risks

❌ **CRITICAL**: `AllowEverything` policy allows creation of new admin credentials  
- **Escalation Path**: `iam:CreateAccessKey`, `iam:AttachUserPolicy`, `iam:CreateRole` + `sts:AssumeRole`  
- **Severity**: CRITICAL  
- **Why This Matters**: Any principal with this policy can:
  - Create additional IAM users and access keys
  - Attach administrative policies to newly created principals
  - Create cross-account roles and establish persistence
  - Maintain access even after the original principal is detected and disabled
  - Establish backdoors that survive credential rotation

### 🟠 Priority 2: HIGH – Replace with Least-Privilege Policies (This Week)

4. **Implement Fine-Grained, Role-Based IAM Policies**
   - **Action**: Replace `AllowEverything` with role-specific policies that grant only required permissions
   - **Rationale**: Enforce principle of least privilege; limit blast radius of credential compromise
   - **Implementation Guidance**:

   **For EC2/Compute Operations**:
   ```json
   {
     "Effect": "Allow",
     "Action": [
       "ec2:DescribeInstances",
       "ec2:DescribeTags",
       "ec2:DescribeSecurityGroups"
     ],
     "Resource": "*",
     "Condition": {
       "StringEquals": {
         "aws:RequestedRegion": "us-east-1"
       },
       "Bool": {
         "aws:MultiFactorAuthPresent": "true"
       }
     }
   }
   ```

   **For S3 Access**:
   ```json
   {
     "Effect": "Allow",
     "Action": [
       "s3:GetObject",
       "s3:PutObject",
       "s3:ListBucket"
     ],
     "Resource": [
       "arn:aws:s3:::prod-app-bucket",
       "arn:aws:s3:::prod-app-bucket/*"
     ],
     "Condition": {
       "Bool": {
         "aws:MultiFactorAuthPresent": "true"
       }
     }
   }
   ```

   **For RDS Access**:
   ```json
   {
     "Effect": "Allow",
     "Action": [
       "rds:DescribeDBInstances",
       "rds:DescribeDBClusters"
     ],
     "Resource": "arn:aws:rds:us-east-1:ACCOUNT-ID:db:prod-*",
     "Condition": {
       "Bool": {
         "aws:MultiFactorAuthPresent": "true"
       }
     }
   }
   ```

   **For KMS (Encryption Key Operations)**:
   ```json
   {
     "Effect": "Allow",
     "Action": [
       "kms:Decrypt",
       "kms:GenerateDataKey",
       "kms:DescribeKey"
     ],
     "Resource": "arn:aws:kms:us-east-1:ACCOUNT-ID:key/xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
     "Condition": {
       "Bool": {
         "aws:MultiFactorAuthPresent": "true"
       }
     }
   }
   ```

   - **Key Principles**:
     - Use specific action names instead of wildcards (e.g., `ec2:DescribeInstances` not `ec2:*`)
     - Scope resources to ARNs instead of `"*"` wherever possible
     - Add condition keys to restrict by region, VPC, source IP, and MFA requirement
     - Separate read-only policies from write/delete policies
   - **Timeline**: Design and test policies within 3 days; deploy within 5 days

5. **Enforce MFA on All Sensitive Actions**
   - **Action**: Add `aws:MultiFactorAuthPresent` condition to all policies granting `kms:*`, `iam:*`, `s3:Delete*`, and `ec2:Terminate*` actions
   - **Rationale**: MFA provides defense-in-depth against credential compromise
   - **Implementation**:
     - Audit all existing policies for missing MFA conditions
     - Apply MFA requirement to any action that can delete, modify, or access sensitive data
     - Configure hardware or software MFA (authenticator app, hardware token)
     - Document MFA device assignment for all production-access principals
   - **Compliance**: Meets AWS Well-Architected Framework security pillar and CIS benchmarks

     - **Organizational**: Source tags (department, cost center, project)

## Verdict Summary

### Reasoning

The `AllowEverything` policy represents a **critical security vulnerability** that cannot be automatically remediated by policy generators because:

1. **Policy Interdependency**: The proposed fixes reference specific resources and services (prod-app-bucket, prod-*, us-east-1), but the original unrestricted policy must be **removed entirely** before applying scoped replacements. If both policies coexist, the unrestricted policy continues to present maximal risk.

2. **MFA Enforcement on Automation**: Some of the recommended fixes require MFA conditions, which will break automated deployments, scheduled tasks, and CI/CD pipelines that use service credentials. Implementation requires **human decision** on whether automation can use temporary credentials via STS AssumeRole with MFA-less privileges, or whether automation should be explicitly excluded from MFA requirements via separate policies.

3. **Production Blast Radius**: This policy is attached to principals with active access to production databases, encryption keys, and storage. Removing it without a validated alternative in place could disrupt legitimate operations. **Change control approval and rollback procedures** must be established before modification.

4. **Evidence of Compromise**: CloudTrail logs must be reviewed for signs that this policy was already exploited before remediation proceeds. If breach indicators are found, this escalates to incident response rather than standard policy revision.
