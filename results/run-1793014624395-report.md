#### Data Protection & Loss Prevention

❌ **HIGH**: S3 bucket lacks versioning, MFA delete, and object lock configuration  
- **Resource**: `aws_s3_bucket.app`
- **Issue**: Production S3 bucket is deployed without object versioning, MFA delete, or object lock retention policies. This leaves stored data vulnerable to accidental deletion, malicious overwrite, and irreversible loss of historical versions.
- **Impact**: Production data loss; inability to recover from ransomware or unauthorized modification; compliance violation for data retention requirements.
- **Affected Data**: Unspecified production objects in `aws_s3_bucket.app`

❌ **MEDIUM**: S3 bucket lacks logging configuration  
- **Resource**: `aws_s3_bucket.app`
- **Issue**: No access logging or CloudTrail logging is configured. All S3 API calls, modifications, and access patterns are unaudited.
- **Impact**: No audit trail for security incidents, compliance violations, or forensic investigation; inability to detect unauthorized access or data exfiltration.

---

❌ **MEDIUM**: S3 bucket uses server-side encryption with AWS-managed keys (SSE-S3) instead of customer-managed KMS  
- **Resource**: `aws_s3_bucket_server_side_encryption_configuration.app`
- **Issue**: Encryption algorithm configured as AES256 (SSE-S3) instead of AWS KMS with customer-managed keys. This limits key rotation control, audit capabilities, and compliance options for regulated data.
- **Impact**: No fine-grained key access control; cannot implement automatic key rotation policies; reduced compliance alignment with HIPAA, PCI-DSS, and SOC 2 requirements.

---

#### Access Control & Authorization

❌ **HIGH**: IAM policy grants `s3:PutObject` without encryption or resource conditions  
- **Resource**: `aws_iam_role_policy.app`
- **Issue**: The s3:PutObject action is permitted without conditions restricting encryption method, KMS key, or target bucket path. Any principal assuming this role can create or overwrite objects in the production bucket using any encryption method—including no encryption.
- **Impact**: Unencrypted objects can be written to production storage; data can be modified without audit trail; malicious actors with role access can exfiltrate or corrupt data undetected.

#### Escalation Reasoning

**Remediation Blockers Identified**:

1. **Destructive Remediation Path for Object Lock**  
   Object lock cannot be retroactively added to an existing S3 bucket—the configuration must be enabled at bucket creation time. The proposed remediation `aws_s3_bucket_object_lock_configuration` requires bucket recreation (`aws_s3_bucket.app` must be destroyed and recreated). This is **destructive and requires human approval** for production data impact assessment.

2. **Missing Resource Dependencies**  
   Two of three proposed remediations reference `aws_kms_key.s3`, a KMS key resource that **does not exist in the provided Terraform plan**. The remediation generator cannot complete:
   - Setting `s3:x-amz-server-side-encryption-aws-kms-key-id` in the IAM policy condition requires the KMS key ARN
   - Configuring `kms_master_key_id` in the encryption configuration requires the KMS key ARN
   
   Without this resource defined, remediations are **incomplete and unapplyable**.

3. **Lifecycle Conflict**  
   Switching from SSE-S3 to KMS encryption mid-lifecycle affects only newly created objects. Existing objects (if any) retain SSE-S3 encryption, creating a mixed encryption estate that complicates compliance and auditing.

**Required Actions**:
- [ ] Human review and approval to proceed with bucket recreation (destructive change)
- [ ] Define `aws_kms_key.s3` resource in Terraform with appropriate key policy, rotation, and grants
- [ ] Decide on encryption migration strategy for any existing objects
- [ ] Document business justification for production S3 modifications
- [ ] Implement changes in non-production environment first; validate logging, versioning, and encryption behavior
- [ ] Schedule production deployment with downtime window or blue-green S3 migration approach

## Unified Recommendations

### Priority 1: CRITICAL — Data Protection (Blocking)

**Action**: Enable versioning and object lock on `aws_s3_bucket.app` before first production write  
- Add `versioning { status = "Enabled" }` block to `aws_s3_bucket` resource
- Define `aws_s3_bucket_object_lock_configuration` with `object_lock_enabled = "Enabled"` and default retention rule: `mode = "GOVERNANCE"`, `days = 30`
- **Note**: This requires bucket recreation; plan accordingly with blue-green migration or downtime window
- **Timeline**: Complete before production data ingestion

---

### Priority 2: HIGH — Encryption & Key Management (Blocking)

**Action 1**: Define customer-managed KMS key for S3 encryption  
```hcl
resource "aws_kms_key" "s3" {
  description             = "S3 bucket encryption key for app bucket"
  deletion_window_in_days = 30
  enable_key_rotation     = true
  tags = {
    Environment = "production"
    Managed_by  = "terraform"
  }
}

resource "aws_kms_alias" "s3" {
  name          = "alias/s3-app-bucket"
  target_key_id = aws_kms_key.s3.key_id
}
```

**Action 2**: Update `aws_s3_bucket_server_side_encryption_configuration.app`  
- Replace `sse_algorithm = "AES256"` with `sse_algorithm = "aws:kms"`
- Set `kms_master_key_id = aws_kms_key.s3.arn`
- Apply after KMS key creation is complete

**Action 3**: Restrict IAM policy `aws_iam_role_policy.app` s3:PutObject action with conditions  
```json
"Condition": {
  "StringEquals": {
    "s3:x-amz-server-side-encryption": "aws:kms",
    "s3:x-amz-server-side-encryption-aws-kms-key-id": "<KMS_KEY_ARN>"
  }
}
```
- **Timeline**: Complete before first application write to production bucket

---

### Priority 3: HIGH — Audit & Compliance Logging

**Action**: Enable S3 access logging on `aws_s3_bucket.app`  
```hcl
resource "aws_s3_bucket_logging" "app" {
  bucket = aws_s3_bucket.app.id
  
  target_bucket = aws_s3_bucket.access_logs.id
  target_prefix = "s3-access-logs/"
}

resource "aws_s3_bucket" "access_logs" {
  bucket = "app-s3-access-logs"
  # Configure lifecycle policy to transition logs to Glacier after 90 days
}
```
- Create separate S3 bucket for access logs with 1-year retention
- Configure bucket lifecycle policy to transition logs to Glacier after 90 days for cost optimization
- **Timeline**: Deploy in parallel with encryption changes
