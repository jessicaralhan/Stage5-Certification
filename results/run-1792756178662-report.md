# Infrastructure Security Review

## Executive Summary

This review covered the Kubernetes manifests for the `api-server` workload and its supporting resources in the `secure-app` namespace, analyzed through the Kubernetes Security Review workflow. The combined risk level is **HIGH**. The container hardening baseline is sound, but the namespace has no default-deny NetworkPolicy, and the `api-server` pods auto-mount a ServiceAccount token they do not need. The one proposed remediation, a namespace-wide default-deny policy (`secure-app/default-deny-all`), was **escalated for human review** because applying it as written would break DNS resolution and inbound traffic for workloads that lack matching allow rules. Required actions are: (1) redesign the default-deny rollout with a DNS egress exception after inventorying all pods in `secure-app`, (2) disable ServiceAccount token auto-mounting for `api-server`, and (3) tighten the DNS egress rule in `api-server-policy` to `kube-system` only.

## Container Security (Kubernetes) Findings

Risk Level: **HIGH**

The `api-server` workload has a sound container hardening baseline, but the namespace lacks a default-deny network policy and the pod auto-mounts its ServiceAccount token, leaving production exposure.

### RBAC Issues

❌ **MEDIUM**: `api-server-role` (Role, `secure-app`) grants `list` on `configmaps` with `resourceNames`.
   - **Issue**: RBAC does not reliably enforce `resourceNames` on `list` requests. A caller can list every ConfigMap in the namespace, so the name restriction may not limit access as intended.
   - **Impact**: The `api-server` ServiceAccount may read ConfigMaps beyond those it needs, which can expose configuration data that is sensitive.
   - **Fix needed**: Remove `list` from the `configmaps` rule and keep `get` with `resourceNames`. If `list` is required, move the required ConfigMaps into a separate, narrowly scoped Role or accept namespace-wide read and document the exception.

> **Severity note**: The analyzer rated this finding **LOW**. It is listed here under RBAC because it relates to the ServiceAccount token exposure below.

### Network Policies

❌ **HIGH**: No default-deny NetworkPolicy exists in `secure-app`.
   - **Namespace**: `secure-app`
   - **Policy gap**: Pods that do not carry the `app: api-server` label accept and send all traffic without restriction.
   - **Impact**: Any compromised or misconfigured pod in the namespace can reach `api-server` and any other workload, and can make unrestricted outbound connections (for example, data exfiltration).
   - **Fix needed**: See Unified Recommendation 1. Do not apply the proposed policy as written. Inventory all pods first, then roll out default-deny with explicit allow rules and a DNS exception.

⚠️ **MEDIUM**: The DNS egress rule in `api-server-policy` (NetworkPolicy, `secure-app`) combines `namespaceSelector: {}` with a kube-dns `podSelector`.
   - **Namespace**: `secure-app`
   - **Policy gap**: UDP 53 egress is allowed to kube-dns pods in any namespace, not only `kube-system`.
   - **Impact**: `api-server` pods can send DNS traffic to any namespace that hosts a pod labeled as kube-dns, widening the egress surface.
   - **Fix needed**: Scope the DNS egress rule to `namespaceSelector` matching `kubernetes.io/metadata.name: kube-system` combined with the kube-dns `podSelector` (for example, `k8s-app: kube-dns`), keeping the UDP and TCP 53 ports.

### Security Contexts

⚠️ **MEDIUM**: `api-server` (Deployment, `secure-app`) sets no `seccompProfile` at either the pod or container level.
   - **Missing setting**: `securityContext.seccompProfile.type: RuntimeDefault`
   - **Impact**: The container may run without the default seccomp filter, which leaves more kernel syscalls available to an attacker who achieves code execution.
   - **Fix needed**: Set `seccompProfile: {type: RuntimeDefault}` in the pod-level `securityContext` of the `api-server` Deployment. Test the change in a non-production environment first.

### Resource Limits

ℹ️ **LOW**: `api-server` (Deployment, `secure-app`) mounts the `tmp` and `cache` emptyDir volumes with no `sizeLimit`, and no `ephemeral-storage` limit is set on the container.
   - **Missing limits**: `emptyDir.sizeLimit` on `tmp` and `cache`; `resources.limits.ephemeral-storage` on the `api` container.
   - **Impact**: A runaway process or a write-heavy workload can fill node disk and affect other workloads scheduled on the same node.
   - **Fix needed**: Set `sizeLimit` on both emptyDir volumes and add an `ephemeral-storage` limit to the container's `resources.limits`.

### Pod Security

⚠️ **MEDIUM**: ServiceAccount `api-server` (`secure-app`) does not set `automountServiceAccountToken: false`.
   - **Impact**: The ServiceAccount token is mounted into every pod that uses this ServiceAccount, even though API access is only needed for the Role-scoped reads defined in `api-server-role`. A compromised pod can use the token to call the Kubernetes API.
   - **Fix needed**: Set `automountServiceAccountToken: false` on the ServiceAccount. Then, if the application needs API access, mount the token explicitly through a projected volume in the pod spec.

⚠️ **MEDIUM**: `api-server` (Deployment, `secure-app`) pod spec does not set `automountServiceAccountToken: false`.
   - **Impact**: The `api` container receives a Kubernetes API token it does not need. This finding is the pod-level counterpart of the ServiceAccount finding above.
   - **Fix needed**: Set `automountServiceAccountToken: false` in the pod template spec of the `api-server` Deployment. Apply it together with the ServiceAccount change so the two settings do not conflict.

ℹ️ **LOW**: `api-server` (Deployment, `secure-app`) uses the image `api-server:v1.2.3`, a mutable tag with no registry or digest.
   - **Impact**: The tag can be overwritten, and the image source cannot be verified, which weakens provenance and supply-chain assurance.
   - **Fix needed**: Reference the image by fully qualified registry path and immutable digest (`<registry>/api-server@sha256:<digest>`), and enforce digest pinning in the deployment pipeline.

### Verdict: ESCALATE

The reviewer escalated the proposed `default-deny-all` policy because it applies to every pod in the production namespace `secure-app`, including unlisted workloads, sidecars, and probes. It has no DNS egress exception, so any pod without a matching allow rule, or any pod that relies on cluster DNS, will lose name resolution and inbound traffic. The blast radius justifies human sign-off before the change is applied.

## Unified Recommendations

Recommendations are ordered by priority, based on the severity assigned by the analyzer and the reviewer's verdict.

### HIGH

**1. Roll out namespace default-deny in `secure-app` in stages, not as a single change.**
   - **Step 1 (inventory)**: List every pod in `secure-app` with `kubectl get pods -n secure-app --show-labels`. Identify sidecars, jobs, cron pods, and any pod that depends on DNS or inbound traffic but does not carry `app: api-server`.
   - **Step 2 (allow rules first)**: Before applying any deny policy, create explicit allow NetworkPolicies for each identified workload. Include a DNS egress rule for all pods that need name resolution, scoped to `kube-system` with the kube-dns `podSelector`.
   - **Step 3 (apply default-deny)**: Apply `secure-app/default-deny-all` only after Step 2 is complete. The generated manifest is shown below. It is a starting point and must not be applied unmodified, because it has no DNS exception.

   ```yaml
   apiVersion: networking.k8s.io/v1
   kind: NetworkPolicy
   metadata:
     name: default-deny-all
     namespace: secure-app
   spec:
     podSelector: {}
     policyTypes:
     - Ingress
     - Egress
   ```

   - **Step 4 (validate)**: Confirm that name resolution, probes, and required inbound and outbound paths still work. Keep a rollback command ready (`kubectl delete networkpolicy default-deny-all -n secure-app`).
   - **Reviewer status**: Requires human sign-off before the change is applied.
