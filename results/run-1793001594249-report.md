## Container Security (Kubernetes) Findings

**Risk Level:** **MEDIUM**

The manifests demonstrate strong baseline security controls with proper RBAC scoping, security contexts, and resource limits, but contain an overly permissive egress NetworkPolicy rule and minor hardening gaps.

### Network Policies

❌ **MEDIUM**: Overly permissive egress rule in `api-server-policy`  
   - **Resource:** `NetworkPolicy / api-server-policy` (namespace: `secure-app`)  
   - **Issue:** Egress rule allows traffic to all pods in all namespaces via `namespaceSelector: {}`, creating an unrestricted wildcard egress path for DNS and potentially other services  
   - **Impact:** The api-server deployment can initiate connections to any pod across the cluster, violating least-privilege network segmentation and enabling potential lateral movement or data exfiltration  
   - **Current State:** Policy lacks specificity in destination pod selectors and namespace selectors, allowing cluster-wide egress connectivity  

### Security Context

❌ **LOW**: Missing syscall filtering in `api-server` Deployment  
   - **Resource:** `Deployment / api-server` (namespace: `secure-app`)  
   - **Issue:** Container lacks `seccompProfile` configuration, missing defense-in-depth syscall filtering for production workload  
   - **Impact:** Without seccomp profiles, containers can execute any syscall, reducing isolation and increasing attack surface if container escape is attempted  
   - **Recommendation:** Add `seccompProfile: { type: RuntimeDefault }` to pod security context to enable default seccomp filtering  

### Pod Security

⚠️ **LOW**: Suboptimal image pull policy in `api-server` Deployment  
   - **Resource:** `Deployment / api-server` (namespace: `secure-app`)  
   - **Issue:** Image pull policy is set to `Always`, which may cause unnecessary registry lookups and delays on every pod restart  
   - **Impact:** Production deployments using stable image tags incur unnecessary registry latency; introduces dependency on registry availability for pod rescheduling  
   - **Recommendation:** Change `imagePullPolicy` to `IfNotPresent` for stable production tags to reduce registry calls and improve pod startup resilience  

### Verdict: ESCALATE

**Reasoning:** The proposed NetworkPolicy fix introduces a critical unresolved risk: the final egress rule (`to: podSelector: {}` with port 443) allows traffic to ANY pod in the secure-app namespace on port 443, directly contradicting the original finding and creating a new overly-permissive wildcard path. Additionally, this is a production policy change affecting the api-server that requires explicit human validation of the application's actual egress dependencies (database, DNS, and external services) before deployment. The remediation cannot be auto-approved without confirming:

### Priority 2: HIGH — NetworkPolicy Fix Deployment

**Action:** Apply corrected NetworkPolicy manifest once egress requirements are validated.

**Remediation YAML:**
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-server-policy
  namespace: secure-app
spec:
  podSelector:
    matchLabels:
      app: api-server
  policyTypes:
    - Ingress
    - Egress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              role: client
      ports:
        - protocol: TCP
          port: 8080
  egress:
    # Database access (internal)
    - to:
        - podSelector:
            matchLabels:
              app: database
      ports:
        - protocol: TCP
          port: 5432
    # DNS resolution
    - to:
        - namespaceSelector:
            matchLabels:
              name: kube-system
          podSelector:
            matchLabels:
              k8s-app: kube-dns
      ports:
        - protocol: UDP
          port: 53
    # External HTTPS services (replace with actual service domains/IPs if possible)
    - to:
        - podSelector:
            matchLabels:
              app: external-api-gateway  # MUST be defined; do not use wildcard
      ports:
        - protocol: TCP
          port: 443
```

**Note:** The `podSelector: {}` catch-all rule must be replaced with explicit service selectors. If external services cannot be reached via pod selectors (e.g., cloud APIs outside cluster), document exception and use Egress Network Policies with DNS/CIDR rules instead.

### Priority 3: MEDIUM — Add Seccomp Profile

**Action:** Add syscall filtering to api-server pod security context.

**Implementation:**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-server
  namespace: secure-app
spec:
  template:
    spec:
      securityContext:
        seccompProfile:
          type: RuntimeDefault  # Use default seccomp profile
      containers:
      - name: api-server
        # ... existing container spec ...
```

**Rationale:** RuntimeDefault seccomp profile blocks dangerous syscalls (e.g., `ptrace`, `bpf`) while maintaining application compatibility.
