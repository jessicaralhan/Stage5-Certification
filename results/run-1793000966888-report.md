## Unified Recommendations

### Priority 1: CRITICAL – Privilege Escalation via RBAC (Address Immediately)

**Action 1.1: Replace overly permissive ClusterRole**

Replace the `admin-like-role` ClusterRole with a least-privilege role scoped to required operations only:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: admin-like-role
rules:
- apiGroups: [""]
  resources: ["pods", "pods/logs"]
  verbs: ["get", "list", "watch"]
- apiGroups: ["apps"]
  resources: ["deployments", "statefulsets"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["services"]
  verbs: ["get", "list"]
- apiGroups: [""]
  resources: ["configmaps"]
  verbs: ["get", "list"]
  namespaces: ["insecure-app"]
```

**Rationale**: This role restricts access to read-only operations on application-relevant resources within the `insecure-app` namespace only. Remove wildcard grants entirely; define specific API groups, resources, and verbs.

**Verification**: After applying, test the application with a test pod using this role to confirm all required functionality works. Attempt to access resources outside `insecure-app` namespace and verify denial.

### Priority 2: HIGH – Container Execution as Root (Address Before Production)

**Action 2.1: Add pod-level and container-level security contexts**

Update the `insecure-app` Deployment to enforce non-root execution and read-only filesystem:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: insecure-app
  namespace: insecure-app
spec:
  template:
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        fsGroup: 2000
      containers:
      - name: app
        securityContext:
          allowPrivilegeEscalation: false
          runAsNonRoot: true
          runAsUser: 1000
          readOnlyRootFilesystem: true
          capabilities:
            drop: ["ALL"]
        volumeMounts:
        - name: tmp
          mountPath: /tmp
        - name: var-cache
          mountPath: /var/cache
      volumes:
      - name: tmp
        emptyDir: {}
      - name: var-cache
        emptyDir: {}
```

**Rationale**:
- `runAsUser: 1000` forces execution as unprivileged user
- `readOnlyRootFilesystem: true` prevents filesystem modification and persistent backdoors
- `allowPrivilegeEscalation: false` blocks capability-based privilege escalation
- `capabilities.drop: ["ALL"]` removes all Linux capabilities, preventing direct system calls
- EmptyDir volumes at `/tmp` and `/var/cache` provide writable space for legitimate application needs

**Critical Testing Required**:
- Deploy to staging; run application smoke tests
- Verify all required application functionality operates with UID 1000
- Check application logs for permission errors or failed writes
- Confirm no undocumented dependencies on root or specific capabilities exist
- **Do not proceed to production without successful staging validation**

### Priority 3: HIGH – Network Isolation Missing (Address Before Production)

**Action 3.1: Deploy namespace-scoped NetworkPolicy**

Apply an egress/ingress policy to restrict `insecure-app` pod communications:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: insecure-app-netpol
  namespace: insecure-app
spec:
  podSelector:
    matchLabels:
      app: insecure-app
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          name: ingress-nginx
    ports:
    - protocol: TCP
      port: 8080
  egress:
  - to:
    - namespaceSelector: {}
    ports:
    - protocol: TCP
      port: 443
    - protocol: TCP
      port: 53
    - protocol: UDP
      port: 53
  - to:
    - podSelector:
        matchLabels:
          app: database
    ports:
    - protocol: TCP
      port: 5432
```

**Rationale**:
- Ingress restricted to `ingress-nginx` namespace (label requirement: verify namespace has `name: ingress-nginx` label)
- Egress allows only HTTPS (443), DNS (53 TCP/UDP), and database connection (5432)
- Blocks outbound C2 communication and internal network scanning

**Pre-Deployment Verification**:
- Ensure `ingress-nginx` namespace has label `name: ingress-nginx` applied: `kubectl label namespace ingress-nginx name=ingress-nginx`
- Confirm `database` pods have label `app: database`
- Test from staging pod that egress to external IPs is denied
- Test that pod-to-database communication succeeds
- Monitor application logs post-deployment for any "connection refused" errors indicating legitimate traffic blocked

### Priority 4: MEDIUM – Resource Limits Incomplete (Address Before Production)

**Action 4.1: Add resource limits to the Deployment**

Update container resource specification to include CPU and memory limits:

```yaml
spec:
  containers:
  - name: app
    resources:
      requests:
        cpu: 100m
        memory: 128Mi
      limits:
        cpu: 500m
        memory: 512Mi
```

**Rationale**: Limits prevent unbounded resource consumption; requests ensure pod scheduling. Adjust values based on application profiling (these are example values).

**Implementation Guidance**:
- Use application performance monitoring (APM) or `kubectl top pod` to determine actual resource usage under load
- Set limits at 2–4× the observed peak usage to allow for traffic spikes
- Set requests at 80% of limits to maintain scheduling efficiency
