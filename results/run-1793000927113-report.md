## Container Security (Kubernetes) Findings

**Risk Level: MEDIUM**

The manifests demonstrate strong baseline security posture with proper RBAC scoping, pod security hardening, resource limits, and defense-in-depth network policies. One medium-severity egress overpermission and one low-severity image pull policy concern identified.

### Network Policies

❌ **MEDIUM**: Overly permissive egress rule in network policy
   - **Resource**: `api-server-policy` (NetworkPolicy in `secure-app` namespace)
   - **Issue**: Egress rule allows all traffic to any namespace via empty `namespaceSelector`, enabling unrestricted outbound communication beyond required database and DNS
   - **Impact**: The api-server pod can communicate with any pod in any namespace, including system services in `kube-system`, bypassing intended network segmentation and creating lateral movement risk
   - **Current Configuration**: Egress permits unscoped traffic to all namespaces
   - **Recommended Fix**: Restrict egress to only required destinations:
     - Database traffic: allow egress to pods in `secure-app` namespace on port 5432 (TCP)
     - DNS resolution: allow egress to any namespace on port 53 (UDP) for coredns queries
     - HTTPS calls: restrict to specific pod selectors or namespaces, not all pods across all namespaces
   - **Implementation Note**: The proposed remediation includes an unscoped `podSelector: {}` that permits connections to any pod on port 443, which partially reintroduces the original vulnerability. Human verification is required to confirm actual application dependencies and whether external HTTPS calls are needed, and if so, to which specific services they must connect.

### Pod Security

⚠️ **LOW**: Mutable image tag and missing digest pinning
   - **Resource**: `api-server` (Deployment in `secure-app` namespace)
   - **Issue**: Container image uses tag `v1.2.3` without SHA256 digest pinning and `imagePullPolicy: Always`, increasing supply chain attack risk
   - **Impact**: The kubelet will pull a fresh image on every pod restart, potentially retrieving a compromised or mutated image if the tag is reused or the registry is compromised
   - **Current Configuration**: `image: myregistry.azurecr.io/api-server:v1.2.3` with `imagePullPolicy: Always`
   - **Recommended Fix**: Pin the container image to a specific digest and set `imagePullPolicy: IfNotPresent`:
     ```yaml
     spec:
       template:
         spec:
           containers:
           - name: api-server
             image: myregistry.azurecr.io/api-server@sha256:abcd1234567890abcd1234567890abcd1234567890abcd1234567890abcd1234
             imagePullPolicy: IfNotPresent
     ```
   - **Additional Guidance**: Obtain the correct SHA256 digest for `v1.2.3` by running `docker inspect myregistry.azurecr.io/api-server:v1.2.3` or checking your registry's image manifest. Update CI/CD pipelines to automatically inject digest references during deployment.

### Verdict: ESCALATE

**Reasoning**: The network policy remediation introduces an operational risk that requires human review. The proposed egress rule `to: podSelector: {}` with port 443 permits unrestricted outbound HTTPS traffic to any pod in any namespace, which partially reintroduces the original overpermission vulnerability and could allow unintended communication with kube-system components. Additionally, the DNS egress rule lacks destination restriction and will break if CoreDNS is not running in the `secure-app` namespace. This production change requires verification of:
- Actual application outbound dependencies (which external services does the api-server contact over HTTPS?)
- Current namespace topology and service locations
- Whether a service mesh or egress gateway is in place that handles external traffic
- DNS resolution strategy (is CoreDNS in `secure-app` or a shared namespace?)

Human approval is mandatory before applying this remediation.
