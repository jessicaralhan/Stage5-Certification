## Container Security (Kubernetes) Findings

**Risk Level: HIGH**

The manifests demonstrate strong foundational security practices with pod security contexts, resource limits, and RBAC restrictions, but contain three issues: overly permissive egress NetworkPolicy, mutable image tag, and unnecessary secret access via RBAC.

### Network Policies

❌ **HIGH**: Overly permissive egress NetworkPolicy allows lateral movement and data exfiltration.
   - **Resource**: `api-server-policy` (NetworkPolicy in `secure-app` namespace)
   - **Issue**: The egress rule includes an empty `namespaceSelector`, which permits traffic to all namespaces without restriction. This defeats network segmentation and enables lateral movement to other workloads or exfiltration to external services.
   - **Impact**: A compromised `api-server` pod can communicate with any pod in any namespace, including external networks if allowed by cluster egress policies. This creates a pathway for data exfiltration and cross-namespace compromise.
   - **Recommendation**: Replace the egress rules with explicit allow-lists restricted to:
     - Database pods (labeled `app: database`) on port 5432 TCP only
     - DNS service in `kube-system` namespace on port 53 UDP only
     - Kubernetes API server communication on port 443 TCP (if required by workload)
     - Remove blanket egress rules that permit communication to all pods or namespaces

### RBAC Issues

⚠️ **MEDIUM**: Role grants unnecessary access to database password secret, increasing blast radius.
   - **Resource**: `api-server-role` (Role in `secure-app` namespace, bound to `api-server` ServiceAccount)
   - **Issue**: The role grants `get` and `list` access to secrets resource, explicitly including the `db-password` secret. If the `api-server` pod is compromised, an attacker gains immediate access to database credentials without additional lateral movement.
   - **Impact**: Reduces time-to-compromise for database; enables credential theft and unauthorized database access; violates least-privilege principle if `api-server` doesn't require direct secret access (credentials should be injected via init containers or volume mounts from restricted sources).
   - **Recommendation**: Audit whether `api-server` workload actually requires access to `db-password` secret. If not required, remove secret permissions entirely. If required, limit to only the specific secret needed (e.g., `api-tls-cert`) using `resourceNames` field, removing `db-password` from the permission scope entirely.

### Pod Security

⚠️ **MEDIUM**: Mutable image tag creates risk of unexpected image changes and supply chain attacks.
   - **Resource**: `api-server` (Deployment in `secure-app` namespace)
   - **Issue**: The deployment uses `imagePullPolicy: Always` with a mutable semantic version tag `v1.2.3` instead of an immutable image digest (sha256:...). This means each pod restart pulls the latest image matching that tag, which could change without explicit version bumps if the tag is re-pushed.
   - **Impact**: Unexpected image changes during pod restarts can introduce unvetted code, security vulnerabilities, or malicious payloads without audit trail or explicit deployment approval. Combined with `Always` pull policy, this creates a supply chain vulnerability.
   - **Recommendation**: Replace the mutable tag with an immutable image digest: change `image: api-server:v1.2.3` to `image: api-server@sha256:<digest>`. Retain or adjust `imagePullPolicy` to `IfNotPresent` for non-development environments to improve performance. Implement a CI/CD gate that pins images to verified digests before deployment.

## Unified Recommendations

### Priority 1: HIGH — Network Policy Egress Rules (Production Blocking)

**Action**: Immediately replace `api-server-policy` egress rules before deploying to production.

**Implementation**:
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-server-policy
  namespace: secure-app
spec:
  podSelector:
    matchLabels:
      app: api-server
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 8080
  egress:
  # Database access only
  - to:
    - podSelector:
        matchLabels:
          app: database
    ports:
    - protocol: TCP
      port: 5432
  # DNS only (UDP port 53)
  - to:
    - namespaceSelector:
        matchLabels:
          name: kube-system
    ports:
    - protocol: UDP
      port: 53
  # Kubernetes API (if workload requires it)
  - to:
    - namespaceSelector:
        matchLabels:
          name: default
    ports:
    - protocol: TCP
      port: 443
```

**Validation**: Test that `api-server` pods can communicate with database and DNS only; verify external traffic is blocked via network policies and cluster egress controls.

### Priority 2: MEDIUM — RBAC Secret Access Restriction

**Action**: Remove or minimize secret access in `api-server-role`.

**Steps**:
1. Verify whether `api-server` workload functionally requires `db-password` secret access. Check application logs and configuration.
2. If credentials are needed, implement alternative injection method:
   - Use init container to fetch and mount credentials as a file
   - Use external secret management (e.g., HashiCorp Vault, AWS Secrets Manager)
   - Inject via environment variables from restricted ConfigMap only
3. Update the role to remove `db-password` from secret permissions:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: api-server-role
  namespace: secure-app
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list"]
- apiGroups: [""]
  resources: ["configmaps"]
  verbs: ["get"]
  resourceNames: ["api-config"]
- apiGroups: [""]
  resources: ["secrets"]
  verbs: ["get"]
  resourceNames: ["api-tls-cert"]
```

**Validation**: Confirm workload startup and operation without `db-password` access; audit CloudTrail/audit logs for any failed secret access attempts post-deployment.
