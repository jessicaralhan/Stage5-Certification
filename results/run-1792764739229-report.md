## Container Security (Kubernetes) Findings

Risk Level: **CRITICAL**

The workload has critical cluster-wide RBAC over-privilege via a wildcard ClusterRole bound to app-sa, plus missing network policies and hardening controls in production.

### RBAC Issues

❌ **CRITICAL**: Wildcard ClusterRole grants cluster-admin equivalence.
- **Resource**: ClusterRole `admin-like-role` (cluster-wide)
- **Issue**: Wildcard `apiGroups`, `resources`, and `verbs` make this role equivalent to `cluster-admin`.
- **Impact**: Any principal bound to this role can read all Secrets, modify workloads, change RBAC, and take over the cluster.
- **Recommendation**: Delete the ClusterRole after the replacement binding is in place (see Unified Recommendations, item 1).

❌ **CRITICAL**: Application service account is bound to cluster-admin-equivalent role.
- **Resource**: ServiceAccount `app-sa` (namespace `insecure-app`), via ClusterRoleBinding `app-admin-binding`
- **Issue**: The ClusterRoleBinding grants `admin-like-role` to `app-sa` across the whole cluster.
- **Impact**: A compromise of the `insecure-app` container, which runs as a possibly root user with an auto-mounted token, gives the attacker full control of the cluster.
- **Recommendation**: Delete `app-admin-binding` and replace it with a namespaced Role and RoleBinding limited to `insecure-app` (see Unified Recommendations, item 1).

### Network Policies

⚠️ **HIGH**: No NetworkPolicy in the `insecure-app` namespace.
- **Namespace**: `insecure-app`
- **Policy gap**: No NetworkPolicy selects the `insecure-app` pods, so all ingress and egress is allowed by default.
- **Impact**: Any pod in the cluster can reach `insecure-app`. Compromised pods can reach any internal service, including the Kubernetes API server, and can exfiltrate data to any destination.
- **Recommendation**: Add a default-deny baseline and an explicit allow policy for `insecure-app`. The draft policy `insecure-app-restrict` needs validation before enforcement (see Unified Recommendations, item 4).

### Security Contexts

⚠️ **HIGH**: Container runs without a securityContext and may run as root.
- **Resource**: Deployment `insecure-app`, container `app` (image `app:latest`)
- **Missing settings**: `securityContext` and `runAsNonRoot`
- **Impact**: The process may run as UID 0, which increases the impact of any container escape or application exploit.

⚠️ **MEDIUM**: Root filesystem is writable.
- **Resource**: Deployment `insecure-app`, container `app`
- **Missing settings**: `readOnlyRootFilesystem: true`
- **Impact**: An attacker who gets code execution can modify binaries and configuration in the container image.

⚠️ **MEDIUM**: Privilege escalation is not blocked.
- **Resource**: Deployment `insecure-app`, container `app`
- **Missing settings**: `allowPrivilegeEscalation: false`
- **Impact**: Child processes can gain more privileges than their parent, for example through setuid binaries.

⚠️ **MEDIUM**: Linux capabilities are not dropped.
- **Resource**: Deployment `insecure-app`, container `app`
- **Missing settings**: `capabilities: drop: ["ALL"]`
- **Impact**: The container keeps the runtime's default capability set, which is broader than most application workloads need.

### Resource Limits

⚠️ **MEDIUM**: No CPU or memory limits are set.
- **Resource**: Deployment `insecure-app`, container `app`
- **Missing settings**: `resources.limits.cpu` and `resources.limits.memory` (requests are defined)
- **Impact**: A runaway process or a denial-of-service attack can exhaust node resources and affect other workloads on the same node.
