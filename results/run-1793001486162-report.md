### Security Exposure

#### 1. Missing MFA Delete Protection on Audit Log Bucket

❌ **HIGH Severity**

- **Resource:** `aws_s3_bucket.logs`
- **Issue:** S3 bucket lacks MFA delete protection, allowing unauthorized permanent deletion of audit logs even with proper access controls in place.
- **Impact:** Audit logs can be irreversibly deleted by any principal with `s3:DeleteObject` permissions, eliminating the ability to prove compliance, investigate security incidents, or defend against accusations of misconduct. This directly undermines audit trail integrity and legal defensibility.
- **Remediation Required:** Enable versioning with MFA delete protection. This requires root account credentials and bucket ownership verification.

**Proposed Fix:**
```hcl
resource "aws_s3_bucket_versioning" "logs" {
  bucket = aws_s3_bucket.logs.id
  versioning_configuration {
    status     = "Enabled"
    mfa_delete = "Enabled"
  }
}
```

---

#### 2. Missing Bucket Access Policy (Least-Privilege Enforcement)

❌ **HIGH Severity**

- **Resource:** `aws_s3_bucket.logs`
- **Issue:** S3 bucket lacks bucket policy to restrict access, relying only on the public access block which does not enforce least-privilege access to the audit logs.
- **Impact:** Without an explicit bucket policy, any principal in the AWS account with S3 permissions can potentially access, modify, or delete audit logs. Public access block alone is a preventive control but does not establish positive authorization rules. This violates least-privilege principles and creates unnecessary exposure.
- **Remediation Required:** Attach a bucket policy that explicitly grants access only to authorized roles (e.g., audit systems, compliance officers, security teams).

**Proposed Fix:**
```hcl
resource "aws_s3_bucket_policy" "logs" {
  bucket = aws_s3_bucket.logs.id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect = "Allow"
      Principal = { AWS = "arn:aws:iam::ACCOUNT_ID:role/authorized-role" }
      Action = ["s3:GetObject", "s3:ListBucket"]
      Resource = [aws_s3_bucket.logs.arn, "${aws_s3_bucket.logs.arn}/*"]
    }]
  })
}
```

#### 3. Missing Versioning Configuration

⚠️ **MEDIUM Severity**

- **Resource:** `aws_s3_bucket.logs`
- **Issue:** S3 bucket lacks versioning configuration, which limits audit trail protection and recovery capabilities for audit logs.
- **Impact:** Without versioning, accidentally or maliciously modified audit logs cannot be recovered to their original state. Compliance frameworks and forensic investigations may require proof of log immutability; versioning is a foundational control for audit log retention.
- **Remediation Required:** Enable versioning on the bucket (this is a prerequisite for MFA delete protection).

**Proposed Fix:**
```hcl
resource "aws_s3_bucket_versioning" "logs" {
  bucket = aws_s3_bucket.logs.id
  versioning_configuration {
    status = "Enabled"
  }
}
```

---

#### 4. Missing Access Logging Configuration

⚠️ **MEDIUM Severity**

- **Resource:** `aws_s3_bucket.logs`
- **Issue:** S3 bucket lacks access logging configuration, preventing audit trail of who accesses the audit logs themselves.
- **Impact:** Without server access logging enabled, there is no record of which principals accessed, read, or attempted to access audit logs. This creates a gap in the audit trail: you cannot prove who viewed sensitive audit data or detect unauthorized access attempts after the fact. This is a secondary but important layer of audit visibility.
- **Remediation Required:** Enable S3 server access logging and configure it to write logs to a separate, protected bucket or prefix.
